## 1. 한눈에 보기

```text
[내 컴퓨터]                                   [GitHub]
 uv ── Python 3.12 + 패키지 (.venv)
 lefthook ── 커밋·push 전에 검사 ──push──►  워크플로 9종 자동 검사 ──► 자동 리뷰 + 병합 전 검증(merge-gate) ──► squash merge

                                                   └─► Discord 봇 알림 (선택)
```

| 도구 | 하는 일 |
|---|---|
| **uv** | Python 설치, 가상환경, 패키지 관리를 한 번에. `pip` 대신 쓴다 |
| **lefthook** | 커밋·push 직전에 규칙 위반을 내 컴퓨터에서 먼저 잡는다 |
| **GitHub Actions** | PR을 올리면 같은 규칙·테스트와 PR 상세 검증·병합 게이트를 서버에서 돌린다 |

## 3. 저장소 받기 (저장소당 1회)

```bash
git clone <repo-url>
cd LG_CNS_RAG_main

uv sync                # ① .venv 생성 + Python 3.12 + uv.lock 그대로 설치
lefthook install       # ② git 훅 설치 — 빼먹으면 검사 없이 커밋·push된다
cp .env.example .env   # ③ API 키는 .env에만 (커밋 금지)
```

**확인** — 세 줄이 모두 이렇게 나오면 셋팅 끝이다.

```bash
uv run pytest          # 모두 passed
uv run ruff check .    # All checks passed!
lefthook validate      # All good
```

### 프런트엔드(`frontend/`)를 건드릴 때만 — Node 준비

React 화면을 만지는 사람만 한다(DEC-032). 파이썬만 만지면 필요 없다. **Node 버전의 정본은 `frontend/.nvmrc`**이다(아직 없으면 우지훈이 고정해 올린다). 버전이 다르면 내 컴퓨터와 CI 결과가 달라질 수 있어 반드시 맞춘다.

1. **Node 설치** — Node 버전 관리 도구를 쓰면 버전을 맞추기 쉽다. 아래는 nvm 기준 예시이고, 다른 방법(공식 설치 파일 등)으로 같은 버전을 맞춰도 된다.
   - macOS·Linux: [nvm](https://github.com/nvm-sh/nvm)을 설치한 뒤 `frontend/`로 이동해(`cd frontend`) `nvm install && nvm use` (`.nvmrc`를 읽어 그 버전을 설치·선택한다)
   - Windows: [nvm-windows](https://github.com/coreybutler/nvm-windows)는 `.nvmrc`를 읽지 않으므로 `nvm install <버전>` → `nvm use <버전>`처럼 **`.nvmrc`에 적힌 버전을 직접** 적는다
2. **버전 확인** (`frontend/` 안에서): `node --version`이 `cat .nvmrc`의 버전과 같은지 본다. 다르면 다음 단계로 가지 않는다.
3. **설치·검사** (같은 `frontend/` 안에서):

```bash
npm ci                                                  # package-lock.json 그대로 설치 (npm install 아님)
npm run lint --if-present && npm run build --if-present && npm test --if-present
```

- `--if-present`: `package.json`에 없는 스크립트는 건너뛰고 나머지를 계속 돌린다. **건너뛴 스크립트는 작업 결과에 "없어서 못 돌렸다"고 보고한다**(CI도 같은 방식이고 로그에 경고를 남긴다).
- 패키지 매니저는 **npm만** 쓴다(`yarn`·`pnpm` 금지). `AGENTS.md` 4절이 정본이다.

### 에디터 (VS Code 기준)

- Python 확장 설치 → `Cmd/Ctrl+Shift+P` → **Python: Select Interpreter** → `.venv` 선택
- 줄바꿈·들여쓰기는 `.editorconfig`가 맞춰 준다 (EditorConfig 확장 권장)
- `.vscode/`는 gitignore돼 있다 — 개인 설정은 자유롭게

## 4. 매일의 작업 흐름

```bash
# 1) main 최신화
git switch main
git pull
uv sync                                  # 팀원이 패키지를 추가했을 수 있다

# 2) 브랜치 만들기 — <type>/<소문자-하이픈>
git switch -c feat/hybrid-retriever

# 3) 작업 → 확인
uv run ruff check --fix . && uv run ruff format .
uv run pytest

# 4) 커밋 — <type>: <설명>  (한국어 OK, 첫 글자 대문자 금지)
git add <파일>
git commit -m "feat: 하이브리드 검색 리트리버 추가"

# 5) push → PR
git push -u origin feat/hybrid-retriever
gh pr create --fill                      # 또는 GitHub 웹에서 — --fill은 템플릿 섹션을 넣지 않으므로 만든 뒤 본문을 템플릿대로 고친다 (git_명령어.md 3절)
```

### 이름 규칙 (브랜치·커밋·PR 제목 공통 type 8종)

| type | 언제 | 브랜치 예 | 커밋 / PR 제목 예 |
|---|---|---|---|
| `feat` | 새 기능 | `feat/hybrid-retriever` | `feat: 하이브리드 검색 추가` |
| `fix` | 버그 수정 | `fix/chunk-overlap` | `fix: 청크 중복 제거` |
| `refactor` | 동작 그대로, 구조만 | `refactor/loader-registry` | `refactor: 로더 등록 방식 정리` |
| `docs` | 문서만 | `docs/planning-stage2` | `docs: 유사 서비스 조사 추가` |
| `research` | 실험·탐색 | `research/embedding-compare` | `research: 임베더 2종 비교` |
| `data` | 스키마·인덱스·데이터 파이프라인 | `data/vector-index-v2` | `data: 벡터 인덱스 v2 생성` |
| `chore` | 빌드·CI·설정·패키지 | `chore/add-openai` | `chore: openai 패키지 추가` |
| `remove` | 삭제 | `remove/legacy-loader` | `remove: 옛 로더 삭제` |

브랜치명은 **소문자·숫자·하이픈만**(한국어·대문자·밑줄 금지). 브랜치 하나는 1~2일 안에 끝낼 크기로.

### PR 올릴 때

- 본문은 PR 템플릿 체크리스트를 채운다.
- **첫 줄 또는 마지막 줄에 리뷰어를 `@태그`하고 "리뷰 요청드립니다"** 를 적는다.
- RAG 품질에 영향이 있는 변경이면 "검증 방법"에 **before → after 수치**를 적는다.
- 의존성을 바꿨으면 `pyproject.toml`과 `uv.lock`이 둘 다 들어 있는지 본다.

### 리뷰와 병합

**필수 리뷰어는 없다.** 대신 병합 전에 [`docs/MERGE_PROTOCOL.md`](MERGE_PROTOCOL.md)의 게이트를 돌린다.

1. 자동 리뷰를 받는다 — 리뷰봇이 남기거나, Claude Code에서 `/code-review` 등을 돌려 PR 코멘트로 남긴다.
2. 지적마다 **반영**(커밋) / **반박**(근거 `파일:줄`) / **후속 이슈** 중 하나로 처리한다. 고쳐서 커밋이 늘면 리뷰를 다시 받는다.
3. Claude Code에 **"PR #N 병합 전 검증해 줘"** 라고 하면 `pre-merge-check` 스킬이 게이트 9개를 돌리고 결과 표를 PR 코멘트로 남긴다.
4. `## ✅ 병합 전 검증 결과` 코멘트를 확인하고 **squash merge** 한다. ❌면 병합하지 않는다.

- 리뷰 코멘트는 결론만 쓰지 않고 근거(`파일:줄`, 이유)를 함께 단다.
- 작성자는 자기 PR을 닫지 않는다.
- 병합 후 원격 브랜치는 자동 삭제된다. 로컬은 `git switch main && git pull && git branch -d <브랜치>`. squash merge라 `-d`가 "not fully merged"로 거부하면, PR이 Merged이고 로컬 브랜치 끝 커밋이 PR의 마지막 커밋과 같을 때만 `-D`로 지운다 (병합 뒤 새 커밋이 있으면 지우지 않는다, [`git_명령어.md`](git_명령어.md) 4절).

## 5. 자동 검사 — 무엇이 언제 막히나

### 내 컴퓨터 (lefthook)

| 시점 | 검사 | 막히면 |
|---|---|---|
| `git commit` | `.env`·개인키·1MB 초과 파일 | 해당 파일을 `git restore --staged <파일>`로 빼기 |
| `git commit` | ruff 린트·포맷 (`.py`만) | 대부분 자동으로 고쳐서 다시 넣어 준다. 남은 오류만 손으로 고치고 다시 커밋 |
| `git commit` | 커밋 메시지 형식 | 거부되면 커밋이 만들어지지 않는다 — 형식을 고쳐 `git commit -m "feat: ..."`로 다시 커밋 |
| `git push` | main 직접 push | 브랜치를 만들어서 push |
| `git push` | 브랜치명 형식 | `git branch -m <type>/<올바른-이름>` |

> `--no-verify`나 `LEFTHOOK=0`으로 우회하지 않는다. 우회해도 CI에서 다시 걸린다.

### GitHub (Actions)

| 워크플로 | 검사 |
|---|---|
| `ci.yml` | `uv sync --locked` → ruff lint → ruff format → pytest |
| `pr-verify.yml` | PR 상세 검증 — 코드에 판정 필드·문구, 비밀값, RAG 코드 변경 시 before → after 수치, PR 본문 필수 항목, type 목록 6곳 일치, 문서 링크 |
| `merge-gate.yml` | 병합 게이트 — 현재 커밋 기준 자동 리뷰 · 미해결 스레드 0 · ✅ 병합 전 검증 결과 코멘트(그 뒤 새 리뷰 없음). main 코드로만 실행. ⏸️ 아직 필수 아님(2단계 도입 중) |
| `frontend-ci.yml` | React 화면(`frontend/`) 검사 — `npm ci` → lint → build → test. **필수 체크가 아니며**, `frontend/` 또는 이 워크플로가 바뀐 PR에서만 돌고, `frontend/package.json`이 있을 때만 검사한다. `frontend/`가 없거나 `.nvmrc`·`.gitkeep`·`README.md`만 있으면 도입 전으로 보고 "건너뜀"이고, 그 밖의 파일이 있는데 `package.json`이 없으면 실패한다. `package.json`이 있는데 `frontend/.nvmrc`·`package-lock.json`이 없어도 실패한다 |
| `branch-name-check.yml` | 브랜치명 형식 |
| `pr-title-check.yml` | PR 제목 형식 (squash 후 main 커밋 메시지가 되므로) |
| `review-bot-notify.yml` · `plan-bot-events.yml` | Discord 봇 알림 (시크릿이 없으면 아무것도 안 하고 통과) |
| `stale-branches.yml` | 매주 월요일, 30일 방치된 브랜치 정리 (현재 dry-run — 목록만 출력) |

PR 제목이 틀렸으면 GitHub에서 제목만 고치면 검사가 다시 돈다. `pr-verify`도 PR 본문을 고치면 다시 돈다.

**필수 체크 4개**(`lint-and-test` · `check-branch-name` · `validate-pr-title` · `pr-verify`)가 모두 초록이어야 병합 버튼이 열린다. `merge-gate`는 2단계 도입 중이라 아직 필수가 아니다 — 그동안은 `## ✅ 병합 전 검증 결과` 코멘트를 사람이 확인한다. 자세한 내용은 [`MERGE_PROTOCOL.md`](MERGE_PROTOCOL.md) 2-1절.

## 7. AI 에이전트와 일하기

### 규칙 파일

| 파일 | 역할 |
|---|---|
| `AGENTS.md` | **규칙 원본.** Claude Code·Codex·Cursor 모두 이것을 따른다 |
| `CLAUDE.md` | `@AGENTS.md`를 불러오고 Claude 전용 내용만 덧붙임 — 규칙은 여기서 고치지 않는다 |
| `.claude/settings.json` | Claude Code 팀 공유 권한 (커밋됨) |
| `.claude/settings.local.json` | 개인 권한 (gitignore) |

`AGENTS.md`의 핵심:
- 답변에 "리콜 대상입니다", "원인은 이것입니다" 같은 **판정을 만들지 않는다**, 모든 선례·원인 문장에 **리콜 번호와 출처를 달고 원문 그대로** 옮긴다 <!-- principle-ok: 금지 문구 인용 -->
- 추측 금지 · 단순하게 · 필요한 곳만 고치기 · 테스트로 확인
- RAG 실험은 **같은 평가셋에서 숫자로** 결정. 주 시험지는 정부 기록(조사 → 리콜)을 정답으로 쓰는 대리 평가이고, 평가 질문·정답을 지어내지 않는다
- 에이전트는 **병합 전 검증 게이트를 먼저 돌리고**(사용자가 지시했을 때만 병합), 훅을 우회하지 않고, `.env`를 읽지 않는다

### `.claude/settings.json`이 하는 일

- 허용(묻지 않고 실행): `uv sync`, `uv run pytest`, `uv run ruff`, `uv lock`, `git status/diff/log/branch`, `gh pr view/checks/diff`
- 매번 확인: `gh pr merge`, `git push --force-with-lease`(옵션 위치와 관계없이)
- 차단: `.env` 읽기, 일반 force push(`--force`·`-f`·`-fu`·`-uf`·`-qf`·`+브랜치`·`--mirror`, 옵션 위치와 관계없이 — 그 밖의 묶음과 `git -C … push`는 못 막음), `pip install` — 설정은 Claude Code에만 적용되므로 사람·다른 에이전트는 AGENTS.md 6절 규칙을 따른다 (DEC-035)
- 스킬: `.claude/skills/pre-merge-check/` — 병합 전 검증 절차

### 세션 인계 (`.agent/`)

## 8. 비밀값 · 데이터

- 실제 키는 `.env`에만 둔다. 새 키를 쓰게 되면 `.env.example`에 **이름만** 추가한다.
- 키를 실수로 커밋·공유했다면 **즉시 키를 폐기(rotate)하고 팀에 알린다.** 커밋을 지우는 것만으로는 부족하다.
- 원본 데이터·벡터 인덱스(`data/raw/`, `vectorstore/`, `*.faiss` 등)는 git에 올리지 않는다. 다시 만드는 스크립트를 올린다.
- 유료 API(LLM·임베딩)를 대량으로 호출하기 전에는 예상 비용을 팀에 공유한다.

## 9. 저장소 관리자용 (최초 1회)

> 팀원은 건너뛰어도 된다. 아래는 GitHub 저장소를 처음 만들 때 한 번만 한다.

### 9-1. 첫 커밋과 GitHub 업로드

pre-push 훅이 main push를 막기 때문에 **이 한 번만** `LEFTHOOK=0`을 붙인다.

```bash
git add -A
git commit -m "chore: 협업 저장소 초기 셋팅"
LEFTHOOK=0 gh repo create <owner>/<repo> --private --source=. --remote=origin --push
```

### 9-2. 병합 방식 설정

```bash
gh repo edit <owner>/<repo> \
  --enable-squash-merge \
  --enable-merge-commit=false \
  --enable-rebase-merge=false \
  --delete-branch-on-merge \
  --squash-merge-commit-message pr-title
```

`pr-title`: squash 커밋 메시지를 PR 제목으로 쓴다 → PR 제목 규칙이 그대로 main 이력이 된다.

### 9-3. main 보호 (웹에서)

GitHub → Settings → **Rules → Rulesets → New branch ruleset** → 대상 `main`:
- ✅ Restrict deletions · ✅ Block force pushes
- ✅ Require a pull request before merging
- ✅ Require status checks to pass → `lint-and-test`, `check-branch-name`, `validate-pr-title` 추가 (PR을 한 번 올려 검사가 실행된 뒤에 목록에 나타난다)

> private 저장소는 무료 플랜에서 룰셋이 적용되지 않을 수 있다 (file-converter는 public 전환 후 적용). 이 저장소는 소유자 계정이 Pro라 2026-10-01에 적용됐다 — 현재 상태는 `CONTRIBUTING.md` 맨 아래 표.

### 9-4. 팀원 초대와 CODEOWNERS

```bash
gh api -X PUT repos/<owner>/<repo>/collaborators/<github-id> -f permission=push
```

초대를 **수락한 뒤에** `.github/CODEOWNERS`의 주석을 풀고 아이디를 채운다. 경로마다 **작성자를 뺀 2명 이상**을 오너로 둔다 (혼자 오너인 경로에 본인이 PR을 내면 영원히 승인받지 못한다).

### 9-5. 선택 항목

| 항목 | 방법 |
|---|---|
| Discord 봇 알림 | `gh secret set DISCORD_EVENT_WEBHOOK` (웹훅 URL 입력) |
| 방치 브랜치 실제 삭제 | 몇 주 dry-run 결과를 확인한 뒤 `stale-branches.yml`의 `'true'` 기본값을 `'false'`로 |
| CI용 API 키 (평가 자동화 시) | `gh secret set OPENAI_API_KEY` 등 |

## 10. 자주 묻는 것

| 질문 | 답 |
|---|---|
| 커밋했는데 ruff가 파일을 바꿨다고 한다 | 정상이다. 고친 내용이 그 커밋에 들어갔다. `git show`로 확인 |
| main에서 실수로 작업했다 | 커밋 전이면 `git switch -c feat/<이름>`으로 그대로 옮겨 간다 |
| PR 제목 검사가 빨간불이다 | `Feat:`처럼 대문자로 시작했거나 type이 8종 밖이다. 웹에서 제목만 고치면 된다 |
| CI에서 `uv.lock needs to be updated` | `uv lock` 후 `uv.lock`을 커밋 |
| Windows에서 훅이 `bash: command not found` | Git for Windows를 설치하고 Git Bash에서 작업 |
| 훅이 아예 안 도는 것 같다 | `lefthook install`을 다시 실행 |
