# 데이터 중복·변경 처리 패턴

> 이 문서는 "같아 보이는 데이터"가 생기는 이유를 종류별로 나누고, 각각 어디서 어떻게 처리하는지 적습니다. DEC-034(스냅샷별 보관)의 일부입니다.
> **스냅샷이 아직 1개뿐이라 시간에 따른 변화(①~③)는 측정한 적이 없습니다.** 아래 종류는 데이터 구조에서 예상한 것이고, 두 번째 스냅샷을 올린 뒤 실측값으로 고칩니다.

## 두 종류의 "중복"

| 구분 | 뜻 | 예 |
|---|---|---|
| **시간에 따른 중복** (①~③) | 같은 리콜이 스냅샷마다 다시 들어오는 것 | 11월판에도 10월판과 같은 리콜이 대부분이다 |
| **원래 데이터의 중복** (④~⑥) | 한 스냅샷 안에서 같은 내용이 여러 줄인 것 | 결함 설명이 복사된 리콜 |

## 처리 패턴

| # | 종류 | 처리 | 어디서 | 기록 |
|---|---|---|---|---|
| ① | 스냅샷 사이에 **그대로인 줄** | 줄 해시(`row_sha256`)가 같으면 "그대로"로 센다. 지금은 줄을 전부 저장한다(스냅샷마다 약 27MB) | `load_db load` | `data_builds.change_summary` |
| ② | 같은 리콜이 **내용이 바뀐 것** | 새 스냅샷에 새 내용으로 저장하고, **어느 칸이 바뀌었는지** 칸별 건수를 센다 | `load_db load` | `change_summary.<테이블>.changed_columns` |
| ③ | 새 스냅샷에서 **사라진 줄** | 지난 스냅샷에는 남아 있고, 사라진 건수를 센다. 어디서도 지우지 않는다 | `load_db load` | `change_summary.<테이블>.removed` |
| ④ | **내용이 같은 서로 다른 리콜** | 지우지 않고 `dup_group`으로 묶는다. 검색에서 묶음당 1건만 보이게 하되 회사 목록은 함께 보여 준다 | `nhtsa build` | `recalls.dup_group` (6,404건) |
| ⑤ | **한 캠페인에 리콜 여러 건** | 지우지 않고 앞 6자리(`campaign6`)로 잇는다. 카드 수는 `distinct campno`로 센다 | DB 생성 칸 | `recalls.campaign6` (282개 캠페인) |
| ⑥ | **같은 회사의 여러 표기** | 지우지 않고 `maker`·`maker_group` 대응표로 잇는다. 확인 전에는 적용하지 않는다 | `maker_aliases` (PR #29) | `review`·`review_note` |

참고: 원본 보고서(`causes`)가 여러 판본이면 최신 판본 하나만 쓰고, 지난 판본의 sha256은 `causes.pdfs`에 남깁니다(스크립트 `rclrpt`가 처리).

## 쌓이는 데이터 관리

- 스냅샷이 늘면 오래된 것은 `load_db prune --keep N`으로 **데이터 줄만** 지웁니다. `data_builds`의 줄은 `pruned_at` 표시와 함께 남아서 "그런 스냅샷이 있었다"는 기록은 사라지지 않습니다.
- `--apply` 없이 실행하면 어떤 스냅샷이 얼마나 지워질지 목록만 보여 줍니다.
- 스냅샷이 4~5개 이상 쌓여 용량이 문제가 되면, `row_sha256`을 이용해 "바뀐 줄만 새 버전으로 쌓는" 방식으로 옮길 수 있습니다. 지금은 필요하지 않습니다.

## 두 번째 스냅샷을 올릴 때 할 일

1. `nhtsa fetch` → `nhtsa build`로 새 스냅샷을 만든다 (다른 날짜).
2. `load_db load --causes sample`을 실행하고 출력되는 "직전 스냅샷 대비 새로 생김·바뀜·사라짐·그대로" 건수를 이 문서에 기록한다.
3. 바뀐 칸 분포(`changed_columns`)를 보고 ①~③의 처리가 충분한지, 칸별로 따로 기록할 사례(예: 회사명 정정, 결함 설명 수정)가 있는지 정한다.
