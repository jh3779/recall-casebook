## 5. 역할 분배

### 5-1. 계획 (이슈 #24, 2026-10-06 공지·확정)

| 파트 | 담당 | 한 줄 | 만드는 것 → 받는 사람 |
|---|---|---|---|
| A. 데이터·시험지 | 박예원 | 정부 리콜 데이터를 정리하고 정답이 있는 시험지를 만든다 | `recalls`·`causes`·`eval`·`build` 파일 → B |
| B. RAG(찾기 + 원인 옮기기) | 우지훈 | 결함 한 줄 → 선례 10건, 원인 문장 | `top10`·`cause_candidates` → C |
| C. 검사·화면 + 발표 | 박성호 | 원문 글자 대조, 카드 화면, 발표 | 화면·발표 |
| D. 근거 + 품질 확인 | 이승노 | 법·사례 원문, 실무자 의견, 사람이 하는 품질 확인 | 회사명 표 → A, 실무자 질문 → B, 추정 표현 목록 → C |

**설계 원칙**: AI가 원인을 옮기는 사람(B)·검사하는 사람(C)·품질을 읽는 사람(D)이 서로 다르다 — 자기가 만든 결과를 자기가 검사하지 않는 구조.
**파트끼리는 파일 모양으로만 주고받는다**(동시 작업 가능). 박예원 님이 표본 파일을 10/8까지 먼저 넘기면 B·C가 바로 시작.

## 6. 시간 예산 — 기간 안에 수행 가능했는가

### 6-1. 판단 근거
1. **핵심 범위(이슈 #24의 최소 범위 1~3번)는 10/14에 완성** — 계획 개발 기간(10/12~14)의 마지막 날, 공개 주소로(4번 검사는 10/11). 검색 방식 확정은 계획보다 3일 빨랐다(10/9).
2. **복귀(평가에서 막혀 앞 단계로 돌아간 것)가 8번 있었지만 일정을 넘기지 않았다.** 날짜가 기록으로 확인되는 5건 — 10/9(DB 내장 검색 16%, LLM 제거), 10/10(부품 좁히기 기각, PR 10/11), 10/11(573 판독·표현 정정), 10/19(임베딩 5종) — 은 결정과 같은 날 또는 다음 날 병합됐다. 나머지 3건(90% 시험지 폐기, 문장 자르기 버그, 61→51 정정)은 날짜를 이 문서에서 확인하지 못했다 ⚠. 병합 PR이 몰린 날은 10/7·10/8·10/12(KST)이고 10/12는 감사 후속·서빙 묶음·배포 결정·체크포인트가 겹쳤다.
3. **후반 5일(10/15~19)은 확장 구간**이었다. 계획 밖 기능(8D·3D·케이스북·랜딩·다크 테마)이 들어오며 하루 2~7 PR(체크포인트 포함), 발표 준비와 병행됐다 — 이슈 #24에서 이미 "10/15 이후 데모 마무리와 발표 준비가 겹친다"고 적은 위험이 그대로 일어났다.
4. **일정을 흔든 것은 외부 의존**이었다: 시점 평가 사람 표시본(마감 10/16 이후에도 미수령) → 결국 AI 표시 참고 점수(DEC-079)로 대체. 우리 쪽 코드 작업이 아니라 **다른 사람의 입력을 기다리는 작업**이 병목이었다.

### 6-2. 계획 단계에서 부족했던 것 (다음에 할 것)
| 문제 | 다음에는 |
|---|---|
| 계획에 없던 작업(배포·감사·공개 운영)이 담당 미지정으로 한 사람에게 쏠림 | WBS에 **배포·운영·프로세스 행을 처음부터 넣고 담당을 정한다** |
| 사람의 표시·확인을 기다리는 작업이 마감을 넘김 | 외부 입력 작업은 **마감 2일 전 중간 점검 + 대체안(마감 연장·표시 범위 축소·미측정으로 보고 중 하나)을 미리 정해 둔다** — 이번에는 마감 후에 정했다. AI 표시(DEC-079)는 한시 예외이며 선례가 아니다(`AGENTS.md` 5-2) |
| 확장 작업이 발표 준비와 겹침 | **확장 상한선**: "핵심 완성 후 N일, 발표 D-3부터는 신규 기능 금지" 같은 기준을 계획 단계에서 정한다 |
| 실무자 확인이 가장 먼저 빠짐 | **사용자 검증은 마지막 순위로 두지 말고 기간 중반에 고정 일정**으로 둔다(DEC-055로 범위에서 빠진 것이 "가치 미측정"으로 돌아옴) |
| 버퍼가 없음 | 단계마다 **20% 버퍼**와 "무엇을 포기하면 일정을 지키는가" 목록을 같이 둔다(이번 우선순위 6단계는 잘 작동했다 — 유지) |

### 6-3. 이번에 잘 작동한 것 (유지)
- **"1~3번만 있어도 데모" 우선순위 6단계** — 후반 확장은 보너스로 두고 핵심을 먼저 닫을 수 있었다.
- **사전 고정 기준(+0.03, 질문 기준일 이전 색인)** — 점수가 오른 사후 진단을 채택 근거로 쓰지 않음.
- **결정 기록(DEC)** — 복귀 이유와 기각한 대안이 남아 이번 WBS의 "실제" 칸을 기록만으로 채울 수 있었다.

## 7. 다음 프로젝트용 WBS 작성 규칙 (템플릿)

1. **작업 단위 ≤ 1~2일**, 각 행에 `담당 · 기간 · 산출물 · 완료 기준 · 의존 · 위험` 6칸.
2. **WBS의 최상위는 처리 순서(정의→수집→정리→학습→평가→배포) + 운영·프로세스·발표·사용자 검증**으로 한다. 이번에는 운영·프로세스가 빠져 있었다.
3. **중간 점검(게이트)**: 단계마다 Exit Criteria를 문장이 아니라 **재현 가능한 명령·수치**로 적는다(예: "기준 파일로 0.510 재현").
4. **우선순위 N단계 + 포기 순서**를 계획 시점에 적는다. 확장은 핵심 완료 뒤, 발표 D-3 이후 신규 기능 금지.
5. **외부 입력(사람 표시·승인)이 필요한 작업**은 대체안과 중간 점검일을 함께 적는다.
6. **역할은 RACI로** 쓰고, 담당이 없는 작업은 "미지정"으로 보이게 둔다 — 비어 있는 칸이 위험 신호다.
7. **계획 대비 실제를 매주 한 번 갱신**한다(이번에는 사후에 DEC·PR 기록으로 복원했다).
