## 2. 촬영 전 준비

**서버(촬영 컴퓨터, 키 값은 화면·로그에 내지 않는다 — AGENTS.md 7절)**

```bash
# 터미널 1 — 서버 (저장소 루트, 새 main 기준)
DRAFT_ENABLED=1 ALLOW_ADMIN_DB_FOR_SERVER=1 uv run --env-file .env uvicorn server.api:app --port 8000
# 터미널 2 — 화면
cd frontend && VITE_API_BASE=http://localhost:8000 npm run dev -- --port 5173
```

- `http://localhost:8000/health`가 `build_id 5e32c164b15a544a`·`cards 30350`을 돌려주면 정상이다.
- 3D 모델 파일 `frontend/public/models/sorento.glb`가 있어야 3D 컷이 나온다(팀 드라이브 파일, 저장소에는 없다 — DEC-041).
- 서버 시작에 약 20초, 시작 메모리(RSS)는 약 1.4GB였다.

**화면·브라우저**

- 새 Chrome 창(프로필에 개인 북마크·확장 프로그램 알림이 없는 것), 창 크기 1440×900, 확대 100%, 주소 `http://localhost:5173/#casebook`.
- 이 브라우저의 `localStorage`에는 메모·D4 글이 남는다. 촬영 전 **사건 이름을 새로 정하거나**(`Demo case A`) 시크릿 창을 쓴다. 사건 이름에 **실제 프로젝트명·고객사명을 쓰지 않는다**(화면 안내문도 같은 말이다).
- macOS 알림·메신저 끄기, 녹화는 `Shift+Cmd+5`(화면 일부 녹화, 마이크 따로 녹음하면 나레이션을 뒤에 입히기 쉽다).

**8D 양식 파일(7컷용)**

- **합성 8D 양식 `.docx`를 미리 만든다.** D4 칸이 있는 빈 표여도 되고, 실제 고객사 양식·실제 사건 내용은 쓰지 않는다. 저장소에는 시험용 `.docx` 파일이 없다(시험은 코드로 만든 파일을 쓴다) — **Word에서 연 결과는 아직 확인한 적이 없다**(HANDOFF 알려진 미확인). 촬영 전에 한 번 올려 보고, 안 되면 7컷은 "Copy the D4 text" 컷으로 바꾼다.

**입력 글(6컷, 엔지니어 역할 — 합성·비식별)**

| 칸 | 넣을 글(영어 UI라 영어 권장, 한국어도 가능) |
|---|---|
| Escape Cause | `Demo: the connector seal gap was not covered by the incoming inspection plan.` |
| Root Cause | `Demo: still under investigation.` |
| Verification method | `Demo: bench test planned.` |

위 글은 **서비스가 만든 문장이 아니라 영상 속 엔지니어가 쓰는 연기용 문장**임을 나레이션이 밝힌다(원칙 1).

## 4. 나레이션 대본 (존댓말, 컷 번호가 같다)

원칙 문구는 그대로 읽는다. 괄호 안은 읽지 않는 촬영 메모다.

1. 원인을 모르는 결함을 받은 엔지니어가 쓰는 케이스북 화면입니다. 먼저 사건 이름을 정합니다. 실제 프로젝트명 대신 가명을 씁니다.
2. 영어로 결함을 한 줄 넣습니다. 현대·기아 선례가 먼저, 다른 제조사 선례가 그 아래에 나옵니다.
3. 근거로 삼을 선례를 네 건 고릅니다. 고른 순서대로 상세가 쌓입니다. 원인 문장은 신고서 원문이며, 말한 주체와 리콜 번호, 원본 파일과 해시, 글 정리 방식이 함께 붙습니다. 원인 글이 "미보고·조사 중" 표현으로 시작하는 리콜은 그 표현이 있다고만 표시하며, 원인을 모른다는 뜻은 아닙니다.
4. 원인을 비슷하게 쓴 문장끼리 묶어 봅니다. 모델은 문장을 새로 쓰지 않고 원문만 묶습니다. (실제 묶음에 맞게: 예—납땜 플럭스 오염을 말한 두 건이 한 묶음입니다.) 묶음이 우리 건의 원인이라는 뜻은 아닙니다.
5. 아래는 D4 구역입니다. 확인 질문은 도구가 고정 문장으로 붙이고, 모델이 더하는 질문도 미리 정해 둔 열 문장에서 번호만 고른 것입니다. 질문은 같은지 다른지를 말하지 않고, 확인할 곳만 가리킵니다.
6. 원인은 엔지니어가 직접 씁니다. (지금 쓰는 글은 연기용 예시입니다.) 탈출 원인, 근본 원인, 검증 방법 칸을 도구는 채우지도 제안하지도 않습니다. 쓴 글은 이 브라우저에만 저장되고 서버로 가지 않습니다.
7. 8D 양식 파일을 올리면 D4 칸에 엔지니어가 쓴 글이 들어갑니다. 선례 원문은 기본으로 넣지 않고, 켜면 표 뒤 부록에 출처와 함께 붙습니다.
8. 선례의 부품 분류가 차량 어디쯤인지 3D로 볼 수도 있습니다. 쏘렌토 모델 위에 추정한 도형이라 실제 위치가 아니고, 우리 건과도 관계없는 설명용입니다.
9. 정리하면, 도구는 선례와 원문, 확인할 질문까지 드립니다. 원인 판단은 엔지니어가 합니다.

**글자 수 점검**(공백·괄호 안 제외, 280자/분 기준 — 발표 대본 "시간 점검"과 같은 환산): 3분판 대본 598자 ≈ 2분 8초로 컷 합계 3:05 안에 들고 나머지는 화면 조작·대기 시간이다. 단축판(컷 2·3·4·5·6·9) 대본은 418자 ≈ 1분 29초로 컷 합계 2:18 안에 든다. 단축판은 컷 1을 찍지 않으므로 사건 이름을 미리 입력해 이름이 화면에 보이게 하고(그래야 나레이션 6의 "이 브라우저에만 저장"이 화면과 맞는다 — 이름이 없으면 화면에 "저장되지 않는다"는 경고가 뜬다), 컷 4를 빼면 컷 5의 모델 선택 질문이 화면에 없으므로 컷 4·5는 함께 넣거나 함께 뺀다. 말 없이 화면만 보이는 구간이 길어지면 속도를 늦추거나 컷을 줄인다.

## 7. 말하지 않는 것 (서비스 원칙)

- "원인은 ○○입니다", "리콜 대상입니다", "이 선례가 우리 건에 해당됩니다"처럼 **판정하는 말**을 하지 않는다(원칙 1).
- 묶음·질문을 "AI가 분석했다"고 부풀리지 않는다 — 모델은 **원문을 묶고 정해진 문장의 번호를 고를 뿐**이다.
- 선례 원문을 영상 속에서 **요약하거나 의역하지 않는다** — 화면에 보이는 원문을 그대로 가리킨다(원칙 2).
- 화면에 없는 수치(정확도·시간 절감)를 말하지 않는다. 덱의 수치는 덱 쪽 근거를 따른다.
- 3D는 "설명용 추정 도형"이라고 반드시 말한다. 모델 제작자 표기(MattDoesBlender, CC BY 4.0)는 영상이나 덱 어딘가에 보이게 한다.
- 화면 위 사건 이름·글은 연기용 가명·합성 문장만 쓴다(AGENTS.md 5-2의 비식별 정신).
