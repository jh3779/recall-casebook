## 1. 촬영 전 준비

**서버는 병합된 main 기준으로 띄운다**(아래 명령). 다시 띄워야 하면 저장소 루트에서:

```bash
# 터미널 1 — 서버 (환경 파일 경로는 본인 저장소의 .env)
DRAFT_ENABLED=1 ALLOW_ADMIN_DB_FOR_SERVER=1 uv run --env-file .env uvicorn server.api:app --port 8000
# 터미널 2 — 화면
cd frontend && VITE_API_BASE=http://localhost:8000 npm run dev -- --port 5173
```

- `http://localhost:8000/health`가 `build_id 5e32c164b15a544a`·`cards 30350`을 돌려주면 정상이다.
- 로컬 파일 확인: `frontend/public/models/sorento.glb`(3D), `frontend/public/landing/roadster.mp4`(랜딩 영상, 없어도 동작).
- 키 값은 화면·로그에 내지 않는다(AGENTS.md 7절).

**화면·브라우저**

- 새 Chrome 창(개인 북마크·확장 프로그램 알림 없는 프로필), 창 크기 **1440×900**, 확대 100%.
- **시작 주소는 해시 없는 `http://localhost:5173/`** — 그래야 랜딩이 먼저 뜬다. (`#casebook`으로 시작하면 랜딩을 건너뛴다.)
- 메모·D4 글은 이 브라우저의 `localStorage`에 남는다. 새 사건 이름(`Demo case A`)을 쓰거나 시크릿 창을 쓴다. **실제 프로젝트명·고객사명은 쓰지 않는다.**
- macOS 알림·메신저 끄기. 녹화는 `Shift+Cmd+5`. 나레이션은 따로 녹음해 뒤에 입히면 편하다.

**입력 글(컷 6, 엔지니어 역할 — 합성·비식별)**

| 칸 | 넣을 글 |
|---|---|
| Escape Cause | `Demo: the connector seal gap was not covered by the incoming inspection plan.` |
| Root Cause | `Demo: still under investigation.` |
| Verification method | `Demo: bench test planned.` |

이 글은 **서비스가 만든 문장이 아니라 영상 속 엔지니어가 쓰는 연기용 문장**이라고 나레이션이 밝힌다.

**8D 양식 파일(컷 6 끝의 선택 장면용)**: 합성 `.docx`를 미리 만든다. **2열 표**, 왼쪽 칸에 라벨 `D4 ROOT CAUSE`, 오른쪽 칸은 비워 둔다. 실제 고객사 양식은 쓰지 않는다.

## 3. 나레이션 대본 (존댓말, 컷 번호가 같다)

읽지 않는 메모는 `(촬영 메모: …)`로만 표시한다. 그 밖의 괄호 안 글은 읽는다.

0. 품질·제품안전 엔지니어를 위한 리콜 케이스북입니다. 미국 정부의 공개 리콜 기록에서, 같은 부품일 수 있는 다른 회사의 선례를, 각 선례가 신고한 원인 글 그대로 찾아 드립니다.
1. 먼저 사건 이름을 정합니다. 실제 프로젝트명 대신 가명을 씁니다. 아래에는 이 도구가 하는 일과 하지 않는 일이 있습니다. 리콜 여부나 원인을 판정하지 않고, 원문을 번역하거나 요약하지 않고, 원문에 없는 원인이나 공급사를 짐작하지 않습니다.
2. 영어로 결함을 한 줄 넣습니다. 예시 질문을 눌러 보겠습니다. 현대·기아 선례가 먼저, 다른 제조사 선례가 그 아래에 나옵니다.
3. 근거로 삼을 선례를 네 건 고릅니다. 고른 순서대로 상세가 쌓입니다. 원인 문장은 신고서 원문이며 말한 주체와 리콜 번호, 원본 파일과 해시가 함께 붙습니다. 아래 확인 항목 여섯 가지는 같은 부품인지, 생산 기간, 고장 양상, 시정, 공급사, 원인을 말한 주체를 근거 원문과 나란히 보여 줄 뿐, 같다 다르다를 말하지 않습니다. 원인 글이 "미보고·조사 중" 표현으로 시작하는 리콜은 그 표현이 있다고만 표시하며, 원인을 모른다는 뜻은 아닙니다.
4. 원인을 비슷하게 쓴 문장끼리 묶어 봅니다. 모델은 원문을 고치지 않고 그대로 묶기만 합니다. 묶음이 우리 건의 원인이라는 뜻은 아닙니다. (촬영 메모: 실제 묶음에 맞게 한 문장 더한다. 예 — 납땜 플럭스 오염을 말한 두 건이 한 묶음입니다.)
5. 아래는 D4 구역입니다. 확인 질문은 도구가 고정 문장으로 붙이고, 모델이 더하는 질문도 미리 정해 둔 열 문장에서 번호만 고른 것입니다. 질문은 같은지 다른지를 말하지 않고, 확인할 곳만 가리킵니다.
6. 원인은 엔지니어가 직접 씁니다. 지금 쓰는 글은 연기용 예시입니다. 유출 원인, 근본 원인, 검증 방법 칸을 도구는 채우지도 제안하지도 않습니다. 쓴 글은 이 브라우저에만 저장되고 서버로 가지 않습니다. 선례 원문을 파일에 넣는 체크박스는 기본으로 꺼져 있고, 켜면 제 글 뒤와 부록에 타사 원문이라는 제목과 출처가 붙어 들어갑니다.
7. 선례의 부품 분류가 차량 어디쯤인지 3D로 볼 수도 있습니다. 완성된 모습에서 시작해, 차체를 투명하게 하지 않고 부품을 층별로 걷어내면 선택한 부품 분류가 주황으로 드러납니다. 이어서 그 부품으로 확대하고 부품 이름을 보여 줍니다. 모두 쏘렌토 모델 위의 설명용 연출입니다. 추정한 도형과 순서일 뿐 실제 위치나 정비·분해 순서가 아니고, 우리 건과도 관계가 없습니다.
8. 체크한 선례를 8D 작성 화면으로 넘길 수 있습니다. 선례 내용은 D4에만 넣고, 나머지 단계는 엔지니어가 직접 씁니다. 선례마다 버튼을 한 번 누르면 원인 원문이 D4 칸 본문과 표 뒤 부록에 함께 들어가고, 누르지 않으면 아무것도 들어가지 않습니다. 들어간 인용에는 타사 선례라는 머리줄과 출처가 붙고, 자사 사실이 아니라는 제목이 앞에 붙습니다. 원인 칸은 엔지니어가 채웁니다. (촬영 메모: 8D 파일 내보내기를 찍었다면 양식을 올리면 D4 칸에 제 글과 선례 근거가 들어간다고 한 문장 더한다.)
9. 정리하면, 도구는 선례와 원문, 확인할 질문까지 드립니다. 원인 판단은 엔지니어가 합니다.

| 검색에서 `Too many requests.` | 호출 상한(1분 60회). 화면에 남은 초가 뜨고 그동안 단추가 막힌다. 기다렸다가 이어간다 |
| 검색이 처음에 느림 | 로컬 서버는 보통 1~2초. 서버를 막 띄웠다면 처음 요청이 느리고 3초 뒤 "The server may be waking up…" 안내가 뜬다 |
| 3D 창이 안 뜸 | 모델 파일 없음·코드 로딩 실패 → 화면에 안내가 뜬다. 컷 7을 빼도 흐름은 이어진다 |
| 3D 안내가 5단계·투시로 나옴 | 옛 코드가 뜬 포트다 — 병합된 main 코드가 뜬 포트로 다시 연다 |
| 8D 화면에 `D4 본문·부록에 넣기` 버튼이 없음 | 선례를 하나도 안 담고 `Write 8D without precedents`로 넘어온 것이다. 케이스북에서 선례를 체크한 뒤 `Write 8D from checked (N) →`로 간다 |
| 묶기를 6번 넘게 누름 | `/draft`는 IP별 1분 6회 — 연속으로 6번 넘게 누르지 않는다 |

## 5. 리허설 관찰값 (헤드리스 Chrome 1440×900, 로컬 서버 build `5e32c164b15a544a`, 소프트웨어 렌더링, 병합된 main `5eae108` — 이 PR의 병합 커밋 기준 화면은 같은 코드)

- 랜딩: 영상 재생 확인, `Open casebook` 한 번에 `#casebook`으로 이동.
- 예시 질문 클릭 → 결과 14행(`electric power steering assist loss`). 로컬 검색은 1초 안팎.
- 선례 4개 체크 → 확인 항목 6종이 서버 순서(Same part → Production period → Failure mode → Remedy → Supplier → Who said the cause)로 표시. `Write 8D from checked (4) →` 버튼이 나타남.
- 묶기 약 3.6초 → 묶음 2개, "Picked by the model" 표시(매번 달라질 수 있음).
- `Show in 3D` → 안내 카드 `Guided view Step 1 of 4`(단계 이름 Assembled·Unfold·Zoom·Parts, 투시 없음), `Next`로 4단계까지 오류 없이 진행(콘솔 오류 0). Unfold에서 차체가 불투명한 채 층별로 걷히고(조향 선례는 4층 Interior까지, 핸들이 주황) 엔진 선례는 안쪽 설명용 도형이라 주황 그림이 작다. 3D 창이 열려 안내 카드가 뜨기까지 약 8초(모델 로딩 포함, 소프트웨어 렌더링이라 실제 GPU에서는 더 빠를 것).

## 6. 말하지 않는 것 (서비스 원칙)

- "원인은 ○○입니다", "리콜 대상입니다", "이 선례가 우리 건에 해당됩니다"처럼 **판정하는 말**을 하지 않는다.
- 묶음·질문을 "AI가 분석했다"고 부풀리지 않는다 — 모델은 **원문을 그대로 묶고, 정해진 문장의 번호를 고를 뿐**이다.
- 선례 원문을 **요약하거나 의역하지 않는다** — 화면의 원문을 그대로 가리킨다.
- 화면에 없는 수치(정확도·시간 절감)를 말하지 않는다. 덱의 수치는 덱 쪽 근거를 따른다.
- 3D는 "설명용 추정 도형·연출"이라고 반드시 말한다. 걷어내기 순서를 정비·분해 순서나 결함 위치처럼 말하지 않는다.
- D4 칸·부록에 들어간 인용은 **타사가 신고서에 쓴 원문**이지 우리 건의 원인이 아니라고 말한다 — "선례를 넣으면 원인이 채워진다"고 하지 않는다.
- "같은 부품"이라고 단정하지 않는다 — "같은 부품일 수 있는" 후보이고 대조는 엔지니어가 한다.
- 화면 위 사건 이름·글은 연기용 가명·합성 문장만 쓴다.
