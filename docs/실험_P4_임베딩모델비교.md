> 목적: `docs/실험_P2_검색방식비교.md` 3-0절은 bge-small과 bge-base 두 개만 비교했다("다른 계열은 시험하지 않았다"). 발표 피드백("임베딩 모델 비교 내용을 확인할 것")에 답하려고 **다른 계열 4개와 더 큰 모델 1개**를 같은 749문항으로 더 쟀다(사용자 요청 2026-10-19: "시험 진행해줘", "더 큰 모델 하나 추가"). **서비스는 바꾸지 않는다** — 연구용 시험이고 서버·화면 코드 변경은 없다.

## 1. 요약

- **사전 고정 규칙(결과를 보기 전에 확정)으로는 채택 후보가 없다.** 후보 5개 모두 기각 — 현재 `bge-small-en-v1.5`를 유지한다(DEC-039 그대로).
- 가장 오른 것은 `gte-base`(합친 검색 H@10 0.555 / 회사 이름 뺀 질문 0.543, +0.013 / +0.012)이고, 참고 상한 `bge-large`는 +0.037 / +0.024이지만 지연 82ms(병렬 실행 중 측정)·모델 1.2GB라 기준을 넘지 못한다. 크기를 키우면 오르지만 서비스 한도 안에서 얻는 이득은 기준 폭(0.03)을 넘지 않는다.
- **시험 설계의 한계가 하나 드러났다**: 사전 규칙이 질문 접두어를 fastembed 기본값(붙이지 않음)으로 고정했는데, `snowflake-arctic-embed` 계열은 모델 카드가 질문에 지시문을 붙이라고 안내한다. 접두어 없이 잰 `arctic-embed-m`은 뜻 검색 단독 H@10이 0.240까지 떨어졌다(이상값). **사후 진단**으로 접두어를 붙이면 `arctic-embed-m` 합친 검색 H@10이 0.598 / 0.573(+0.056 / +0.042), `arctic-embed-s`가 0.582 / 0.561(+0.040 / +0.030, 경계값 — §6)으로 오른다. **이 값은 결과를 본 뒤의 진단이라 채택 근거로 쓰지 않는다** — 접두어 규칙을 미리 고정한 2차 탐색(P4b)으로 다시 보고, 채택 확정은 이번 749문항의 결과를 본 뒤에 후보를 고르는 선택 편향이 없는 별도 시험지(시점 평가 등)에서 해야 한다(§8).

- 접두어를 붙이면 `arctic-embed-m`은 뜻 검색 단독이 0.240 → 0.607로 뛰어 현행 `bge-small`(0.463)과 `bge-base`(0.501)를 크게 넘고, 합친 검색도 0.598 / 0.573이다. `arctic-embed-s`도 0.582 / 0.561로 오른다.
- **해석할 때 주의**: ① 접두어를 붙이는 것은 모델 카드의 사용법이지 정답을 보고 정한 값이 아니다. 그러나 이 진단은 사전 결과를 본 뒤에 한 것이라, 같은 749문항에서 채택을 결정하면 사전 규칙이 무너진다. ② `gte-base`·`all-MiniLM-L6-v2`·`bge`는 이번에도 접두어 없이 쟀는데 이 모델들이 접두어를 쓰는 편이 더 좋은지는 모델 카드를 다시 확인하지 않았다 — 접두어가 필요한 모델만 따로 보정하면 비교가 공정하지 않을 수 있다. ③ 접두어 적용 값이 기준 ①을 넘을 수 있는 후보는 `arctic-embed-m`(+0.056 / +0.042, H@1·3·5도 하락 없음)이다. `arctic-embed-s`는 +0.040 / **+0.030으로 경계값**이고 정수 건수로는 22문항 = 0.0294로 0.03에 한 문항 모자란다(사전 규칙은 반올림값 비교였다) — 주 후보는 `arctic-embed-m`이지만 768차원이라 배포 용량(§5) 제약이 있고, `arctic-embed-s`는 용량은 안전하나 경계값이다.

## 7. 읽는 법

1. **"더 큰 모델이 낫다"는 부분만 맞다.** `bge-small → base → large`는 합친 검색 H@10이 0.542 → 0.553(기록값) → 0.579로 오르지만(원래 질문), 회사 이름 뺀 질문에서는 0.531 → 0.530 → 0.555다. 크기를 키울수록 비용(시간 3배→8배, 용량 2배→2.6배)이 커지는 데 비해 이득은 작다.
2. **계열이 달라도 비슷한 크기에서는 큰 차이가 없다** — `gte-base`가 `bge-base`와 거의 같고(+0.002 / +0.013) `all-MiniLM-L6`은 `bge-small`보다 약간 낮다.
3. **측정 설계가 결과를 바꿀 수 있다** — 접두어 하나로 한 모델의 점수가 0.24에서 0.61이 된다. "한 모델·한 설정" 시험의 한계다(§9).
4. 749문항은 대리 평가이고 한 문항이 0.0013이다. 기준 폭 0.03 미만의 차이는 같다고 본다.

## 8. 결정과 후속

- **결정**: 임베딩 모델은 `bge-small-en-v1.5` 유지(DEC-039 그대로). 새 DEC는 만들지 않는다 — 결정이 바뀌지 않았다. 기각한 후보와 이유는 이 보고서가 기록이다(AGENTS.md 5-4).
- **후속 제안(사용자 결정 필요)**: 접두어 규칙(모델 카드의 query prefix)을 **미리 고정한 2차 탐색(P4b)**으로 `arctic-embed-s`·`arctic-embed-m`을 다시 잰다 — **`bge`·`gte-base`·MiniLM의 접두어 유무도 같이 고정해야 공정하다**(현행 기준선도 접두어 없이 쟀고 `bge-small` 모델 카드는 짧은 질문에 지시문을 권장한다). 용량 기준은 모델 파일 크기가 아니라 **묶음 다운로드부터 압축 해제까지의 `/tmp` 최대 사용량**(500MB 한도, `docs/배포_Vercel.md`)으로 정한다. 비교 기준은 반올림값이 아니라 **정수 건수**(0.03 × 749 = 22.47을 올림해 23문항 이상)로 미리 적는다. 카드 벡터는 캐시가 있어 질문 임베딩만 하면 되므로 몇 분이면 끝난다. 다만 같은 749문항에서 후보와 설정을 고른 선택 편향이 남으므로 **채택 확정은 선택에 쓰이지 않은 별도 시험지(시점 평가 후보 묶음 등)**에서 해야 한다. 통과 후보가 나와도 배포 용량(§5)과 시점 평가 후보 묶음이 `bge-small` 기준이라는 제약(P2 보고서 3-0)을 먼저 해결해야 서버에 넣을 수 있다.

## 9. 한계

- **질문 접두어**: 사전 규칙이 fastembed 기본값으로 고정돼 `arctic-embed`를 불리하게 쟀다(§6). 이 한계는 시험 전 보고에서 예고했으나(`접두어는 fastembed 기본값`) 영향이 이렇게 클 줄은 몰랐다.
- 한 번씩만 쟀다(실행마다 흔들림은 임베딩이 결정적이라 작을 것으로 보지만 재지 않았다). 한 문항 0.0013이라 작은 차이는 우연일 수 있다 — McNemar 같은 문항별 검정은 이번에 하지 않았다.
- 지연·임베딩 시간은 병렬 실행 중 측정한 참고값이다. 배포 환경(Vercel 서버리스)에서의 지연·메모리는 재지 않았다.
- fastembed 0.9.0에서 현행 `bge-small`(0.067GB)과 `bge-base`는 양자화(`-Q`) 변형이고 `bge-large`(1.2GB)·`gte-base` 등은 아니다 — §7 1의 "크기를 키우면 오른다"에는 크기와 양자화 효과가 섞여 있고, 시간 "3배 → 8배"는 `bge-base`(P2 단독 측정)와 `bge-large`(병렬 측정)를 한 비율에 섞은 값이다. 판정(기각)에는 영향이 없다.
- 영어 질문만, 같은 계열·크기 위주의 후보 5개다 — 다른 계열의 더 큰 모델(`mxbai-embed-large`·`gte-large` 등)과 다국어 모델은 시험하지 않았다.
- 대리 평가라 "과거 선례 찾기" 성능을 주장하지 않는다(AGENTS.md 5-2). 시점 평가 후보 묶음은 `bge-small` 기준이라 후보 모델의 시점 평가는 하지 않았다.
