# 계획 — 근거 연결형 8D CAR 작성 보조 Agent

## 1. 결정 요약

현재 제품의 중심은 계속 **실제 예상 질문으로 결함 선례를 찾고, 원문과 출처를 추적 가능하게 보여 주는 RAG**다. 그 검색 결과를 한 번 더 구조화해 대시보드와 8D CAR 작성 보조가 함께 쓰는 `EvidencePacket`을 다음 제품 계층으로 둔다.

이 계획은 결함 선례 찾기를 버리는 주제 전환이 아니라 활용 범위 확장이다. 순서는 다음과 같다.

1. 실제 예상 질문 Golden Set 100문항 후보에서 유효성 검사를 통과한 최종 N문항으로 retrieval 성능과 유의성을 확정하고, 제외 수·사유를 함께 보고한다.
2. 검색된 선례에서 부품·고장 양상·영향·원인 원문·시정·공급사·생산 기간을 추출해 대시보드에 표시한다.
3. 같은 근거 묶음을 사용해 8D CAR의 문제 설명과 분석 참고자료를 작성하도록 돕는다.

8D Agent는 근본 원인이나 조치의 적합성을 대신 결정하지 않는다. 이름도 **8D 자동 작성 Agent**가 아니라 **근거 연결형 8D 작성 보조 Agent**로 사용한다.

## 2. 왜 이 순서인가

8D 보고서의 유효성은 문장이 자연스러운지가 아니라 세 가지가 분리돼 있는지에 달려 있다.

- 현재 사건에서 사용자가 제공한 내부 사실
- NHTSA 공개 기록에서 찾은 외부 선례 원문
- 아직 확인해야 할 가설과 빈칸

현재 RAG는 `SearchResponse`에 리콜 카드의 결함·영향·시정, Part 573 원인 원문과 출처, 결함 조사, 공급사·생산 기간 등의 확인 항목을 담는다. 먼저 검색이 실제 질문에서 타당한 선례를 찾는지 검증한 뒤에야 이 데이터를 대시보드와 8D 초안에 재사용할 수 있다. Retrieval 검증보다 문서 생성을 앞세우면 자연스러운 문장이 검색 실패를 가리는 문제가 생긴다.

## 3. 검토한 8D 양식과 주의점

저장소 밖 사용자 제공 파일 `8D REPORT_양식.xls`(2026-10-15)를 읽기 전용으로 확인했다. 파일은 다음 세 시트로 구성돼 있다.

- `8D CAR 작성방법`: 1D 팀 구성 → 2D 문제 설명 → 3D 잠정조치 → 4D 원인 → 5D 영구조치 → 6D 효과 검증 → 7D 재발방지 → 8D 종료
- `8D CAR - 영문`: 작성방법과 같은 순서
- `8D CAR - 한글`: **1D 부적합내용 → 2D 팀 구성**으로 앞의 두 단계 순서가 반대이며, 이후 잠정조치·원인·영구조치·효과 검증·재발방지·종료가 이어진다. F-COST·재작업 시간/수량·폐기 수량, FMEA 갱신, 담당자·검토자·부서장 승인 칸도 있다.

따라서 셀을 `D1`, `D2` 번호만으로 연결하면 한글 양식에 잘못 쓸 수 있다. 양식별 adapter는 번호가 아니라 아래 의미 키로 매핑해야 한다.

```text
team
problem_description
containment_action
root_and_escape_cause
permanent_action
effectiveness_verification
prevent_recurrence
closure
```

양식 원본은 이 PR에 넣지 않는다. 자동 입력을 구현할 때는 원본 파일의 사용 권한과 팀 공유 위치를 먼저 확인한다.

## 4. 제품 흐름과 module seam

```text
사용자 사건 입력
  → 기존 RAG 검색
  → build_evidence_packet(query, search_response)
      ├─ 대시보드 표시
      └─ compose_8d(case_facts, evidence_packet, template_profile)
           → 승인 전 8D 초안 + 근거 부록 + 입력 필요 목록
```

`build_evidence_packet`을 검색 화면과 8D 작성기가 함께 쓰는 깊은 module로 둔다. 검색·추출·출처 보존의 복잡성은 implementation 안에 두고, 두 caller가 같은 근거 규칙을 쓰게 한다.

`EvidencePacket`의 개념 필드는 다음과 같다. 구현 전에 실제 interface와 저장 여부를 별도 결정한다.

```text
EvidencePacket
  retrieval: build_id, snapshot_date, question, returned_campaigns
  precedents[]:
    campno, rank
    facts[]:
      key, value
      source_ref: dataset, campno, action?, file?, pdf_sha256?, submission_date?
      source_span
      text_basis?
  missing_evidence[]
```

불변조건은 다음과 같다.

- 모든 외부 사실은 검색이 반환한 리콜 범위 안에서만 추출한다.
- 원인 문장은 글자 대조를 통과한 원문만 사용하고 말한 주체를 보존한다.
- 모든 선례와 원인 문장은 `CAMPNO`를 필수로 갖고, 사실마다 출처 유형에 맞는 원본을 붙인다. Part 573이면 파일·sha256·제출일·`text_basis`, 결함 조사이면 `ACTION`, flat 파일이면 데이터셋·스냅샷 날짜를 보존한다.
- 부품·고장 양상·영향·원인·시정·공급사·생산 기간 각각에 `source_ref`와 `source_span`을 붙여 필드별로 원문까지 되짚을 수 있게 한다.
- 근거가 없으면 문장을 생성하지 않고 `입력 필요` 또는 `원문에서 찾지 못함`으로 남긴다.
- 사용자 사실, 외부 원문, 확인 질문을 화면과 내보낸 문서에서 구분한다. 출처 없는 조치·시험 방법·기술 권고는 만들지 않는다.
- 검색 실패를 관련 선례가 없다는 결론으로 바꾸지 않는다.

## 5. 8D 단계별 역할

| 의미 영역 | Agent가 할 수 있는 일 | Agent가 하지 않는 일 |
|---|---|---|
| 팀 구성 | 필요한 역할·책임자 빈칸 제시 | 사람·책임자 지정 |
| 문제 설명 | 사용자 입력을 5W2H와 정량 항목으로 구조화, 누락 질문 | 발생 범위·수량 추측 |
| 잠정조치 | 출처가 붙은 유사 선례와 확인 질문 제시 | 출처 없는 조치 추천, 조치 선정·완료 판단 |
| 원인 | Part 573 원인 원문과 조사 요약을 비교 근거로 제시 | 현재 사건의 근본 원인·유출 원인 확정 |
| 영구조치 | 출처가 붙은 과거 시정 사례와 검토 질문 제시 | 출처 없는 조치 추천, 조치 선택·실행 지시 |
| 효과 검증 | 지표·전후값을 적는 빈 입력 틀과 확인 질문 제시 | 출처 없는 시험 방법 추천, 시험 결과 생성·효과 선언 |
| 재발방지 | FMEA·관리계획·표준서·타 제품 전개 질문 제시 | 문서 갱신이나 전개 완료 선언 |
| 종료 | 필수 증빙과 승인 누락 확인 | 적합성·종료 승인·서명 |

가장 안전한 출력은 8D 본문과 별도의 **NHTSA 선례 근거 부록**이다. 본문에는 승인된 사용자 사실만 들어가고, 외부 선례는 현재 사건의 원인이 아니라 분석 참고자료로 표시한다.

## 6. MVP

### 포함

1. 사건 입력: 부품, 고장 현상, 영향, 발생 위치·시점·수량, 차종/공정, 현재 확인 상태. 접근 제어·보존 기간·정본을 정하기 전에는 합성 또는 비식별 입력만 사용한다.
2. `problem_description` 초안(작성방법·영문 D2, 한글 D1)과 누락 정보 질문
3. 기존 RAG를 통한 유사 선례 검색
4. 상위 선례의 원인 원문·시정·공급사·생산 기간과 출처를 근거 부록으로 구성
5. D3~D7에 담당자가 답해야 할 질문과 빈칸 생성
6. 양식별 의미 키 mapping과 사용자 승인 전 `draft` 상태
7. 입력 → 검색 → 인용 → 사용자 승인 이력 보존

### 비범위

- 공개 기록만으로 8D 전체 자동 완성
- 현재 사건의 근본 원인이나 유출 원인 확정
- 잠정·영구·예방 조치 자동 선택
- 조치 효과나 보고서 종료 승인
- 검색 결과 밖의 리콜 번호·원인·공급사 생성
- 실제 사용자 질문 원문이나 회사·팀·프로젝트 식별정보의 저장소 반입

## 7. 평가

평가값은 한 점수로 합치지 않는다.

### Retrieval

- 실제 예상 질문 Golden Set 100문항 후보 중 유효성 검사를 통과한 최종 N문항의 level-2 Hit@10, Precision@10, nDCG@10. 제외 수·사유를 함께 보고한다.
- 후보 Recall@100
- 같은 문항의 before/after 차이에 대한 신뢰구간과 사전에 정한 유의성 검정

### Extraction·근거 안전성

- 필드 precision/recall과 원문 span 정확도
- 원인 원문 일치율 100%
- 외부 문장 출처 완전성 100%
- 검색 범위 밖 출처 생성 0건
- 근거 없는 문장 0건
- 현재 사건의 근본·유출 원인 자동 확정 0건
- 잠정·영구·예방 조치 자동 선택 0건
- 효과 확인·보고서 종료 승인 표현 0건
- 선례의 적용 가능성이나 리콜 필요성을 판정하는 표현 0건
- 한글·영문 양식의 의미 mapping 정확도 100%

### 작성 보조 효용

- 섹션별 전문가 채택률과 수정률
- 올바르게 비워 둔 필드 비율
- 엔지니어 작성 시간 감소
- 생성한 확인 질문의 유용성

Retrieval 유의성이 확인되기 전에는 8D 초안 품질을 검색 성능의 근거로 사용하지 않는다. 대리 평가·시점 평가·실사용 100문항 평가도 합산하지 않는다.

## 8. 다음 순서와 승인 지점

1. **검색 평가 완료**: Golden Set 100문항 후보의 정답·평가 기준·입력 지문을 고정하고 유효성 검사를 통과한 최종 N문항으로 평가와 유의성 검정을 완료한다. 제외 수·사유를 함께 보고한다.
2. **근거 표본 생성**: 현재 `SearchResponse`에서 바로 만들 수 있는 `EvidencePacket` 표본을 소량 생성한다.
3. **추출 평가**: 표본의 부품·고장 양상·원인·시정·공급사·생산 기간과 필드별 출처를 사람이 대조한다. 통과한 필드만 다음 단계로 넘긴다.
4. **대시보드 설계**: 검증된 `EvidencePacket` 필드를 어떤 우선순위와 표현으로 보여 줄지 정한다.
5. **8D MVP interface 확정**: 내부 사건 입력 필드, 접근 제어·보존 기간·정본, 양식 공유·사용 권한, 근거 부록 위치, 승인 흐름을 정한다.
6. **양식 adapter 구현**: 한글·영문 시트의 의미 mapping을 테스트로 고정한다.
7. **실무자 파일럿**: 완성도가 아니라 작성 시간·수정량·근거 추적 가능성을 확인한다.

유료 모델 대량 호출, 실제 사용자 질문 추가, 원본 양식 저장소 반입, 내부 사건 데이터 연동은 각각 기존 승인 규칙을 따른다. 내부 사건 입력의 접근 제어·보존 기간·정본을 정하기 전에는 실제 회사 사건 자료를 사용하거나 로그·저장소에 남기지 않는다.

## 9. 열린 결정

- 8D Agent가 받을 내부 사건 입력의 최소 필드와 보관 위치
- 원문·사진·시험 결과 같은 내부 증빙의 접근 제어와 보존 기간
- 근거 부록을 기존 workbook의 새 시트로 넣을지 별도 파일로 둘지
- 한글·영문 중 첫 지원 양식과 실제 배포 대상
- 초안 승인자와 단계별 수정 이력의 정본
- 대시보드와 8D Agent가 공유할 `EvidencePacket`의 최종 interface
