# 리랭커(재순위화) 시험 계획 — 초안

> 작성: 2026-10-12 · 상태: **초안 — 사용자 확인 전.** 이 문서의 "사전 고정 규칙"(3절)은 **확인을 받아 커밋한 뒤에** 시험을 돌려야 의미가 있다. 결과를 본 뒤 규칙을 바꾸면 그 시험은 무효이고 새 시험으로 다시 한다 (AGENTS.md 5-1·5-2, 기준 폭은 [`기획_결함선례.md`](기획_결함선례.md) 6절).
> 이 계획은 현재 목표(화면 연결·시점 평가·배포, `.agent/HANDOFF.md`) 밖의 **새 작업**이다. 착수 여부와 시점은 사용자가 정한다 (7절).
>
> **현재 상태(2026-10-15, [DEC-060](../../.agent/DECISIONS.md))**: 위 두 줄은 2026-10-12 작성 당시 서술이다(원본 SHA-256 `edbb4d9e…` — 이 메모 외 본문은 그대로). 담당은 이승노(검색 개선 실험, 이슈 #128)로 정해졌고, 3절·7절은 아직 **미확정**이다 — 확정 커밋 전에는 749문항을 실행하지 않는다. 확정 때 함께 고칠 것: ① 재정렬 대상 N(아래 50, 또는 이슈 #128의 상위 10·20)과 N별 채택 기준. ② **용량 기준을 모델 파일 크기가 아니라 배포 `/tmp` 최대 사용량으로** — 서버는 묶음 tar를 `/tmp`에 남긴 채 모델 파일을 따로 풀어(`server/rag/bundle.py`) 묶음에 넣은 리랭커는 두 번 잡힌다. 현재 묶음 155.4MB(실측 — DEC-049·051의 측정 기록; 이 메모를 처음 쓸 때는 추정 약 160MB였다) + 풀린 임베딩 모델 약 67MB + 0.15GB 리랭커×2 ≈ 522MB(처음 계산 527MB)로 500MB 한도를 넘을 수 있으므로, 묶음에 넣을지 따로 받을지 먼저 정하고 0.15GB 후보를 자동 통과시키지 않는다. ③ 후보별 고정 revision과 모델·토크나이저·설정 파일 SHA-256을 표본 시험에서 기록해 전체 시험 전에 커밋하고, 결과 메타에 `fastembed` 판본·파일 지문을 남겨 서버 반영 때 같은 지문인지 확인한다(AGENTS.md 2-4·5-1).

## 1. 왜 하나 — 현재 검색이 놓치는 곳

2026-10-12에 749문항을 BM25 단독으로 돌려 정답 리콜의 최고 순위를 세었다 (일회성 계산, 저장소 스크립트가 아님 — 이 시험의 첫 단계에서 저장소 스크립트로 다시 재현한다).

| 정답 순위 | 문항 | 비율 |
|---|---|---|
| 1위 | 230 | 31% |
| 2~10위 | 152 | 20% |
| **11~100위** | **135** | **18%** |
| 101위 이하 | 223 | 30% |
| 단어가 하나도 안 겹침 | 9 | 1% |

- 정답이 **상위 100 안에는 있는데 10위 밖**인 문항이 18%다. 후보를 건지는 일(찾기)은 되었고 **순서를 고르는 일**이 모자란 구간이다. 이 구간을 위로 올리는 것이 재순위화다.
- 서버는 BM25 상위 100 + 뜻 검색 상위 100을 RRF로 합친다 (`server/rag/search.py:12`, DEC-039). 합친 뒤의 순위 분포는 이 시험의 0단계에서 잰다 (BM25 수치를 그대로 쓰지 않는다).
- 풀리지 않는 구간도 있다: 질문이 `SEE ATTACHED SUMMARY.`처럼 내용이 없는 문항(내용 단어 8개 미만 46문항, BM25 Hit@10 0.11)은 순서를 바꿔도 소용없다. 그래서 **기대 효과의 상한은 18%p보다 훨씬 작다**고 본다.

**가설**: 질문과 카드 글을 같이 읽고 점수를 매기는 모델(cross-encoder)을 RRF 상위 N개에 적용하면, 같은 749문항에서 Hit@10이 기준 폭(0.03) 이상 오른다.

## 2. 왜 이 방식이 서비스 원칙과 맞나

| 원칙 | 영향 |
|---|---|
| 판정하지 않는다 | 리랭커 점수는 **순서를 정하는 데만** 쓰고 응답에 노출하지 않는다 ("관련도 0.93"이 판정처럼 읽히지 않게) |
| 근거 없는 말을 하지 않는다 | 리랭커는 검색이 넘긴 후보(RRF 최대 200개) **안에서 순서만** 바꾼다. 새 리콜을 만들지 않으므로 "인용은 검색이 넘긴 범위 안에서만"이 그대로 지켜진다 |
| 추적 가능해야 한다 | 채택하면 응답과 build 기록에 리랭커 모델 이름·버전을 남긴다 (DEC 필요) |
| 로컬 오픈소스만 (DEC-038) | `fastembed==0.9.0`이 이미 `TextCrossEncoder`를 갖고 있다. **새 의존성 없음**, 유료 API 호출 없음 |

## 3. 사전 고정 규칙 (결과를 보기 전에 확정)

| 항목 | 고정 값 |
|---|---|
| 입력 순위 | 서버와 같은 계산의 RRF 순위 (`server/rag/search.py`의 `Searcher.search`, BM25 상위 100 + bge-small 상위 100, k=60) |
| 재순위 범위 | RRF 상위 **N = 50** (N은 하나만 쓴다. 다른 N을 시험하지 않는다) |
| 재순위 방법 | 상위 50개를 리랭커 점수 내림차순으로 다시 늘어놓고, 51위 이하는 RRF 순서 그대로 둔다. **RRF 점수와 섞는 가중 합산은 하지 않는다** (섞는 비율을 정답을 보며 맞추는 일이 되므로) |
| 카드 글 | `card_text` (결함+결과+시정) 그대로. 잘라내기·길이 제한은 모델 기본값을 쓰고 바꾸지 않는다 |
| 질문 | 원래 질문과 회사 이름 뺀 질문(`BRANDS` 고정 목록) **둘 다** (기존 보고서 3-A·3-B와 같음) |
| 후보 모델 (3개, 이 안에서만) | ① `Xenova/ms-marco-MiniLM-L-6-v2` (0.08GB) ② `Xenova/ms-marco-MiniLM-L-12-v2` (0.12GB) ③ `jinaai/jina-reranker-v1-turbo-en` (0.15GB) — 모두 apache-2.0 |
| 제외한 모델 | `BAAI/bge-reranker-base`(1.04GB)·`bge-reranker-v2-m3`(0.57~2.27GB): 배포 함수 크기 한도(`docs/guides/배포_Vercel.md` 3절, `/tmp` 한도 **500MB**)에 맞지 않음. `jina-reranker-v2-base-multilingual`: 라이선스 cc-by-nc-4.0(비상업)이라 제외 |
| 시험지 | 같은 749문항 (`eval.jsonl`), 정답 = 조사의 `CAMPNO`. 입력 사본이 기준 파일과 같아야 "재현"이고 다르면 "재평가"로 보고한다 (AGENTS.md 5-1) |
| 지표 | 주 지표 Hit@10(any). 함께 Hit@1·3·5, first@10(참고), 2014-08-20 이후 94문항, 2010년 이후 214문항 |
| 비교 기준 | 같은 입력의 현행 RRF: 원래 질문 H@10 **0.542**, 회사 이름 뺀 질문 **0.531** (`실험_P2_검색방식비교.md` 3-A·3-B, `server.rag.parity`로 재현 확인) |

### 채택 기준 (모두 만족해야 채택)

1. **효과**: 원래 질문과 회사 이름 뺀 질문 **둘 다** H@10이 현행보다 0.03 이상 높다 (0.572 이상 / 0.561 이상).
2. **후퇴 없음**: 두 질문 모두 H@1·H@3·H@5 중 어느 것도 현행보다 0.03 이상 낮지 않다.
3. **지연**: 질문 1건당 추가 시간 p95가 **500ms 이하** (이 맥 CPU에서 잼. 배포 환경은 다를 수 있어 첫 배포에서 다시 잰다). ← *제안값, 7절에서 확인*
4. **용량**: 모델 파일이 **0.15GB 이하** (서빙 묶음 약 220MB에 더해도 `/tmp` 500MB 안).
5. 여러 모델이 1~4를 통과하면 **더 작고 빠른 모델**을 고른다. 점수가 더 높은 모델은 다른 통과 모델보다 H@10이 0.03 이상 높을 때만 고른다.

기준 폭 0.03 미만의 차이는 "같다"로 본다. 같다는 결과도 **기각으로 기록**한다 (AGENTS.md 5-3·5-4).

## 5. 하지 않는 것

- **시점 평가 후보 묶음으로 리랭커를 평가하지 않는다.** 그 묶음은 BM25 상위 20 + 현행 방식 상위 20이라 리랭커가 올린 새 후보는 정답 표시가 없다. 정답을 본 뒤 모델을 바꾸는 일과 같다 (bge-base 때와 같은 이유, `실험_P2_검색방식비교.md` 3-0절).
- 시험 결과를 보고 N·모델·가중치를 바꿔 다시 재지 않는다. 다른 값을 보려면 새 규칙을 먼저 고정한 새 시험으로 한다.
- 정답에 자주 나오는 리콜을 고정으로 끼우는 방식 등 정답을 보고 맞추는 방식은 쓰지 않는다 (AGENTS.md 5-2).
- 후보 3개 중 최고점을 고르면 선택 편향이 생기므로, 3절 "채택 기준" 5항의 규칙으로만 고른다.
- 이 시험으로 시점 평가 성능이나 "과거 선례 찾기" 성능을 주장하지 않는다 — 749문항은 대리 평가다.

## 6. 알려진 한계 (미리 적어 둠)

- 749문항 질문은 조사관 문체의 대문자 문장이 많고 2010년 이후는 214문항뿐이다. 이 시험에서 오른 점수가 현대 영어 결함 한 줄 질문에서도 오르는지는 **알 수 없다**.
- 정답이 리콜 1건뿐이라 "같은 부품의 다른 좋은 선례"가 1위에 와도 오답으로 센다. 점수 상승이 과소 또는 과대로 나올 수 있다.
- ms-marco 계열 모델은 웹 검색 질문으로 학습되어 결함 신고 글에 맞는지 알 수 없다 — 시험으로만 확인한다.
- 화면 구조 영향 (미결, 7절): 화면의 고객사 선례 구역은 "합친 순위 상위 100 안에서 최대 5건"이다. 재순위화를 상위 50에만 하면 11~50위 고객사 선례의 순서는 바뀌고 51~100위는 그대로다. 채택하면 구역 규칙(DEC-042)을 같이 정해야 한다.

## 7. 사용자 확인이 필요한 것

1. **착수 여부와 시점** — 개발 마감 10/14, 현재 목표(화면 연결·시점 평가·배포) 밖의 새 작업이다. 발표 전에 할지, 발표 후 개선 항목으로 둘지.
2. **지연 예산 500ms**와 **용량 0.15GB** (3절 채택 기준 3·4항) — 제안값이다.
3. **후보 모델 3개와 N=50** — 더 넣거나 빼려면 시험 전에 정한다.
4. 채택 시 고객사 구역의 순위 규칙을 어떻게 할지.
