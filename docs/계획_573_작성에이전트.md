# 573 작성 에이전트 — 방향 수정 계획 (제안, 팀 결정 전)

> 작성: 이승노(검색 성능 개선 실험 담당, [DEC-060](../.agent/DECISIONS.md)) · 2026-10-15 · 상태: **제안 — 구현하지 않았다. 팀 결정 뒤에 착수한다.**
> 이 문서는 PR로 공유하는 계획이다. 코드·서버·데이터를 바꾸지 않는다. 아래 "결정이 필요한 것"(1절)이 정해지기 전에는 어떤 항목도 시작하지 않는다.

## 0. 방향 수정 한 줄

> 과거 선례 결함 기록을 살펴보고, 현재 결함이 **보고해야 하는 결함으로 이어질 만하다고 볼 근거가 모이면** Part 573(리콜 보고서) 초안을 써 주는 **자동차 부품 엔지니어용 문서 작성 에이전트**를 만든다. 지금의 검색(retrieval) 구조를 그 방향으로 고쳐 나가고, **목표 재현율은 90% 이상**이다. (사용자 지시, 2026-10-15)

현행 서비스(`docs/기획_결함선례.md`)는 "엔지니어가 보고 판별할 선례와 원인 원문을 보여 주는 검색 도구"다. 새 방향은 그 위에 **판별 신호**와 **573 초안 작성**을 얹는다. 두 가지가 현행 서비스 원칙과 직접 부딪히므로 1절이 이 문서의 중심이다.

## 1. 결정이 필요한 것 (착수 조건)

## 2. 에이전트 구조와 현재 retrieval에서 바뀌는 점

```text
[입력] 엔지니어: 결함 설명(영어) + 573 초안에 필요한 사실(차종·생산 기간·대수·날짜 등)
   │
   ▼
A. 증거 찾기 (현행 검색의 확장 — 2.1)
   BM25 + 뜻 검색 → RRF → (재정렬, 리랭커 계획서 확정 뒤) → "증거 묶음"(리콜 카드 + 573 섹션 + 비리콜 조사 기록)
   │
   ▼
B. 신호 (판정 아님 — D1 A안)
   증거 묶음의 사실 집계: 같은 부품·고장의 선례 N건 중 리콜로 이어진 M건, 연도 분포, 같은 공급사·같은 완성차 건수
   │
   ▼
C. 573 초안 조립 (3절 표: 칸마다 출처 종류 고정)
   엔지니어 입력 → 양식 칸 배치 / 선례 → 인용 박스 / 비어 있는 칸은 비워 둠
   │
   ▼
D. 검사 (AI 없음, 기존 원칙 확장)
   문장 출처 태그 · 인용 원문 글자 대조 · 판정어 금지 · 검색 결과 밖 리콜 번호 금지
   │
   ▼
[출력] 573 초안 + 선례 인용 박스 + 공란 항목 목록 + "엔지니어 결정 필요" 표시(서비스는 채우지 않음)
```

### 2.1 현행 retrieval에서 바꿀 것

| 현재 | 에이전트에 필요한 것 | 비용 |
|---|---|---|
| 질문 = 영어 한 줄 | 질문 + **구조화된 사실**(차종·부품·증상·대수·날짜). 검색 질의는 결함 설명 부분만 쓴다 | 입력 스키마(작음) |
| 색인 = 리콜 카드의 결함·결과·시정 | 573 보고서의 **결함 설명(Description of the Defect)·연대기·대상 범위·시정 섹션**이 필요 — 지금은 원인·공급사·생산 기간 칸만 판독해 보관한다 | **573 PDF 재판독(원본 약 2.4만 파일·5GB 재수집 3.5~4시간 또는 보관 사본), 파서 확장, DB·서빙 묶음 재적재** |
| 코퍼스 = 리콜만 | 리콜 + **리콜 없이 종결된 조사**(D4) | 데이터 확장, 정답(양성·음성) 정의 필요(4절) |
| 순위 = RRF(H@10 0.542) | 재정렬로 순서 개선. 상위 10 재정렬은 H@10이 바뀌지 않고 H@3·H@5만 오른다. 상위 20이면 H@10도 바뀜 | 리랭커 계획서(`계획_P3_리랭커시험.md`) 3절 확정 뒤. **지연이 병목**(아래) |
| 응답 = 카드 + 원인 + 확인 항목 | **증거 묶음 + 신호 + 573 초안 + 공란 목록**. 판정 칸 없음 | 응답 스키마(`server/api.py`), 화면 |
| 평가 = 749문항 대리 평가 | 4절의 R1·R2 | 사람 표시와 새 정답 정의 |

**지금까지 알아낸 것(탐색 시험, 이슈 #128 코멘트)**: ① 사전·약어·동의어 확장·어간 처리·색인 변형은 모두 H@10 ±0.01로 효과 없음. ② 재정렬은 모델에 따라 갈린다 — `jina-reranker-v1-turbo-en`만 H@3 +0.059(원래 질문)·+0.065(회사 이름 뺀 질문)였고 나머지 두 모델은 나빠짐. 그러나 2스레드 p95 858ms(이 PC)라 지연이 크다. ③ 점수가 낮은 큰 이유는 정답 정의가 좁고(조사 1건당 소수의 리콜) 100자 미만 질문이 정보가 없다는 것이다. **이 결과는 7절처럼 탐색 결과로만 쓴다.**

## 3. 573 초안: 칸마다 어디서 오는가

49 CFR 573.6(c)의 항목(2026-10-15에 Cornell LII 원문 확인). **원문과 다시 대조한 뒤 쓸 것**(법령 개정 가능).

| (c) 항목 | 내용 | 초안의 출처 | 비고 |
|---|---|---|---|
| (1) | 제조사 이름(브랜드·상표 소유자, 수입 시 대리인) | **엔지니어 입력** | |
| (2) | 대상 차량·장비 식별(제조 기간·차종·연식, 외주 부품은 부품·원산지·제작사) | **엔지니어 입력** + 선례 양식을 **참고 박스**로 | 초기 보고에 필요 |
| (3) | 대상 총수 | **엔지니어 입력** | |
| (4) | 결함 추정 비율 | **엔지니어 입력** | |
| (5) | 결함 설명(요약·상세·위치·안전 위험) | **엔지니어 입력**을 양식 칸에 배치 + 선례의 같은 칸 표현을 **인용 박스**로 | 초기 보고에 필요. 서비스가 새로 쓰지 않는다 |
| (6) | 결함 판단 근거의 **연대기**(보증 청구·현장 보고, 받은 날짜) | **엔지니어 입력**(날짜·사건) + 선례 연대기 **양식 인용** | |
| (7) | 비준수 시험 결과 | 해당 시에만, 엔지니어 입력 | |
| (8) | 시정 계획(시정 내용·통지·시정 시작·완료 시점, 환불 계획) | **엔지니어 입력** + 선례의 시정 원문 **인용 박스** | |
| (9) | 타이어 전용 계획 | 범위 밖 | |
| (10) | 통지문 사본 | **엔지니어 첨부** | |
| (11) | 제조사 캠페인 번호 | **엔지니어 입력** | |

- 보고 기한: 결함이 있다고 **판단된 뒤** 5영업일 안(573.6(b)). 최초 보고에는 (c)(1)·(2)·(5)가 들어가고 나머지는 확인된 뒤 5영업일 안에 낸다 — 그래서 **1단계 초안은 (1)(2)(5)만** 채우는 것으로 시작할 수 있다.
- "판단"은 엔지니어·회사의 일이다. 초안에는 **"안전 관련 결함인가"를 서비스가 채우는 칸을 두지 않는다**(D1).
- 선례 인용은 선례의 573 보고서에서 가져오므로, 현행 파서가 보관하지 않은 섹션(2.1)이 필요하다.

## 4. "재현율 90% 이상" — 정의와 평가 설계 (D5)

> **2026-10-15 갱신**: 현행 749문항 평가셋은 이 방향의 기준으로 쓸 수 없다고 판단해 평가 자체를 새로 설계했다 — 상세는 [`계획_평가셋_재설계.md`](계획_평가셋_재설계.md). 아래 4.1·4.2는 그 문서의 R1·R2·과도학습 방지 장치(S1~S10)로 대체·보강된다. **특히 R2는 `FLAT_INV` 요약문에 결과가 새어 있어(키워드 `recall` 한 줄이 민감도 0.793·특이도 0.882) 요약문을 그대로 쓰면 안 되고, 조사 개시 시점 텍스트와 키워드 기준선 비교가 필요하다.**

### 4.1 후보 정의 두 가지 (둘 다 쓰는 것을 제안)

| | 무엇의 재현율인가 | 정답(정의) | 짝 지표 | 현재 값 |
|---|---|---|---|---|
| **R1 선례 증거 재현율** | 현재 결함과 **같은 부품·비슷한 고장**인 선례가 상위 k(=10)에 **하나 이상** 있는 질문의 비율 | **사람이 표시**(풀링 평가: 기준선·새 방식의 상위 10을 섞어 출처를 가리고 "같은 부품·비슷한 고장인가"를 표시). AI가 표시하지 않는다(AGENTS.md 5-2) | 상위 10의 정밀도(쓸 만한 선례 비율) | 749문항 정답 정의로는 **0.542**(상한 H@100 0.730). 부품 대분류 수준 참고값은 약 85%(정답 맞힌 406 + 놓친 343×0.671 ≈ 636/749)이나 분류가 42종으로 넓어(무작위 10장도 41%) 90% 기준으로 쓰기엔 약하다 |
| **R2 보고 대상 신호 재현율(민감도)** | 실제로 리콜(=보고)로 이어진 사례를 에이전트가 "근거 있음" 신호로 낸 비율 | **정부 기록**: 양성 = 조사 개시 뒤 리콜로 이어진 조사, 음성 = 리콜 없이 종결된 조사(`FLAT_INV`). 평가 정답을 지어내지 않는다 | **특이도 또는 정밀도** — 재현율만 보면 전부 양성이라고 답해도 100% | **미측정**. 음성 데이터 수는 M1 첫 단계에서 센다 |

- **90%의 현실성**: 같은 749문항 정답 정의로는 후보 상한(H@100 0.730, 정답이 200위 밖인 질문 24%)이 **0.90보다 낮아** 어떤 재정렬로도 도달할 수 없다(탐색 시험). 그래서 지표를 바꿔야 의미가 있다 — 이는 목표를 쉽게 만드는 일이 아니라, 에이전트가 하는 일(선례 증거 제공·신호)을 재는 지표로 바꾸는 일이다.
- R2는 라벨 잡음이 있다: "리콜 없이 종결 = 안전 결함 아님"이 아니다(제조사가 자발적으로 조치했거나 조사가 다른 이유로 끝났을 수 있음). 정답이 아니라 **정부 기록 기반의 대리 라벨**이라고 밝힌다.
- **정보 없는 입력**(100자 미만, 이 시험지의 15%)은 재현율이 나올 수 없다. 이 입력은 별도로 보고하고, 화면에서 정보를 더 받도록 안내하는 것이 검색 개선보다 효과가 클 수 있다.

### 4.2 평가 설계 규칙 (결과를 보기 전에 고정)

1. **시간 분할**: 조사 개시일 기준으로 개발(≤2015)·검증(2016~2019)·시험(2020~) 구간을 나눈다(경계는 양성·음성 수를 센 뒤, 결과를 보기 전에 확정). 신호의 **작동점(임곗값)은 개발·검증 구간에서만** 고정하고 시험 구간은 한 번만 잰다. 시험 구간 결과를 보고 임곗값·규칙을 바꾸지 않는다(AGENTS.md 5-1·5-2).
2. **90% 판정**: R2 민감도 ≥ 0.90을 **고정한 특이도(또는 정밀도) 이상에서** 달성할 때만 "달성"으로 쓴다. 특이도 하한은 D5에서 정한다.
3. **누수 점검**: 신호 입력에서 조사 요약·조사 종결 정보(결과를 알려 주는 칸)를 뺀다. 질문은 조사 **개시** 시점의 요약만 쓴다(`기획_결함선례.md` 6절 시점 평가와 같은 이유).
4. **573 초안 품질**(별도): 자동 검사(문장 출처 태그 100%, 인용 원문 일치 100%, 판정어 0건, 검색 범위 밖 리콜 번호 0건)와 사람 검토(칸 충족도, 엔지니어가 그대로 쓸 만한지)를 **재현율과 합치지 않고** 따로 보고한다.
5. 같은 입력 사본이 아니면 "재평가"로 부르고, 기각한 실험도 기록한다(5-3·5-4). 대리 평가(749)·시점 평가·R1·R2 점수는 **합산하지 않는다**(5-2).

## 7. 알려 둘 것 (이 계획의 근거와 한계)

- **탐색 시험의 지위**: 2절의 "지금까지 알아낸 것"은 같은 날(2026-10-15) 이슈 #128 제안에 따라 돌린 **탐색 시험**이다. 그 시험은 리랭커 계획서 3절(사전 고정 규칙)과 DEC-060의 "확정 커밋 전에는 749문항을 실행하지 않는다"가 확정되기 **전에** 11시대에 실행됐고, 같은 날 오후에 시작한 추가 라운드는 DEC-060을 확인하자마자 중단했다(결과 파일 없음). 사전의 sha256은 점수 전에 고정했지만 채택 기준은 계획서 3절과 다르다. 그래서 **채택 근거로 쓰지 않고** 계획서 3절 확정 뒤 규칙대로 다시 잰다. 시험 코드와 보고서는 이 PR에 포함하지 않는다(별도 PR).
- 이 문서의 수치는 `docs/기획_결함선례.md`, 이슈 #128 코멘트, 49 CFR 573.6 원문 조회에서 가져온 것이다. R1의 "약 85%"는 탐색 진단에서 계산한 값(정답 맞힌 406 + 놓친 343×0.671)이다.
