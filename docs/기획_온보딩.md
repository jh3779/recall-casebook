## 1. 문제 정의 (상황별로 디테일하게)

> **대상 · 결핍 · 구체적 어려움** 세 요소가 다 있어야 한다.
> "불편하다"로 끝나면 안 된다. 듣는 사람이 그 사람을 머릿속에 그릴 수 있어야 한다.

### 배경: 문서를 잘 쓰는 회사조차 온보딩 정보가 흩어져 있다

GitLab은 회사 운영 전부를 공개 핸드북으로 관리하는 회사다(마크다운 4,612개, 약 612만 단어). 그런데도 신규 입사자 온보딩 정보는 다음처럼 흩어져 있다.

| 관찰 | 수치 | 근거 |
|---|---|---|
| "onboarding"으로 찾으면 절반 가까이가 입사와 무관 | 129건 중 61건(47%)이 고객 온보딩·시스템 연결·당직 합류 등 | 경로·제목·소제목 검색 후 건별 분류 |
| 팀 온보딩 페이지 상당수가 링크 한 줄 | 엔지니어링 팀 17개 중 9개가 "이슈 템플릿을 열어라"뿐 | 예: `engineering/infrastructure-platforms/tenant-scale/gitaly/_index.md:368-371` |
| 실제 체크리스트는 핸드북 밖 | 전사 온보딩 이슈 템플릿 저장소가 비로그인 상태에서 API 404 / 파일 403 | `people-group/general-onboarding/_index.md`가 "public repository"라고 소개하지만 실제로는 접근 불가 |
| 사내 전용 링크 | 페이지 445개(11%)에 `internal.gitlab.com` 링크 836개 | 스냅샷 전수 집계 |
| 같은 사실이 페이지마다 다름 | 온보딩 이슈 생성 시점이 "4일 전" / "4 영업일 전" / "4~10 영업일 전" | `general-onboarding/_index.md:14, 73`, `product/product-management/product-manager-role.md:130` |

| 항목 | 내용 |
|---|---|
| 1차 대상 (구체적으로) | **아직 없음** — 후보: 신입·부서 이동자를 받는 회사의 온보딩 담당(인사 담당자, 팀 리드). 실제 인터뷰나 조사 기록은 없다. |
| 그 사람이 처한 상황 | 아직 없음 (팀 회의 아이디어 단계: "입사 시점·부서 이동 시점에 활용", "팀장 보고 전 사수가 현재 단계를 빠르게 파악") |
| 없어서 못 하는 것 | 우리 회사 자료를 넣으면 **빠진 칸을 찾아 묻고, 근거 달린 온보딩 문서 초안을 만들어 주는 도구** |
| 그래서 무엇이 어렵나 | 무엇이 빠졌는지 모른다(예: 버디 제도, 완료 기준, 권한 요청 절차). GitLab 사례처럼 정보가 여러 문서·외부 도구로 흩어진다. |
| 현재는 어떻게 때우고 있나 | 아직 없음 — 조사 필요 |

**문제 정의 한 문장** (초안):
> 신입·부서 이동자를 받는 회사의 온보딩 담당자가 / 흩어진 사내 자료로 온보딩 문서를 만들 때 / 무엇이 빠졌는지 짚어 주고 근거를 붙여 정리해 줄 도구가 없어서 / 빈칸이 많은 문서로 신입을 받게 된다.

### 해결 범위 — 어디까지 풀고 어디부터 안 푸나

> ❗ 자주 빠뜨리는 칸. "못 한 것"과 "안 하기로 한 것"을 구분해서 적어야 신뢰를 얻는다.

| 단계 | 해결 여부 | 비고 |
|---|---|---|
| GitLab 온보딩 문서에서 참조 목차(칸 목록) 만들기 | 🟡 시범만 | 68건에서 11개 칸의 출현 비율을 키워드로 측정함 (6번 참고) |
| 다른 회사 문서에서 빈칸 찾기 | 🟡 시범만 | 키워드 규칙으로 Basecamp 문서 11칸 중 8칸 일치 (평가셋 아님, 6번 참고) |
| 빈칸에 대한 질문 생성 | ⬜ 아직 없음 | — |
| 근거가 붙은 초안 작성 | ⬜ 아직 없음 | — |
| 신입 온보딩 외 사내 문서 전반 | ❌ 미해결(의도적) | 발표까지는 "신입 온보딩 문서" 한 종류로 한정 |
| 회사 사실을 모델에 학습(파인튜닝) | ❌ 미해결(의도적) | 회사 지식은 RAG로 다룸 (3번) |
| GitLab의 **내용**을 다른 회사에 복사 | ❌ 안 함(의도적) | 구조(칸 목록)만 참조. "장비 지원금 1,500달러" 같은 GitLab 사실은 다른 회사에선 틀린 답 |
| 목차 편집 화면, 여러 부서 동시 지원, 퀴즈, 티켓 자동 분담 | ❌ 이번 범위 밖 | 발표에서 "다음 단계"로만 소개 |

**실패하는 경우** (지금까지 확인한 것):
- 회사마다 같은 칸을 다른 말로 부르면 놓친다 — Basecamp는 이슈 템플릿 대신 "환영 프로젝트의 할 일 목록", PostHog는 매니저 대신 "team lead".
- 팀 문서는 계정·권한·입사 전 칸을 전사 문서에 맡긴다 — 목차가 한 층이면 모든 팀 문서에 "권한 요청 없음"이라는 잘못된 경고가 뜬다.
- 내용이 핸드북 밖(비공개 템플릿, Google Docs, 슬라이드 임베드)에 있으면 근거를 붙일 수 없다.

## 3. 이 기술이 왜 들어가야 하는가

> 기술이 목적이 되면 안 된다. **"그 기술 없이는 안 됐던 것"**을 먼저 쓴다.

| | 그 기술 없이 | 그 기술로 |
|---|---|---|
| **RAG** (2026-10-01 팀 결정) | 회사 사실을 파인튜닝하면 출처 추적·삭제·권한 적용이 어렵고, 정책이 바뀔 때마다 재학습해야 한다. 비지도 파인튜닝은 새 지식 주입에서 RAG보다 못했고([Ovadia et al., EMNLP 2024](https://aclanthology.org/2024.emnlp-main.15/)), 새 지식 학습은 환각 증가와 연결됐다([Gekhman et al., EMNLP 2024](https://aclanthology.org/2024.emnlp-main.444/)). | 문장마다 회사 문서 출처를 달고, 문서가 바뀌면 다시 넣기만 한다 |
| **참조 목차 (GitLab 구조)** | 무엇이 빠졌는지 알 기준이 없다 | GitLab 온보딩 68건에서 반복되는 칸을 기준으로 빈칸을 찾는다 |
| **LLM 빈칸 판정** | 키워드 규칙은 말이 다르면 놓친다 (Basecamp 시범 11칸 중 3칸 오답) | 의미로 판정 — **효과는 아직 측정 안 함** |

**정직하게 남길 지점**:
- 온보딩 문서 68건은 약 4.6만 단어(약 6.2만 토큰)로 LLM 컨텍스트에 들어간다. 이 범위에서 RAG를 쓰는 이유는 분량이 아니라 **출처 추적과 갱신**이다.
- 파인튜닝은 버리지 않았다 — 승인된 문서 이력이 쌓이면 "묻는 습관·문체" 같은 행동 학습에 쓸 수 있다. 지금은 학습 데이터가 없다.

## 5. 아키텍처 · 워크플로우 설계

```text
[참조]    GitLab 온보딩 문서 68건 ──► 참조 목차 (2층: 전사 공통 칸 / 팀 칸)   ← 사람이 정리·확정
             │
[입력]    대상 회사의 온보딩 자료 (문서·메일 양식·규칙 등)
             ▼
[분류]    자료 종류 나누기
             ▼
[빈칸]    참조 목차의 칸마다 "있음 / 없음 / 애매" 판정 + 근거 위치
             ▼
[질문]    없음·애매 칸에 대해 담당자에게 질문
             ▼
[초안]    답변 + 기존 자료로 칸별 초안 작성 (문장마다 출처)
             ▼
[검증]    출처 밖 문장 검사 → 근거 없으면 쓰지 않고 다시 질문
             ▼
[승인]    담당자가 칸별로 승인
```

**핵심 흐름**: 회사 자료 → 참조 목차와 대조 → 빈칸 질문 → 근거 달린 초안 → 사람 승인

**설계 제약** (어겨서는 안 되는 것):
1. **근거 없는 문장은 쓰지 않는다** — 초안의 모든 문장에 대상 회사 자료 또는 담당자 답변 출처를 단다. 없으면 질문한다.
2. **GitLab은 구조만 빌린다** — GitLab의 사실(금액·도구명·일정)을 초안에 넣지 않는다.
3. **칸 이름은 일반 용어로** — "이슈 템플릿"이 아니라 "할 일 체크리스트", "매니저"가 아니라 "직속 상사·팀 리드".
4. **평가 정답은 사람이 표시한다** — AI가 만든 정답으로 평가하지 않는다 (AGENTS.md 5-2).

| 키워드 규칙 (Basecamp 1건) | — | 11칸 중 8칸 일치 | 단어 패턴 매칭. **정답은 AI가 원문을 읽고 표시한 시범값이라 공식 평가셋이 아님** |

틀린 3칸은 모두 "말이 달라서" 놓침 — "before you start" 미인식, 이슈 템플릿 대신 "할 일 목록", 실습을 "실제 프로젝트 시작"으로 표현.

### 앞으로의 개선 (측정 가설까지)

| 버전 | 바꿀 것 | 기대 효과 | 측정 방법 |
|---|---|---|---|
| v0 (기준선) | 키워드 규칙 | 칸별 일치율 | 팀원이 표시한 정답표 (문서 3개 이상) |
| v1 | 칸 이름을 일반 용어로 + LLM 의미 판정 | 말이 달라 놓치던 칸 회수 | 같은 정답표로 v0과 비교 (차이 0.03 미만은 "같다", AGENTS.md 5-3) |
| v2 | 2층 목차 (전사 / 팀) | 팀 문서의 잘못된 "권한 요청 없음" 경고 감소 | 팀 문서에서의 오경고 수 |

## 7. 어려움과 해결

> ❗ 사례를 나열하지 말고 **하나의 서사로 엮는다**. "우리는 이런 식으로 일한다"가 드러나야 한다.
> 작업 중에 그때그때 적어 두지 않으면 나중에 절대 못 쓴다.

| 언제 | 막힌 지점 | 어떻게 접근했나 | 결과 | 남은 것 |
|---|---|---|---|---|
| 온보딩 문서 수집 | "onboarding" 검색 결과에 고객 온보딩·시스템 연결이 섞임 | 129건을 소제목·본문으로 직접 열어 5개 유형으로 분류 | 입사·팀 온보딩 68건 확정 (11개 부서) | 소제목에 단어가 없는 문서는 못 잡음 |
| 참조 목차 시범 | 팀 문서에 계정·권한 칸이 거의 없음 (10~19%) | 원인 확인 — 팀 문서는 이 칸을 전사 문서에 맡김 | 목차를 2층(전사 / 팀)으로 나누기로 함 | 2층 목차 정리 (사람 작업) |
| 다른 회사 문서 시험 | 같은 칸을 다른 말로 불러 놓침 | 원문을 줄 단위로 대조 | 칸 이름을 일반 용어로 바꾸기로 함 | LLM 판정으로 개선되는지 측정 |
| 근거 확인 | 핸드북이 "공개"라던 템플릿 저장소가 실제로는 비공개 | 비로그인 API·파일 접근으로 직접 확인 | 체크리스트 본문은 범위에서 제외 | — |

**꿰는 한 문장** (초안): 검색 결과도, 문서의 자기소개도 그대로 믿지 않고 — 직접 열어 보고, 숫자로 확인하고, 다른 회사 문서로 시험한다.
