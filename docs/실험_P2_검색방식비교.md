# P2 검색 방식 비교 보고서

> 작성: 우지훈(B 파트) · 2026-10-08 · PR #49 (`research/p2-retrieval-comparison`)
> 목적: P2 개발(10/12~14) 전에 **검색 방식·저장 위치·원인 표시(LLM)** 를 같은 시험지 숫자로 비교해 정한다 (AGENTS.md 5-1).
> 모든 점수는 **대리 평가**(조사 요약 → 그 조사로 나온 리콜, 749문항)다. "과거 선례 찾기" 성능은 시점 평가로 따로 잰다 (`기획_결함선례.md` 6절).

## 2. 시험 조건

- 시험지: `eval.jsonl` 749문항, 정답 = 그 조사의 `CAMPNO`(정부 기록).
- 데이터 판본: main(#48 반영)의 회사명 대응표로 만든 카드 — `recalls_sha256 3f996182…`, `eval_sha256 fe5433db…`, `causes_sha256 d215ff58…`, `maker_aliases_sha256 ee528c18…`(기준 파일 `baseline_2026-10-06_maker-aliases.json`과 일치, `bm25_baseline --baseline`으로 0.510 재현). 각 결과 JSON의 `data` 칸에 이 해시가 기록되고, 파일이 `build.json`과 다르면 스크립트가 멈춘다.
  - 처음 측정은 #48 이전 카드(`recalls_sha256 a4e9d59d…`)로 했고, 리뷰 뒤 위 판본으로 전부 다시 쟀다. 색인 대상(결함·결과·시정)은 회사명 대응표와 무관해 모든 점수가 같았다.
- 지표: **Hit@k(주) = 연결 리콜 중 하나라도 상위 k개 안**, `first@10` = 첫 연결 리콜만(참고). 2014-08-20 이후 접수 리콜이 정답인 94문항은 따로 보고(573 원인 칸이 있는 시기, n이 작아 1문항 = 약 0.011).
- 색인 대상: 리콜 카드의 결함·결과·시정 텍스트. **조사 요약은 시험 질문의 출처라 넣지 않는다**(누수 방지).
- 시험 전에 정한 것: 색인 대상, RRF 상수 k=60(관례값), 지표, 0.03 기준 폭. **v0b의 브랜드 목록은 v0a 점수를 본 뒤 만든 진단용 변형**이다(3-1) — 정답 필드(`gold_campnos`)는 규칙을 만드는 데 쓰지 않았고 점수 계산에만 쓴다(AGENTS.md 5-2).
- 기준 폭 0.03 미만의 차이는 "같다"로 본다(`기획_결함선례.md` 6절). H@1·3·5·10 각각에 적용한다.
- 환경: Apple M5 Max(메모리 38GB), Python 3.12, 로컬 임베딩은 `fastembed`(ONNX, CPU).

## 3. 검색 방식 결과

### 3-A. 원래 질문 (회사 이름 포함)

| 버전 | 방식 | H@1 | H@3 | H@5 | **H@10** | first@10 | 94문항 H@10 |
|---|---|---|---|---|---|---|---|
| v0 | BM25 (기준선) | 0.307 | 0.393 | 0.455 | **0.510** | 0.503 | 0.734 |
| v4 | v0 + 573 원인 칸 색인 | 0.311 | 0.402 | 0.461 | 0.505 | 0.497 | 0.713 |
| v1 | 뜻 검색 단독 (bge-small) | 0.258 | 0.367 | 0.407 | 0.463 | 0.451 | 0.723 |
| v1 | 뜻 검색 단독 (bge-base) | 0.282 | 0.395 | 0.455 | 0.501 | 0.486 | 0.734 |
| **v2** | **BM25 + bge-small, RRF** | 0.311 | 0.411 | 0.462 | **0.542** | 0.525 | 0.755 |
| v2′ | BM25 + bge-base, RRF | 0.331 | 0.445 | 0.499 | 0.553 | 0.542 | 0.777 |

- v2 대 v0: H@10 +0.032(기준 폭 초과), H@1 +0.004·H@3 +0.018·H@5 +0.007(모두 기준 폭 안). **이득은 상위 10 안쪽에서 정답을 더 건져 올리는 것**이고, 1위 정확도는 같다.
- v2′ 대 v2: H@10 +0.011(같음), **H@3 +0.034·H@5 +0.037(기준 폭 초과)**, H@1 +0.020(같음).

### 3-B. 회사 이름을 뺀 질문 (실사용에 가까움)

사용자는 회사가 아니라 부품으로 묻는다(기획 1절). 질문에서 완성차·브랜드 이름(고정 목록 `BRANDS`)만 지우고 같은 문장을 BM25와 뜻 검색에 모두 넣었다.

| 버전 | 방식 | H@1 | H@3 | H@5 | **H@10** | first@10 | 94문항 H@10 |
|---|---|---|---|---|---|---|---|
| v0b | BM25 | 0.296 | 0.374 | 0.431 | **0.483** | 0.475 | 0.628 |
| v1b | 뜻 검색 단독 (bge-small) | 0.226 | 0.320 | 0.364 | 0.419 | 0.413 | 0.596 |
| v1b | 뜻 검색 단독 (bge-base) | 0.250 | 0.355 | 0.402 | 0.447 | 0.435 | 0.564 |
| **v2b** | **BM25 + bge-small, RRF** | 0.292 | 0.393 | 0.442 | **0.531** | 0.517 | 0.691 |
| v2b′ | BM25 + bge-base, RRF | 0.308 | 0.413 | 0.467 | 0.530 | 0.515 | 0.702 |

- 회사 이름을 빼도 RRF 이득은 남고 오히려 커진다(H@10 +0.032 → **+0.048**). RRF의 이득이 회사 이름 덕분이 아니다.
- 이 조건에서 bge-base와 bge-small의 차이는 H@1 +0.016·H@3 +0.020·H@5 +0.025·H@10 −0.001로 **모두 기준 폭 안**이다.

### 3-0. 임베딩 모델 선택 (bge-small vs bge-base)

| | bge-small | bge-base |
|---|---|---|
| 차원 | 384 | 768 |
| 전체 임베딩 시간(30,350장, 이 맥 CPU) | 525초(약 9분) | 1,572초(약 26분) |
| 질문 임베딩·검색 시간(질문당) | 10ms | 30ms |
| 저장 용량(임베딩) | 약 47MB | 약 93MB |
| RRF, 원래 질문 H@3 / H@5 / H@10 | 0.411 / 0.462 / 0.542 | 0.445 / 0.499 / 0.553 |
| RRF, 회사 이름 뺀 질문 H@3 / H@5 / H@10 | 0.393 / 0.442 / 0.531 | 0.413 / 0.467 / 0.530 |

- **판단**: 원래 질문에서는 base가 H@3·H@5에서 기준 폭을 넘게 높다. 그러나 실사용에 가까운 회사 이름 뺀 질문에서는 모든 k에서 같다. 비용(임베딩 3배, 질문당 3배, 용량 2배)을 고려해 **bge-small을 권장**한다.
- 이것은 비용과 맞바꾼 선택이다. 화면이 상위 3~5개만 보여 준다면 base가 원래 질문 기준으로 약 0.035 낫다는 점을 사용자가 판단해 정한다.
- 기각 기록(AGENTS.md 5-4): bge-base는 원래 질문의 H@3·H@5에서 기준 폭을 넘게 높았지만, 회사 이름 뺀 질문에서는 차이가 사라지고 비용이 커서 권장하지 않았다. 시점 평가에서 차이가 커지면 다시 본다.

### 3-1. 회사 이름 의존도

- 질문(조사 요약)에는 "GENERAL MOTORS STATED…"처럼 회사 이름이 들어 있고, 카드의 시정 문구에도 회사 이름이 나온다. 그래서 대리 평가 점수에는 **회사 이름이 맞아서 오른 몫**이 있다.
- BM25에서 회사 이름을 빼면 0.510 → 0.483(−0.027), 2014 이후 94문항에서는 0.734 → 0.628(**−0.106**, n=94라 오차 큼). 원래 질문 점수는 실사용보다 높게 나온다.
- **v0b의 경위**: 처음 정한 v0a(대응표의 모든 회사 이름 단어 제거)는 `safety`·`new`·`trucks`·`highway` 같은 일반어까지 지웠다(질문 628개에서 2,174단어, H@10 0.418). 회사 이름 효과만 재지 못해 **기각**하고, 질문 단어만 보고(정답은 보지 않고) 완성차·브랜드 고정 목록으로 지우는 v0b를 진단용으로 추가했다. v0b는 해석용이고 검색 방식 선택(RRF)에는 영향을 주지 않는다.

### 3-2. 573 원인 칸 색인 (v4) — 보류

- 원인 칸이 있는 카드는 8,179장(27%)이다. 정답이 2014-08-20 이후인 문항은 94개(12.6%)뿐이고, 나머지 655문항은 정답 카드에 원인 칸이 없어 색인해도 정답 점수가 바뀔 수 없다.
- 94문항에서도 H@10 0.734 → 0.713(2문항 차이)으로 내려갔지만 H@3 0.585 → 0.628은 올랐다 — 이 시험지로는 **효과를 판단할 수 없다**.
- 그래서 "효과가 없어서"가 아니라 **"측정할 수 없어서" 보류**한다(AGENTS.md 5-4). 시점 평가에서 다시 본다. 원인 칸은 우선 화면의 원인 표시(5절) 입력으로 쓴다.

## 4. 저장 위치 결과

같은 749문항, bge-small 임베딩. Postgres는 로컬 컨테이너(Postgres 17 + pgvector, build `c6872ae8…` = 위 판본)에서 쟀다 — 운영 Supabase에는 `select 1`만 보냈다. 지연은 749회 측정의 p50·p95(최근접 순위).

| 방식 | H@10 | 질문당 시간 p50 / p95 | 비고 |
|---|---|---|---|
| Python 메모리 BM25 | 0.510 | 약 39ms(평균) | 표준 라이브러리 구현 |
| Python 메모리 뜻 검색(numpy 내적) | 0.463 | **1.5 / 1.9ms** | 정확한 계산 |
| Postgres 전문 검색 — `to_tsquery('english', 질문 단어 OR)` + `ts_rank_cd` | **0.163** | 136 / 495ms | **이 설정에서는** BM25보다 크게 낮다(점수 방식이 다름, DEC-034 미결 ②) |
| pgvector HNSW (로컬, 기본 `ef_search` 40) | 0.441 | 0.5 / 0.8ms | 근사 검색이라 정확한 계산(0.463)보다 낮다 |
| Supabase 네트워크 왕복 (`select 1`, 100회) | — | **197 / 206ms** | 노트북(한국)에서 측정 — API 서버를 Supabase 가까이 두면 달라진다 |

- 색인 크기: FTS 31MB, 384차원 벡터 표 107MB(HNSW 색인 포함, build 1개).
- **결론**: 검색은 API 서버가 시작할 때 카드(약 29MB)와 임베딩(약 47MB)을 메모리에 읽어 두고 그 안에서 한다. 주 근거는 품질(Postgres에는 BM25가 없고, 시험한 FTS 설정은 0.163)이고, 질문마다 DB를 부르는 지연은 보조 근거다. Supabase는 build 단위 보관과 "답변 → 리콜 번호 → build → 원본" 추적(서비스 원칙 4)에 쓴다.
- 임베딩 보관 위치(Supabase 벡터 칸 `recall_embeddings` / 파일 / 드라이브)는 아직 정하지 않았다(DEC-034 미결 ①). 이 권장안에서는 서버가 시작할 때 카드로 만들거나 파일로 읽는다.
- pgvector는 나중에 카드 수가 크게 늘거나 서버를 여러 대 두어야 할 때 다시 본다.

## 5. 원인 표시(엔진 2) — 30건 시험

- 시험(`engine2_trial.py`): 질문 순서대로 BM25 1위 리콜 중 573 원인 칸(`cause_text`)이 있는 것 30건(무작위 표본 아님, 정답 여부와 무관). LLM에게는 "원인을 말하는 문장을 한 글자도 바꾸지 않고 고르기, 원인을 말하지 않으면 빈 목록"만 시켰다(판정·요약 금지).
- 검사: 돌려받은 문자열이 원인 칸 원문에 **공백까지 포함해 그대로** 들어 있는지 정규화 없이 대조하고, 통과한 것은 원문에서 찾은 구간(시작·끝 위치)을 남긴다. 5단어 미만 조각은 따로 센다.
- 모델·가격(OpenAI 공식 문서 `developers.openai.com/api/docs/models/gpt-5.4-mini`, 2026-10-08 확인, 100만 토큰당): `gpt-5.4-mini` 입력 0.75달러·출력 4.50달러, `gpt-5.4-nano` 입력 0.20달러.

| | gpt-5.4-mini | gpt-5.4-nano |
|---|---|---|
| 돌려준 문자열이 원문과 정확히 일치 | **29/29건 (100%)** | **28/28건 (100%)** |
| 5단어 미만 조각 | 0 | 0 |
| 원인 칸 **전체**를 그대로 돌려줌 | 24건 | 25건 |
| 일부 문장만 고름 | 5건 | 3건 |
| 빈 목록("원인을 말하지 않음") | 1건 | 2건 |
| 평균 응답 시간 | 1.61초 | 1.36초 |
| 토큰(30건 합계) | 입력 8,910 · 출력 1,731 | 입력 8,910 · 출력 1,716 |
| 비용(30건) | 약 0.015달러 | 0.01달러 미만 |

**알게 된 것**
1. **글자를 바꾸는 문제는 없었다**(정확 일치 기준). 그래도 서비스에서는 LLM이 돌려준 문자열이 아니라 **원문에서 찾은 구간**을 보여 주고, 원문 문장 경계에서 시작·끝나는지도 검사한다.
2. **LLM이 할 일이 거의 없다.** 573 "Description of the Cause"는 처음부터 원인만 쓰는 칸이라 30건 중 24~25건에서 칸 전체를 그대로 돌려줬다. 일부만 고른 경우 기준이 모델마다 달랐다(7건에서 결과가 다름 — 예: "Fewer than 1% of the subject vehicles…"를 nano는 넣고 mini는 뺌).
3. **쓸모 있는 곳은 "원인을 아직 모른다"는 문장 표시다.** `23V319000` "…has not provided the reason for failure currently and continues to investigate." → 두 모델 모두 빈 목록(맞음). `24E058000` "No root cause has been identified…" → nano는 빈 목록, mini는 원인 문장으로 돌려줌(틀림). 간단한 규칙(`continues to investigate` 등)은 첫 예는 잡지만 둘째 예는 못 잡는다(`no root cause` 형태가 따로 필요) — **규칙의 정확도는 아직 재지 않았다.**

**권장**
- 기본: **원인 칸 원문을 LLM 없이 그대로 보여 준다**(말한 주체 = 제조사 표시). 0초, 비용 없음, 글자가 바뀔 위험이 원천적으로 없다.
- "원인 미확인" 표시 방법(규칙 / LLM nano / 둘 다)은 표본으로 정확도를 잰 뒤 정한다(후속).
- 30건 결과가 "원인을 맞게 골랐는가"는 사람이 확인한다(D 파트 몫, 지금은 우지훈). 이 보고서의 숫자는 "글자 일치"만 잰 것이다.

- 아직 정하지 않은 것: 검색 방식·모델 확정(DEC), 부품 트리로 범위 좁히기(v3, 할 일 22의 연결 규칙이 먼저), 임베딩 보관 위치, API 서버를 어디서 돌릴지, 호출 상한.

## 7. 한계와 남은 측정

- **대리 평가**다. 정답 리콜 대부분이 조사 뒤에 접수돼 "과거 선례를 찾는 능력"은 재지 못한다. 시점 평가는 질문 판본 확보(할 일 18, PR #50·#52) 뒤에 한다.
- 원래 질문에는 회사 이름이 섞여 있어 점수가 실사용보다 높게 나온다(3-1). 그래서 회사 이름 뺀 질문(3-B)도 함께 보고했다.
- 2014 이후 94문항은 n이 작아 1문항이 약 0.011이다.
- 엔진 2 표본은 질문 순서 앞에서부터 30건이고 무작위가 아니다.
- 전체 임베딩은 표본 속도(카드 1,000장)로 예상한 것보다 오래 걸렸다(bge-small 0.7분 → 실제 8.8분, bge-base 2.2분 → 실제 26분). 표본의 카드가 짧았기 때문이다 — 다음에는 무작위 표본으로 잰다.
- pgvector는 HNSW 기본값(`ef_search` 40)으로만 쟀다.
- Supabase 왕복은 노트북(한국)에서 잰 값이다.
