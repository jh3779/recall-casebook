> 목적: P2 개발(10/12~14) 전에 **검색 방식·저장 위치·원인 옮기기(LLM)** 를 같은 시험지 숫자로 비교해 정한다 (AGENTS.md 5-1).

## 2. 시험 조건

- 시험지: `eval.jsonl` 749문항, 정답 = 그 조사의 `CAMPNO`(정부 기록). 기준 파일 `baseline_2026-10-06_maker-aliases.json`의 새 카드(build `f5cb2f944f36125d`).
- 지표: **Hit@k(주) = 연결 리콜 중 하나라도 상위 k개 안**, `first@10` = 첫 연결 리콜만(참고). 2014-08-20 이후 접수 리콜이 정답인 94문항은 따로 보고(573 원인 칸이 있는 시기).
- 색인 대상: 리콜 카드의 결함·결과·시정 텍스트. **조사 요약은 시험 질문의 출처라 넣지 않는다**(누수 방지).
- 규칙은 시험 전에 정했고, 정답을 보고 바꾸지 않았다(AGENTS.md 5-2). RRF 상수 k=60은 관례값이다.
- 기준 폭 0.03 미만의 차이는 "같다"로 본다(`기획_결함선례.md` 6절).
- 환경: Apple M5 Max(메모리 38GB), Python 3.12, 로컬 임베딩은 `fastembed`(ONNX, CPU).

## 3. 검색 방식 결과

| 버전 | 방식 | H@1 | H@3 | H@5 | **H@10** | first@10 | 2014 이후 94문항 H@10 | 판단 |
|---|---|---|---|---|---|---|---|---|
| v0 | BM25 (기준선) | 0.307 | 0.393 | 0.455 | **0.510** | 0.503 | 0.734 | 기준선 재현 ✅ |
| v0b | v0 + 질문에서 완성차·브랜드 이름 빼기 | 0.296 | 0.374 | 0.431 | 0.483 | 0.475 | 0.628 | 아래 3-1 |

| v1·v2 | bge-base (768차원) | | | | | | | 측정 중 (아래 7절에 추가) |

### 3-1. 회사 이름 의존도 (v0b)

- 질문(조사 요약)에는 "GENERAL MOTORS STATED…"처럼 회사 이름이 들어 있고, 카드의 시정 문구에도 회사 이름이 나온다. 그래서 대리 평가 점수에는 **회사 이름이 맞아서 오른 몫**이 있다.
- 실제 사용자는 회사가 아니라 부품으로 묻는다(기획 1절). 그래서 질문에서 완성차·브랜드 이름(Ford·GM·Toyota 등 고정 목록)을 빼면 0.510 → **0.483(−0.027)** 이 된다. 이 값이 실사용에 더 가까운 기준선이다.
- 기각한 측정 — v0a: 대응표의 모든 회사 이름 단어를 빼는 규칙은 `safety`·`new`·`trucks`·`highway` 같은 일반어까지 지워(질문 628개에서 2,174단어) 회사 이름 효과만 재지 못했다. 점수(0.418)는 판단에 쓰지 않는다.
- 후속: 뜻 검색(v2)도 브랜드를 뺀 질문으로 다시 재서, 회사 이름 없이도 이득이 유지되는지 확인한다.

### 3-2. 573 원인 칸 색인 (v4)

- 원인 칸이 있는 카드 8,179장에 원인 문장을 붙여 색인해도 0.510 → 0.505로 차이가 없다. 2014 이후 문항에서는 0.734 → 0.713으로 오히려 조금 내려갔다.
- 원인 칸은 **검색용이 아니라 엔진 2(원인 옮기기)의 입력**으로 쓰는 것이 맞다. 연대기는 처음부터 넣지 않았다(누수 방지).

## 4. 저장 위치 결과

같은 749문항, bge-small 임베딩. Postgres는 로컬 컨테이너(Postgres 17 + pgvector)에서 쟀다 — 운영 Supabase는 건드리지 않았다.

| 방식 | H@10 | 질문당 시간 p50 / p95 | 비고 |
|---|---|---|---|
| Python 메모리 BM25 | 0.510 | 34ms | 표준 라이브러리 구현 |
| Python 메모리 뜻 검색(numpy 내적) | 0.463 | **1.9 / 2.2ms** | 정확한 계산 |
| Postgres 전문 검색(FTS, `ts_rank_cd`) | **0.163** | 168 / 603ms | 점수 방식이 BM25와 달라 크게 낮다 |
| pgvector HNSW (로컬) | 0.438 | 0.5 / 0.8ms | 근사 검색이라 정확한 계산(0.463)보다 낮다 |
| **Supabase 네트워크 왕복** (`select 1`) | — | **229 / 587ms** | 서버가 멀다(한국에서 측정) |

- 색인 크기: FTS 31MB, 384차원 벡터 표 107MB(HNSW 색인 포함, build 1개).
- **결론**: 검색은 API 서버가 시작할 때 카드(약 29MB)와 임베딩(약 47MB)을 메모리에 읽어 두고 그 안에서 한다. 질문마다 DB를 부르면 왕복만 0.23초가 든다. Supabase는 build 단위 보관과 "답변 → 리콜 번호 → build → 원본" 추적(서비스 원칙 4)에 쓴다.
- pgvector는 나중에 카드 수가 크게 늘거나 서버를 여러 대 두어야 할 때 다시 본다.

## 5. 원인 옮기기(엔진 2) — 미측정

- 준비한 시험(`engine2_trial.py`): 질문마다 BM25 1위 리콜 중 573 원인 칸이 있는 것 30건. LLM에게 "원인 문장을 한 글자도 바꾸지 않고 고르기, 없으면 빈 목록"만 시킨다. 돌려받은 문장이 원문에 그대로 있는지 **글자 대조**하고, 없으면 버린다.
- 모델 후보와 가격(OpenAI 공식 문서, 100만 토큰당): `gpt-5.4-mini` 입력 0.75달러·출력 4.50달러, `gpt-5.4-nano` 입력 0.20달러. 30건이면 두 모델을 합쳐도 0.1달러 미만.
- **상태**: `.env`의 OpenAI 키가 인증에 실패(401)해 한 건도 호출되지 않았다(비용 없음). 키를 교체하면 바로 돌린다.
- 원인 문장이 "정말 원인을 말하는가"는 사람이 표본으로 확인한다(D 파트 몫, 지금은 우지훈).

## 6. P2 구현 권장안

```text
[React 화면] ──HTTP──▶ [Python API 서버]
                         ├ 시작 시: Supabase(또는 파일)에서 latest build 카드·원인 읽기 + 로컬 임베딩 로드
                         ├ ② 찾기: BM25 + bge-small → RRF → 상위 10
                         ├ ③ 원인 옮기기: LLM(573 원인 칸만, 원문 그대로)  ← 모델은 5절 시험 뒤 결정
                         └ ④ 검사: 원문 글자 대조·리콜 번호가 검색 결과 안인지
```

- 키(`DATABASE_URL`·LLM 키)는 API 서버 `.env`에만 둔다(DEC-032·DEC-037).
- 임베딩은 build가 바뀔 때 다시 만든다(bge-small 기준 30,350장 약 9분, 이 맥 CPU).
- 아직 정하지 않은 것: 부품 트리로 범위 좁히기(v3, 할 일 22의 연결 규칙이 먼저), API 서버를 어디서 돌릴지(발표 때 로컬/클라우드), 호출 상한.

## 7. 한계와 남은 측정

- **대리 평가**다. 정답 리콜 대부분이 조사 뒤에 접수돼 "과거 선례를 찾는 능력"은 재지 못한다. 시점 평가는 질문 판본 확보(할 일 18) 뒤에 한다.
- 질문에 회사 이름이 섞여 있어 점수가 실사용보다 높게 나온다(3-1, 약 0.03).
- 뜻 검색 모델은 bge-small만 끝났다. **bge-base 결과는 측정이 끝나면 3절 표에 추가한다.**
- 전체 임베딩은 표본 속도(카드 1,000장)로 예상한 것보다 오래 걸렸다(예상 0.7분 → 실제 8.8분). 표본의 카드가 짧았기 때문이다 — 다음에는 무작위 표본으로 잰다.
- pgvector는 HNSW 기본값(`ef_search` 40)으로만 쟀다.

## 8. 재현 방법

```bash
# 검색 방식 (표준 라이브러리, 약 2분)
uv run python -m scripts.defect_precedent.retrieval_compare bm25
# 로컬 뜻 검색 + RRF (fastembed는 이 명령에서만 임시 설치, pyproject 변경 없음)
RETRIEVAL_CACHE=<캐시 폴더> uv run --with fastembed python -m scripts.defect_precedent.retrieval_compare dense --model BAAI/bge-small-en-v1.5
# 저장 위치 (로컬 Postgres 17 + pgvector, 사용법은 storage_bench.py 머리말)
uv run --with fastembed --env-file .env python -m scripts.defect_precedent.storage_bench --model BAAI/bge-small-en-v1.5
# 원인 옮기기 (OpenAI 키 필요)
uv run --with openai --env-file .env python -m scripts.defect_precedent.engine2_trial --model gpt-5.4-mini --n 30 --out <결과.jsonl>
```

입력은 `data/processed/defect/`의 새 카드(build `f5cb2f944f36125d`, 드라이브 `defect_data_2026-10-08_maker-group`)다.
