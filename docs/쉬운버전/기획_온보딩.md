# 사내 온보딩 문서 정리·생성 에이전트 — 쉬운 버전

> 자세한 근거와 수치 출처는 원본 [`../기획_온보딩.md`](../기획_온보딩.md)를 본다.
> 원본은 팀 회의에서 나온 주제 전환 후보를 담은 **검토용 초안**이다. 주제 전환은 아직 공식 결정 기록에 없다.

## 한눈에 보기

- **무엇을**: 회사 자료를 넣으면 온보딩(신입 적응 안내) 문서의 **빠진 칸을 찾아 묻고, 근거 달린 초안을 만드는 도구**.
- **누구를 위해**: 신입·부서 이동자를 받는 회사의 온보딩 담당자(후보). **대상은 아직 확정되지 않았다.**
- **왜**: 문서를 잘 쓰는 회사조차 온보딩 정보가 흩어져 있어, 빈칸 많은 문서로 신입을 받게 된다.

## 어떻게 동작하나

시험 채점과 비슷하다. "모범 답안의 문항 목록"을 기준으로 우리 회사 답안지에서 빠진 문항을 찾는다.

1. GitLab 온보딩 문서 68건에서 자주 나오는 칸으로 **기준 목차**를 만든다. 사람이 확정한다.
2. 대상 회사의 온보딩 자료를 넣고 종류별로 나눈다.
3. 칸마다 "있음 / 없음 / 애매"를 판정하고 근거 위치를 적는다.
4. 없거나 애매한 칸은 담당자에게 묻는다.
5. 답변과 자료로 초안을 쓴다. 문장마다 출처를 단다. 출처 없는 문장은 쓰지 않고 다시 묻는다.
6. 담당자가 칸별로 승인한다.

## 1. 무엇이 문제인가

GitLab은 회사 운영을 공개 핸드북(회사 안내서)으로 관리한다. 문서 4,612개, 약 612만 단어다. 그래도 온보딩 정보는 흩어져 있다.

- "onboarding" 검색 결과 129건 중 61건(47%, 약 절반)은 입사와 무관하다.
- 엔지니어링 팀 17개 중 9개는 온보딩 페이지가 링크 한 줄뿐이다.
- 실제 체크리스트는 "공개"라고 소개되지만, 로그인 없이는 열리지 않는다.
- 같은 사실이 페이지마다 다르게 적혀 있다.

**1차 대상, 그 사람의 상황, 지금 어떻게 때우는지는 아직 없다.** 인터뷰나 조사 기록도 없다.

**알려진 실패 경우**: 회사마다 같은 칸을 다른 말로 부르면 놓친다. 팀 문서는 권한 같은 칸을 전사 문서에 맡겨서, 목차가 한 층이면 잘못된 경고가 뜬다. 내용이 핸드북 밖에 있으면 근거를 붙일 수 없다.

## 2. 비슷한 것은 이미 있나

**아직 모른다.** 상용 서비스 조사는 하지 않았다. "경쟁자 없음"이 아니라 "아직 안 찾아봄"이다. 관련 **연구**(STORM, Co-STORM, DocETL 등)만 확인했다.

**차별점(초안)**: 답을 지어내지 않는다. 검증된 문서 구조를 기준으로 빠진 칸을 묻고, 근거 있는 내용만 쓴다.

## 3. 왜 이 기술이 필요한가

- **RAG**(AI가 자료를 먼저 찾아보고 그 근거로 답하는 방식. 오픈북 시험과 비슷하다)를 쓰기로 팀이 정했다.
  - 대안인 **파인튜닝**(AI에 지식을 직접 학습시키기. 통째로 외우기와 비슷하다)은 출처를 따라가기 어렵고, 정책이 바뀌면 다시 학습해야 한다.
  - RAG는 문장마다 출처를 달 수 있고, 문서가 바뀌면 다시 넣기만 하면 된다.
  - 온보딩 문서 68건은 AI가 한 번에 읽을 수 있는 양이다. 즉 RAG를 쓰는 이유는 **양이 아니라 출처 추적과 갱신**이다.
- **기준 목차**가 없으면 무엇이 빠졌는지 판단할 기준이 없다.
- **LLM**(글을 이해하고 쓰는 대형 AI 모델)은 표현이 달라도 뜻으로 판정할 수 있다. 단어 규칙은 시범에서 11칸 중 3칸을 놓쳤다. 다만 **LLM의 효과는 아직 측정하지 않았다.**

## 4. 무엇으로 만드나

- 정해진 것: Python 3.12 + uv, 지식은 RAG로 넣기.
- 제외한 것: n8n(흐름 관리 도구) — 라이선스가 상업적 사용과 맞지 않아 팀이 제외했다.
- **아직 없음**: 흐름 관리, 임베딩 모델, 벡터 저장소, 검색 방식, LLM. 후보는 있다(예: 벡터 저장소는 PostgreSQL + pgvector, 검색은 뜻 검색 + 단어 검색 혼합).

## 5. 전체 구조

```text
회사 자료 → 기준 목차와 비교 → 빈칸 질문 → 근거 달린 초안 → 사람 승인
```

**꼭 지킬 약속**:
1. 근거 없는 문장은 쓰지 않는다.
2. GitLab은 구조만 빌린다. 금액·도구명·일정 같은 GitLab 사실은 넣지 않는다.
3. 칸 이름은 누구나 아는 말로 쓴다(예: "이슈 템플릿" 대신 "할 일 체크리스트").
4. 평가 정답은 사람이 표시한다. AI가 만든 정답으로 채점하지 않는다.

## 6. 지금까지 한 것과 앞으로 할 것

**평가셋**(사람이 정답을 표시해 둔 채점용 문서 묶음)은 **아직 없다.** GitLab이 아닌 회사의 공개 문서에 팀원이 직접 정답을 표시할 계획이다. GitLab으로 GitLab을 평가하면 자기 답안지로 채점하는 셈이기 때문이다.

**지금까지 (모두 시범)**:
- 기준 목차: GitLab 68건에서 칸별 출현 비율을 쟀다. 가장 많은 칸은 소통 채널(66%), 가장 적은 칸은 입사 전 준비(10%)다.
- 빈칸 찾기: 단어 규칙으로 Basecamp 문서 1건에서 11칸 중 8칸이 맞았다. 이 정답은 AI가 표시한 **시범값이며 평가셋이 아니다.** 틀린 3칸은 모두 표현이 달라서 놓쳤다.

**앞으로 (가설)**:
- v0: 지금의 단어 규칙을 기준선으로 잰다.
- v1: 칸 이름을 쉬운 말로 바꾸고 LLM으로 판정한다. 놓치던 칸을 찾기를 기대한다.
- v2: 목차를 2층(전사 / 팀)으로 나눈다. 잘못된 경고가 줄기를 기대한다.

## 7. 어려웠던 점

- 검색 결과에 입사와 무관한 문서가 섞였다 → 129건을 직접 열어 68건을 골랐다.
- 팀 문서에 권한 칸이 거의 없었다 → 전사 문서에 맡기기 때문이었다 → 목차를 2층으로 나누기로 했다(정리는 아직 남음).
- 다른 회사 문서가 같은 칸을 다른 말로 불렀다 → 칸 이름을 쉬운 말로 바꾸기로 했다(효과는 아직 측정 전).
- "공개"라던 템플릿 저장소가 실제로는 비공개였다 → 체크리스트 본문은 범위에서 뺐다.

**한 문장으로**: 검색 결과도 문서의 자기소개도 그대로 믿지 않고, 직접 열어 보고, 숫자로 확인하고, 다른 회사 문서로 시험한다.

## 하지 않기로 한 것

- 신입 온보딩 외의 사내 문서 전반 (발표까지는 한 종류만)
- 회사 사실을 AI에 학습시키기(파인튜닝) — RAG로 다룬다
- GitLab의 **내용**을 다른 회사에 복사하기 — 구조만 참고한다
- 목차 편집 화면, 여러 부서 동시 지원, 퀴즈, 티켓 자동 분담 — 발표에서 "다음 단계"로만 소개

## 아직 정해지지 않은 것

- 주제 확정과 공식 기록 (기존 `docs/기획.md`로 옮길지도 미정)
- GitLab 전용인지, 다른 회사에도 쓰는 범용인지
- 1차 대상 (인사 담당자 / 팀 리드 / 신입 본인)
- 임베딩 모델 · 벡터 저장소 · LLM
- 퀴즈·티켓 분담 포함 여부
- 팀 4명의 역할 분담 (발표자 역할은 따로 있음)
- 못 한 점검: 상용 서비스 조사, 평가셋, 정식 효과 수치. 지금 수치는 임시 스크립트로 센 것이라 **이 저장소에서 재현할 수 없다.**
- 일정 부담: 발표는 10/20(화), 실제 개발은 10/12~14 사흘뿐이다. 그래서 평가 정답표와 2층 목차는 개발 전(10/8~10)에 끝내야 한다.

## 용어 풀이

| 용어 | 쉬운 뜻 |
|---|---|
| 온보딩 | 새로 온 사람이 회사·팀에 적응하도록 돕는 과정 |
| 기준 목차 | 온보딩 문서에 보통 들어가야 할 칸들의 목록 |
| LLM | 글을 이해하고 쓰는 대형 AI 모델 |
| RAG | AI가 자료를 먼저 찾아보고 그 근거로 답하는 방식 |
| 파인튜닝 | AI 모델에 지식을 직접 학습시키는 것 |
| 임베딩 | 글의 뜻을 숫자 목록으로 바꾼 것. 뜻이 비슷하면 숫자도 비슷하다 |
| 벡터 저장소 | 숫자로 바꾼 글을 저장하고 비슷한 것을 빨리 찾는 창고 |
| 평가셋 | 성능을 재려고 사람이 정답을 표시해 둔 문서 묶음 |
| 기준선 | 개선 전 성능. 나중 버전과 비교하는 출발점 |
| 시범값 | 정식 평가가 아니라 가능성만 확인하려고 잰 값 |
| 재현 | 같은 방법으로 다시 해서 같은 수치가 나오는지 확인하는 것 |
