# 결함 선례 RAG — 쉬운 버전

> 자세한 근거와 수치 출처는 원본 [`../기획_결함선례.md`](../기획_결함선례.md)에 있다. 이 문서는 원본을 쉬운 말로 줄인 것이다.
> 원본은 2026-10-01에 쓴 **검토용 초안**이다. 10/2 주제 결정 회의에 올라간 후보 중 하나(N2)이고, 아직 채택되지 않았다.

---

## 한눈에 보기

- **무엇을**: 결함 내용을 한 줄로 넣으면, 다른 회사·같은 부품에서 있었던 과거 리콜·결함조사 사례(선례)를 원문 그대로 찾아 주는 도구를 만든다.
- **누구를 위해**: 자동차 회사와 부품 회사의 품질 엔지니어(제품 결함의 원인과 영향을 조사하는 사람)를 위해 만든다.
- **왜**: 결함 보고에는 법적 기한이 있다. 다른 회사의 비슷한 사례를 놓치면 큰 과징금을 물 수 있다. 그런데 지금은 그런 사례를 빨리 찾을 수단이 없다.

이 도구는 **"리콜해야 한다/안 해도 된다"나 "원인은 이것이다"라고 말하지 않는다.** "그 원인을 밝혔던 과거 사례와 근거"까지만 보여 준다.

---

## 어떻게 동작하나

도서관 사서에 비유할 수 있다. 사서는 "이 책을 읽으면 답이 나옵니다"라고 판단해 주지 않는다. 비슷한 책을 찾아 해당 쪽을 펼쳐 줄 뿐이다.

1. **미리 준비**: 미국 도로교통안전국(NHTSA)의 공개 리콜·결함조사 자료를 내려받아 검색하기 좋게 정리한다.
2. **질문 입력**: 품질 엔지니어가 결함 내용을 한 줄로 쓴다. 예: "앞 브레이크 캘리퍼에서 브레이크액이 샌다."
3. **찾기 (엔진 1)**: 단어 검색과 뜻 검색을 함께 써서 비슷한 선례를 고른다. 부품 분류표로 범위를 좁힌다.
4. **원인 문장 뽑기 (엔진 2)**: AI(LLM)가 선례 원문에서 원인을 설명한 문장을 **글자 그대로** 골라낸다. 새로 지어내지 않는다.
5. **검사**: 뽑은 문장이 원문에 정말 있는지, 리콜 번호가 실제로 있는 번호인지 프로그램이 대조한다.
6. **결과 보여 주기**: 선례 카드(원문 + 원인 문장 + "추정" 표시)와 확인 체크리스트를 화면에 띄운다.

AI(LLM)는 4단계에서만 쓴다. 나머지는 일반 프로그램과 규칙이라 매번 같은 결과가 나온다.

## 1. 무엇이 문제인가

### 실제 사건
2018년 BMW 차량 화재 사태에서 국토교통부는 과징금 112억 원과 형사고발을 결정했다. 지적 중 하나는 **같은 엔진·EGR 부품(배기가스 재순환 장치)을 쓴 일부 차종을 리콜에서 뺐다**는 것이었다. 독일 본사는 2015년 10월에 관련 대응팀을 꾸렸지만, 리콜은 2018년 7월에야 했다.

### 왜 시간이 중요한가
- 미국에서는 결함이 안전 관련으로 판단되면 **5영업일 안에** 보고해야 한다. 부품 제조사도 대상이다.
- 기한은 "실제로 안 날"이 아니라 **"알았어야 했던 날"**부터 따진다. (규정 문장 자체가 아니라, 집행 과정에서 쓰는 해석이다.)
- 늦게 리콜하면 큰 제재를 받는다. 예: 부품 공급사 Takata 2억 달러(2015), Ford 1.65억 달러(2024).
- 한국도 결함을 늦게 고치면(시정조치: 결함을 바로잡는 수리·교체) 매출액 3% 이하의 과징금을 받는다. 부품 제작사도 대상이다.
- 한 연구에서는 회사에 지식 데이터베이스가 있어도 엔지니어들이 "있는 줄 모르고" "동료에게 직접 묻는 것을 더 좋아했다".

### 사용자의 상황
현장에서 결함 신고가 몇 건 들어왔다. 반품된 부품을 보면 **무엇이** 고장 났는지는 안다. 하지만 **왜** 그렇게 됐는지는 아직 모른다. 회사 안의 기록만 보면 다른 회사의 같은 부품 사례를 놓친다. 공개 리콜 자료는 3만 건이 넘고, 단어 검색만 된다.

지금 현장에서 어떻게 대처하는지는 **조사하지 않았다.** "동료에게 묻거나 사내 도구를 쓸 것"이라는 가설만 있다.

### 결함의 세 층
| 층 | 질문 | 예 | 이 도구에서 |
|---|---|---|---|
| ① 증상 | 어떻게 보이나 | "브레이크가 덜 듣는다" | 입력 가능. 결과가 넓게 흩어진다 |
| ② 고장 부위 | 무엇이 고장 났나 | "앞 브레이크 캘리퍼에서 브레이크액이 샌다" | 입력 가능. 같은 부품 선례로 좁혀진다 |
| ③ 근본 원인 | 왜 그렇게 됐나 | 실링 재질, 조립 공정 등 | 선례에 적힌 원인을 "후보"로 인용만 한다. 확정하지 않는다 |

②까지 아는 경우가 가장 흔하다. 이 도구가 가장 잘 맞는 경우다.

**주의**: 실제 품질 엔지니어에게 물어본 적이 없다. 10/8 전에 최소 1명에게 확인할 계획이다.

### 잘 안 되는 경우
- 질문이 너무 짧으면("소음 발생") 결과가 흩어진다.
- 아주 새로운 결함 유형은 선례가 없다. 이때는 "유사 선례 없음"이라고 답한다.
- 자료가 미국 중심이라 한국 내수 전용 차종은 대부분 없다.
- 현장 말투로 물으면 더 어려워질 가능성이 높다. (아직 재 보지 않은 가정이다.)

## 2. 비슷한 것은 이미 있나

있다. **"NHTSA 자료 + RAG" 조합은 이미 다른 팀(Recall Recon)이 만들었다.** 다만 그쪽은 "리콜이 1년에 몇 건 나올지" 예측하는 것이 목적이다. (그 글의 원문은 직접 열어 보지 못했고, 검색 요약만 확인했다.)

다른 회사 도구들은 주로 **자기 회사 안의** 보증·불만 자료를 분석한다. 다른 회사 선례를 원문으로 인용하는 기능은 확인되지 않았다. 기업 내부 기능은 확인하지 못했다.

**우리의 차이**: 증상 한 줄로 다른 회사·같은 부품의 선례를 원문과 함께 찾는다. 그리고 그 정확도를 **규제기관이 실제로 연결해 둔 "조사 → 리콜" 728쌍**으로 증명한다. 이런 방식의 평가는 다른 연구에서 찾지 못했다.

---

## 3. 왜 이 기술이 필요한가

RAG(검색 증강 생성)는 AI가 답하기 전에 자료를 먼저 찾아 보게 하는 방식이다. 시험에서 "외워서 쓰기" 대신 "교과서를 펴 놓고 쓰기"와 같다.

| | AI(LLM) 혼자 | RAG로 |
|---|---|---|
| 선례 찾기 | 유명한 사건만 기억한다 | 3만 건 전체에서 찾는다 |
| 리콜 번호 | **지어낼 수 있다** | 실제로 있는 번호만 쓴다 |
| 최신 자료 | 학습 이후 리콜은 모른다 | 매일 바뀌는 공개 파일을 다시 정리한다 |

단어 검색만으로는 부족하다. 소비자 말("차가 갑자기 꺼짐")과 리콜 문서 말("loss of motive power")이 다르기 때문이다. 단어 검색의 정답률은 0.51(약 절반)이다.

**솔직하게 남기는 점**
- 단어 검색이 이미 0.51이다. RAG가 0.03 이상 높지 않으면 "같다"고 보고한다.
- AI 혼자 답하게 하고, 그 번호가 실제 목록에 있는지 자동 검사할 계획이다. 이 결과는 **아직 재지 않았다.**

## 4. 무엇으로 만드나

아래는 모두 **후보**이다. 아직 설치하지 않았고, 10/6–7 시험 제작 때 확정한다.

- **자료**: 미국 NHTSA 공개 파일. 리콜 30,341건과 결함조사 5,349건이다. 원인·결과·시정조치가 칸별로 나뉘어 있다. 한국 리콜 자료는 "리콜사유" 한 칸뿐이라 쓰지 않는다.
- **단어 검색**: BM25. 부품명이나 약어("EGR")를 정확히 찾는다. 이미 시험해 봤다.
- **뜻 검색**: 임베딩(글을 숫자 목록으로 바꿔 뜻이 비슷한 글끼리 가깝게 놓는 기술) + 벡터 저장소(그 숫자를 보관하고 가까운 것을 찾는 창고). 한국어 질문을 받으려면 여러 언어를 아는 모델이어야 한다. OpenAI 모델과 bge-m3 중 비교해서 고른다.
- **두 검색 합치기**: RRF. 두 검색의 순위를 합친다.
- **원인 문장 뽑기**: LLM(대형 언어 모델, ChatGPT 같은 AI). **이 기획에서 LLM을 쓰는 유일한 곳이다.** 모델은 아직 정하지 않았다.
- **표시 규칙**: 사람이 관리하는 단어 목록 2개("추정" 표현 목록, 말한 주체 목록).
- **부품 그래프**: NHTSA 부품 분류표를 나무 모양으로 정리한 것. 부품 이름으로 범위를 좁힌다.
- **번역**: 한국어 질문을 영어로 바꿔 검색한다. 화면에 보여 줄 선례만 한국어로 번역하고, 영어 원문을 나란히 둔다.
- **화면**: Streamlit(파이썬으로 간단한 웹 화면을 만드는 도구).

## 5. 전체 구조

```text
[미리]           [질문할 때]                                    [마무리]
① 준비    →   ② 엔진 1: 찾기     →   ③ 엔진 2: 원인 문장 뽑기   →   ④ 검사·정리
자료 정리      단어+뜻 검색            LLM이 원문에서                원문 대조
               부품 그래프             글자 그대로 골라냄            체크리스트
```

- 엔진 1만 있어도 선례 카드는 나온다.
- 엔진 2는 **뽑기만 하고 추론은 금지**다. 예를 들어 "아마 재질 문제일 것이다" 같은 말은 만들지 않는다.
- 원문에 "appeared to(~인 것으로 보였다)", "might(~일 수도)" 같은 추정 표현이 있으면 그대로 둔다. 단정으로 바꾸면 규제기관도 확정하지 않은 원인을 확정한 셈이 되기 때문이다.

### 검사 장치
| 장치 | 하는 일 | 못 잡는 것 |
|---|---|---|
| 글자 대조 | 뽑은 문장이 원문에 그대로 있는지 확인(Ctrl+F와 같다) | 원문에 있지만 원인이 아닌 문장. 그래서 30건은 사람이 직접 본다 |
| 번호 대조 | 리콜 번호가 실제 목록에 있는지 확인 | — |
| 추정 표현 목록 | "추정" 표시를 붙인다 | 목록에 없는 새 표현 |
| 말한 주체 목록 | "정부 시험 추정"과 "제조사 주장"을 구분한다 | 문장에 주어가 없으면 비워 둔다 |

### 꼭 지킬 원칙
1. **판정하지 않는다.** "리콜 대상입니다/아닙니다", "원인은 ○○입니다"를 출력하지 않는다. 판정용 칸 자체를 만들지 않는다.
2. **근거 없는 말을 하지 않는다.** 원인·결과·시정조치는 원문 인용만 한다.
3. **리콜 번호를 지어내지 않는다.**
4. **출처를 따라갈 수 있게 한다.** 카드 → 리콜 번호 → 원본 파일 → 내려받은 날짜를 남긴다.
5. **법적 위험을 알린다.** 검색 기록이 "알았어야 했다"의 증거가 될 수 있다. 실제 도입 때 기록 보관은 법무 검토 대상이다.

체크리스트("같은 부품인가? 생산기간이 겹치나? 결과가 같은가?")도 자료의 칸에서 만든다. LLM이 지어내지 않는다.

## 6. 지금까지 한 것과 앞으로 할 것

### 평가셋(실력을 재는 시험지)
NHTSA 결함조사 기록에는 "이 조사로 시작된 리콜 번호"가 적혀 있다. 그래서 사람이 정답을 달지 않아도 시험지를 만들 수 있다.
- 질문: 조사 요약의 첫 두 문장(원인이 밝혀지기 전의 신고 내용)
- 정답: 그 조사로 실제 시작된 리콜
- 전체 **728쌍**(그중 2010년 이후 212쌍). 정답은 규제기관 기록이다. AI가 만든 것이 아니다.
- 질문에서 회사·브랜드·모델 이름과 리콜 번호는 지운다(정답을 미리 흘리지 않기 위해).

이 시험지는 "맞는 선례를 찾았나"만 잰다. **"원인(왜)을 알려 주나"는 재지 못한다.** 그래서 발표에서 "원인을 찾아 준다"고 말하지 않는다. "원인을 밝혔던 선례를 찾아 준다"까지가 정확하다.

### 지금까지 한 것
- 처음 만든 시험지(같은 조사로 묶인 리콜끼리 찾기)는 단어 검색만으로 0.90이 나왔다. 너무 쉬워서 버렸다. 이 방식은 관계 그래프 시연용으로만 쓴다.
- 새 시험지로 단어 검색(BM25) 기준선(비교의 출발점 점수)을 쟀다. 상위 10개 안에 정답이 있는 비율(hit@10)이 0.514다. 2010년 이후만 보면 0.613이다.
- 품질 쪽 개선 기록은 **아직 없다.**

**중요**: 0.51은 **잠정값**이다. 10/2에 시험지를 만드는 코드에서 버그를 찾았다. "2.5"나 "U.S." 같은 곳의 마침표에서 문장이 잘려, 질문이 엉망이 된 경우가 있었다. 이 버그로 영향받은 질문 수는 **아직 세지 않았다.** 고친 뒤 다시 잰다.

실험 코드는 아직 임시 폴더에만 있고, 이 저장소에는 없다.

### 앞으로 할 것 (기대 효과는 모두 가설이다)
| 버전 | 바꿀 것 |
|---|---|
| v-1 | AI 혼자 답하게 하고, 지어낸 번호 비율을 잰다 |
| v0 | 단어 검색 — 시험지 수정 후 다시 잼 |
| v0+ | 단어 다듬기 (예: leak/leaking을 같은 말로) |
| v1 | 뜻 검색 |
| v2 | 단어 검색 + 뜻 검색 합치기 |
| v3 | 결함조사 요약도 검색 대상에 넣기 |
| v4 | 부품 그래프 추가 |
| v5 | 원인 문장 뽑기 + 검사 |

- 0.03 미만 차이는 "같다"로 본다. AI가 들어가는 버전은 3번 돌려 범위로 보고한다.
- **보조 시험지**: 728쌍 중 30개를 골라 팀원이 현장 말투로 바꿔 쓴다(영어 15 + 한국어 15). 정답은 그대로 정부 기록이다.
- 비용은 모델이 정해지면 계산해서, 실행 전에 팀에 확인받는다.

### 일정 (원본 9절)
10/2 주제 결정 → 10/6–7 시험 제작(버그 수정 후 기준선 재측정 포함) → 10/8–10 설계 확정 → 10/12–14 파트 개발 → 10/15–18 개선·정리 → 10/19 리허설 → 10/20 발표. 파트 분담(데이터·평가 / 엔진 1 / 엔진 2+검사 / 화면)은 **제안일 뿐 확정이 아니다.**

## 7. 어려웠던 점

모두 10/1–10/2 주제 검토 중에 실제로 겪은 일이다.

- **리콜 파일 링크가 깨져 있었다.** 파일 설명서를 읽고 찾아보니 2010년 전/후 두 파일로 나뉘어 있었다.
- **보고된 숫자가 원본과 달랐다.** "LG 배터리 조사가 리콜 7건을 묶었다"는 보고가 있었지만, 원본을 직접 세 보니 11건이었다.
- **시험지가 너무 쉬웠다.** 단어 검색만으로 0.90이 나왔다. 열어 보니 공급사의 결함 설명 문구가 리콜마다 거의 똑같이 반복돼 있었다. 그래서 시험지를 바꿨다.
- **경쟁 서비스가 있었다.** 비어 있는 분야라고 생각했는데 Recall Recon이 있었다. 그래서 차이점을 좁혔다.
- **정답이 1,000등 밖으로 밀린 질문이 있었다.** 처음엔 엔진 문제라고 생각했다. 순서대로 열어 보니 시험지를 만드는 코드의 버그였다.
- **리콜 문서에는 "왜"가 빠진 경우가 많았다.** 결함조사 요약에 원인 문장이 있는 경우가 있어, 엔진을 "찾기"와 "원인 문장 뽑기"로 나눴다.

**배운 점**: 숫자가 이상하면 엔진보다 원본을 먼저 연다. 시험이 너무 쉬우면 버리고, 너무 어려우면 시험지를 의심하고, 남이 보고한 숫자는 원본으로 다시 센다.

## 하지 않기로 한 것

- **리콜 여부 판정** — 회사의 법적 판단이다. 일부러 하지 않는다.
- **원인 확정** — "원인은 ○○입니다"라고 말하지 않는다. 일부러 하지 않는다.
- **공급사 단위로 묶기** — 자료에 공급사 칸이 없다. PDF를 읽어야 해서 이번 범위에서 뺀다.
- **소비자 신고와 조사·리콜 연결** — 연결할 칸이 없어 이번 범위에서 뺀다. 차대번호·운전자 이름 같은 개인정보 칸은 쓰지 않는다.
- **회사 내부 보증·불만 자료 연결** — 공개 자료로만 시연한다.
- **한국 리콜 자료** — 1,045행에 "리콜사유" 한 칸뿐이라 깊이가 부족하다.
- 다음 두 가지는 **일부만** 한다: 선례끼리의 관계 그래프(시연 수준), 예비조사 → 정밀분석 이력(본문 문장에만 있어 일부만 연결).

## 아직 정해지지 않은 것

- 이 주제를 채택할지 (다른 후보: A 규제 RAG / B 온보딩 문서 / B' 문서 구조화 / C 코드 온보딩)
- 발표에서 LG에너지솔루션 배터리 사례를 쓸지 (원본은 BMW·Takata를 앞에 세우자는 입장이다. 팀이 미리 정한다.)
- 임베딩 모델(OpenAI / bge-m3)과 LLM 모델, 예상 비용
- 평가 범위: 전체 728쌍으로 할지, 2010년 이후 212쌍으로 할지
- 품질 실무자 1명 인터뷰 — 아직 없다
- Recall Recon 원문 직접 확인
- 결함조사 요약에 원인 분석이 실제로 담긴 비율 — **아직 재지 않았다.** (단순 단어 검색으로는 95건 중 53건에 원인 표현이 있었지만, 대략적인 값이다.) 비율이 낮으면 "왜"를 보완하는 효과가 약하다.
- **시험지 수정**: 버그 고치기 → 영향받은 질문 수 세기 → 조사 제목을 질문에 넣을지 정하기 → 결함 정보 없는 질문을 뺄 기준 정하기 → 기준선 다시 재기
- 보조 시험지 30문항을 쓸 팀원
- 규칙 사전 초안(추정 표현 목록, 말한 주체 목록)
- 부품 그래프에 넣을 한국어·현장어 같은 말 — 사람이 승인해야 한다
- 임베딩 모델이 한국어를 잘 다루는지 확인
- 실험 코드를 저장소로 옮기기
- 한국 국토부 리콜정보 API의 칸 구성 확인
- 이 도구로 시간이 얼마나 줄어드는지, 1년에 조사가 몇 건인지 — **자료가 없다.** 지어내지 않고 "확인 못 함"으로 둔다.

## 용어 풀이

| 용어 | 쉬운 뜻 |
|---|---|
| 리콜 | 제품에 결함이 있을 때 회사가 이미 판 제품을 거둬 고쳐 주거나 바꿔 주는 것 |
| 결함조사 | 규제기관이 신고를 받고 결함이 있는지 살펴보는 조사. 예비조사(PE)와 그보다 깊은 정밀분석(EA)이 있다 |
| 시정조치 | 결함을 바로잡는 방법(수리, 부품 교체 등) |
| 품질 엔지니어 | 제품 결함의 원인과 영향 범위를 조사하는 회사 직원 |
| 선례 | 과거에 있었던 비슷한 사례 |
| NHTSA | 미국 도로교통안전국. 리콜·결함조사 자료를 공개한다 |
| 과징금 | 법을 어긴 회사에 정부가 물리는 돈 |
| LLM | 대형 언어 모델. ChatGPT 같은 글 쓰는 AI |
| RAG | AI가 답하기 전에 자료를 먼저 찾아 보게 하는 방식. "교과서 펴 놓고 쓰기" |
| BM25 | 질문과 같은 단어가 많이 든 문서를 찾는 단어 검색 방법 |
| 임베딩 | 글을 숫자 목록으로 바꿔, 뜻이 비슷한 글끼리 가깝게 놓는 기술 |
| 벡터 저장소 | 임베딩 숫자를 보관하고 가까운 것을 찾아 주는 창고 |
| RRF | 두 검색 결과의 순위를 합쳐 하나의 순위로 만드는 방법 |
| 부품 그래프 | 부품 분류를 나무 모양(큰 분류 → 작은 분류)으로 정리한 것 |
| 평가셋 | AI 실력을 재기 위한 시험지(질문 + 정답 묶음) |
| 기준선 | 개선 전 비교의 출발점이 되는 점수 |
| hit@10 | 정답이 상위 10개 결과 안에 들어 있는 비율 |
| MRR | 정답이 몇 번째에 나왔는지를 반영한 점수. 앞에 나올수록 높다 |
| 정답 누출 | 질문에 정답 단서가 섞여 점수가 부풀려지는 일 |
| 글자 대조 | 뽑은 문장이 원문에 그대로 있는지 확인하는 검사 |
| 규칙 사전 | 사람이 관리하는 단어 목록. 매번 같은 결과를 낸다 |
| Streamlit | 파이썬으로 간단한 웹 화면을 만드는 도구 |
