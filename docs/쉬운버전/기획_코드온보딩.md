## 한눈에 보기

- **무엇을**: 프로젝트 코드를 설명해 주는 도구를 만든다. 설명마다 "어느 파일 몇째 줄에 있는지"를 붙인다. 설명한 내용으로 퀴즈를 내서 정말 이해했는지 확인한다.
- **누구를 위해**: 이미 몇 년째 돌아가는 프로젝트에 중간에 들어온 개발자를 위해 만든다. 이들은 사내 시스템 권한이 나올 때까지 소스 코드만 볼 수 있다.
- **왜**: 이들이 권한을 기다리며 1주~1달을 그냥 보내기 때문이다. 이해했는지 확인해 주는 사람도 없어서, 한참 뒤 중간 점검에서야 이해가 부족했다는 것이 드러난다.

## 어떻게 동작하나

1. **미리 준비**: 코드 저장소를 함수·클래스 단위 조각으로 나눈다. 누가 누구를 부르는지 연결 지도(호출 그래프)도 만든다.
2. **질문**: 개발자가 "로그인 검증은 어디서 하나요?"처럼 묻는다.
3. **찾기**: 이름이 똑같은 것(키워드 검색)과 뜻이 비슷한 것(벡터 검색)을 둘 다 찾고, 연결 지도에서 이웃 함수도 가져온다.
4. **설명**: AI가 찾아온 코드 안에서만 설명한다. 문장마다 "파일:줄" 근거를 붙인다.
5. **근거 검사**: 근거가 실제 코드에 있는지 기계가 확인한다. 근거가 부족하면 답하지 않고 "확인 필요"라고 한다(기권).
6. **퀴즈**: 방금 설명에 쓴 코드로 객관식·빈칸 문제를 낸다. 틀리면 다시 설명하고 다시 낸다.
7. **기록**: 어느 영역을 다시 봐야 하는지 PM(프로젝트 관리자) 화면에 표시한다. 개인 점수는 남기지 않는다.

## 1. 무엇이 문제인가

SI 프로젝트(고객사 시스템을 대신 만들어 주는 일)에는 중간에 새 개발자가 자주 들어온다. 이 사람은 권한 신청을 넣고 기다린다. 그동안 사내 위키나 이슈 게시판에 못 들어간다. 볼 수 있는 것은 소스 코드뿐이다.

- 코드를 혼자 파악할 길잡이가 없다. 공식 안내 자료는 없거나 낡았다. 물어볼 사람은 바쁘다.
- 그래서 1주~1달을 그냥 보낸다.
- 설명을 들어도 이해했는지 아무도 확인하지 않는다. 격차는 중간 점검에서야 드러난다.
- 두 번째 대상도 있다. AI로 빨리 개발한 나머지, 자기가 만든 코드를 설명하지 못하는 개발자다.

이 문제의 근거는 **LG CNS 현직자 특강에서 나온 말**이다. "권한이 나오기까지 빠르면 일주일, 길면 2주에서 한 달", "같은 걸 10번 이상 설명했다" 같은 발언이 있었다.

> **주의**: 실제 사용자에게 확인한 적은 없다. "권한 기다리며 논다"는 특강 발언 1건에 기댄 것이다. 얼마나 자주, 얼마나 길게 생기는지는 아직 모른다. 10/8 전까지 현직자 1–2명에게 확인할 계획이다.

**잘 안 되는 경우** (먼저 밝혀 둔다): 주석·이름이 엉망인 오래된 코드, 실행해 봐야 아는 동작(외부 연동, 예약 작업 등), 업무 사정을 묻는 질문("이 할인 정책은 왜 이런가")이다. 업무 질문은 코드에 답이 없으니 기권한다.

## 2. 비슷한 것은 이미 있나

있다. 코드를 설명해 주는 도구는 많다(DeepWiki, GitHub Copilot, Cursor 등). 대부분 "물어보면 답하는" 방식이고, 이해했는지 되묻지 않는다.

**퀴즈를 내는 도구도 이미 있다.** 오픈소스 "Codebase to Course"는 코드를 학습 코스로 바꾸고 퀴즈를 넣는다. 가장 가까운 경쟁자다. 그러니 "이해를 확인하는 도구는 없다"고 말하면 틀린다.

우리 안의 차이점은 세 가지다.
1. 퀴즈 정답이 정말 코드에 있는지 **코드 줄로 검증**한다.
2. 틀린 영역을 **PM에게 전달**한다.
3. 정확도를 **공개 평가셋(누구나 쓰는 시험 문제 모음) 점수**로 보여 준다.

> **주의**: 이 비교는 각 도구의 소개 페이지(README)만 보고 한 것이다. Codebase to Course를 직접 돌려 비교한 적은 아직 없다. 10/6–7 프로토타입 때 같은 코드로 돌려 볼 계획이다.

학술 연구(RANGER)는 "연결 지도 + 검색" 방식이 통한다는 근거로 인용한다. 그 연구도 이해 확인은 하지 않는다.

## 3. 왜 이 기술이 필요한가

이 안은 **RAG**(AI가 답하기 전에 관련 자료를 먼저 찾아 읽게 하는 방식)와 **호출 그래프**(함수끼리 누가 누구를 부르는지 그린 지도)를 쓴다.

- **AI만 쓰면**: 회사 코드는 공개된 적이 없어서, AI가 그럴듯하게 지어낸다. 근거도 댈 수 없다.
- **RAG를 쓰면**: 실제 코드에서 찾아온 함수 안에서만 설명한다. 사용자가 근거 줄을 직접 열어 볼 수 있다.

**왜 파인튜닝이 아닌가.** 파인튜닝은 AI를 추가로 공부시켜 지식을 머리에 넣는 방법이다. 그런데 코드는 프로젝트마다 다르고 매일 바뀐다. 들어올 때마다 다시 공부시킬 수 없다. 그때그때 찾아보는 편이 맞다.

**왜 "비슷한 것 찾기"만으로는 안 되나.** "이 함수를 부르는 곳은?"이라는 질문은 비슷하게 생긴 코드가 아니라 **연결선**을 따라가야 답이 나온다. 지하철 공사 구간의 영향을 보려면 비슷하게 생긴 역이 아니라 노선을 따라가야 하는 것과 같다. 또 뜻으로 찾는 검색은 `getUserById`와 `getUserByEmail`을 잘 못 가른다. 그래서 이름 그대로 찾는 검색을 함께 쓴다.

**솔직하게 남길 점**:
- 근거 검사를 붙여도 AI가 지어내는 답(환각)은 남는다. 작성자의 이전 개인 프로젝트(공시 RAG)에서는 **19.2%가 남았다**. 이 저장소에서 다시 잰 값은 아니다. 그래서 모르면 답하지 않는 "기권"을 넣고, 환각 비율을 숫자로 공개할 계획이다.
- 연결 지도는 실행 중에야 정해지는 호출을 놓친다. 그래서 영향 범위는 "**최소** 이만큼"이라고 표시한다.

## 4. 무엇으로 만드나

> 아직 설치한 것은 없다. 아래는 **후보**다. 10/6–7 프로토타입에서 확정한다.

- **대상 언어**: Python 하나. 평가셋이 Python 코드라서다. SI 현장 주력인 Java는 "다음 단계"로 둔다.
- **코드 나누기**: 함수·클래스 단위로 자른다. 중간에서 자르면 설명이 깨진다.
- **검색**: 이름으로 찾기(BM25) + 뜻으로 찾기(임베딩·벡터 검색)를 섞는다. 두 결과는 순위만으로 합친다(RRF).
- **임베딩 모델**: 로컬 모델과 OpenAI 모델 중 프로토타입에서 비교해 고른다.
- **연결 지도**: 처음에는 간단한 파이썬 도구(networkx)로 만든다. 커지면 그래프 전용 DB(Neo4j)로 바꾼다.
- **AI 모델**: OpenAI API. 어떤 모델인지는 프로토타입에서 정한다. 로컬 경량 모델은 이전 개인 프로젝트에서 성능(재현율)이 43.2%로 떨어졌다(이 저장소에서 다시 잰 값 아님).
- **화면**: Streamlit.

**보안 전제**: 데모는 공개 코드로만 한다. 고객사 코드는 외부 AI로 보내지 않는다는 전제로, AI 호출 부분을 한곳에 모아 사내 모델로 바꿀 수 있게 만든다.

## 5. 전체 구조

층을 쌓듯 나눈다. 아래층이 위층에 재료를 넘긴다.

```text
평가     — 정확도·근거 검사 통과율·퀴즈 품질을 잰다 (모든 층에 걸침)
화면     — 질문, 퀴즈, 영향 범위 그림, PM 화면
퀴즈     — 근거 코드로 출제 → 검증 → 채점 → 기록
영향 범위 — 연결 지도를 따라 "이 함수를 고치면 어디가 영향받나"
설명     — 근거 안에서만 답하기, 근거 검사, 기권
검색     — 이름 검색 + 뜻 검색 + 연결 지도 이웃
색인     — 코드 내려받기 → 버전 고정 → 함수 단위로 자르기 + 연결 지도
```

**퀴즈를 믿을 수 있게 하는 규칙.** AI가 만든 퀴즈를 그대로 내보내지 않는다.
1. 방금 설명에 쓴 코드 안에서만 낸다.
2. 객관식·빈칸만 낸다. 정답은 함수·변수 이름 같은 코드 조각이어야 한다. 그래야 채점이 글자 비교로 딱 떨어진다.
3. 정답이 근거 줄 안에 실제로 있는지 확인한다. 없으면 버린다.
4. 오답 보기는 근거 줄 안에 없어야 한다. "오답이 사실은 정답"인 경우를 막는다.
5. 질문에 정답 이름이 그대로 들어 있으면 너무 쉬우니 버린다.
6. 두 번 다시 내도 통과 못 하면 그 주제는 퀴즈 없이 넘어간다. 지어낸 퀴즈보다 퀴즈 없음이 낫다.

**꼭 지킬 약속**: 근거 없는 문장은 내보내지 않는다. 모르면 기권한다. 답에서 원본 코드 위치까지 거꾸로 따라갈 수 있게 한다.

## 6. 지금까지 한 것과 앞으로 할 것

**지금까지 한 개선: 아직 없다.** 이 저장소에는 아직 코드가 없다. 대신 무엇을 어떻게 잴지 먼저 정해 두었다.

**평가셋**: SWE-QA라는 공개 시험 문제 모음을 쓴다. 질문 720개, Python 저장소 15개로 되어 있다. 이 중 저장소 1–2개(저장소당 평균 48문항)만 쓴다. 채점은 AI 심판이 100점 만점으로 매긴다. 근거 줄이 실제로 있는지는 기계로 검사하고, 퀴즈 품질은 표본 30건을 팀원 2명이 직접 표시한다.

**잴 때의 규칙**: 점수 차이가 0.03 미만이면 "같다"로 본다. 이전 개인 프로젝트에서는 같은 코드·같은 문제로 돌려도 재현율이 74.0~80.3%로 흔들렸다. 그래서 같은 설정을 3회 이상 돌려 범위로 보고한다.

**앞으로의 개선 계획** (기대 효과는 모두 **가설**이다):

| 버전 | 바꿀 것 | 기대 효과 |
|---|---|---|
| v0 | AI만 사용 (검색 없음) | 비교 기준. "RAG가 왜 필요한가"를 숫자로 보여 준다 |
| v1 | 뜻 검색 + 근거 안에서만 답하기 | v0보다 정확도 상승 |
| v2 | + 이름 검색 섞기 | 이름이 들어간 질문에서 더 잘 찾음 |
| v3 | + 연결 지도 이웃 | "누가 누구를 부르나" 질문에서만 크게 상승 |
| v4 | + 근거 검사·기권 | 지어낸 답 감소, 정확도는 유지 |
| Q1 | 퀴즈 검증 규칙 적용 전/후 | 퀴즈 품질 통과율 상승 |

**비용**: 유료 API를 쓴다. 저장소 2개, 약 96문항으로 가정하면 6개 버전 × 3회로 답변 생성이 약 1,700회다. 여기에 같은 수 이상의 심판 채점이 더해진다. 금액은 모델 값이 정해진 뒤 계산하고, 실행 전에 팀 확인을 받는다.

## 7. 어려웠던 점

**아직 없다.** 구현 전이라 실제로 막힌 기록은 없다. 대신 예상되는 어려움을 적어 둔다.

- **코드 자르는 크기**: 너무 길면 잘리고, 너무 짧으면 맥락이 없다.
- **호출 해석**: 같은 이름 함수가 여럿이면 연결이 애매하다. 확실하지 않으면 "추정"으로 표시한다.
- **퀴즈 품질**: 정답이 코드에 없으면 채점할 수 없다. 이때는 출제를 포기한다.
- **평가 비용**: 버전 × 반복 × 문항 수만큼 돈이 든다. 저장소 2개로 줄인다.
- **사흘 개발**: 기능이 많다. 시간이 모자라면 아래 순서의 뒤쪽부터 줄인다.
  인용 답변 > 퀴즈+검증 > 평가 수치 > 영향 범위 그림 > PM 화면

**기록 규칙**: 막힌 날 바로 한 줄이라도 적는다(날짜 / 증상 / 시도 / 결과). 버린 아이디어도 이유와 함께 적는다. 현직자 특강에서도 "예전 일을 떠올리기가 너무 어려웠다"는 말이 나왔다.

## 하지 않기로 한 것

이 도구는 "코드에 **무엇이 쓰여 있나**"까지만 다룬다. 판단을 하기 시작하면 틀렸을 때 책임이 생기기 때문이다.

- **코드 평가·수정 제안**: "잘 짰다/잘못됐다", "이렇게 고쳐라"를 말하지 않는다. 코드 리뷰는 별개 문제다.
- **개발자 실력 평가·인사 자료**: 퀴즈가 시험이 되면 사람들이 도구를 피한다. PM 화면은 "어디를 더 설명할지"만 보여 준다. 개인 점수표는 만들지 않는다.
- **사내 시스템·위키·이슈 게시판 연결**: 바로 그 권한이 없는 기간이 대상이기 때문이다.
- **서술형 퀴즈 채점**: 객관식·빈칸만 한다.
- **회사 안에 설치하는 AI 모델**: 이번 범위 밖이다. 나중에 바꾸기 쉬운 구조로만 만든다.
- **어느 정도만 하는 것**: 코드 흐름 설명은 코드만 보고 따라갈 수 있는 데까지만 한다. 영향 범위는 연결 1–2단계까지 시연 수준으로만 한다.

## 아직 정해지지 않은 것

**주제 자체**
- 이 안(C)을 채택할지 아직 모른다. A안(규제 RAG), B안(온보딩 문서)과 함께 10/2에 정한다. 주제 전환은 아직 결정 기록에 남지 않았다.

**확인이 안 된 사실**
- 권한 대기로 노는 일이 얼마나 자주, 얼마나 길게 생기는지 (현직자 추가 확인 필요)
- Codebase to Course를 같은 코드로 직접 돌려 본 비교
- 한국어 주석 코드에서도 잘 되는지 — 공개 평가셋이 전부 영어라서 따로 말한다
- 효과 계산에 필요한 숫자: 유휴 기간을 며칠 줄일지, 1년에 몇 명이 들어오는지, 하루 인건비가 얼마인지. 모두 **아직 없다**. ("자사가 협력사의 약 2배"라는 특강 발언만 있다.) 숫자는 지어내지 않고 계산 공식만 보여 준다.

**기술·평가 선택**
- 평가에 쓸 SWE-QA 저장소 1–2개
- 임베딩·AI 모델과 예상 비용
- AI 심판 모델과 채점 반복 횟수
- 연결 지도를 networkx로 충분히 할지, Neo4j가 필요할지
- SWE-QA 데이터에 질문 유형 표시가 있는지 — 없으면 팀원이 직접 분류해야 한다
- Spyder-CodeQA를 보조 지표로 쓸지 — AI로 만든 뒤 전문가가 검증한 문항이라, "평가셋을 AI로 지어내지 않는다"는 팀 원칙과 맞는지 팀 판단이 필요하다

**사람·역할**
- 파트 분담과 발표자 (원본에 4파트 제안이 있지만 확정 아님, 10/8–10에 정한다)
- 퀴즈 표본을 평가할 팀원 2명

## 용어 풀이

| 용어 | 쉬운 뜻 |
|---|---|
| LLM | 글을 읽고 쓰는 대형 AI 모델 (ChatGPT 같은 것) |
| RAG | AI가 답하기 전에 관련 자료를 먼저 찾아 읽고, 그 안에서 답하게 하는 방식. 시험을 오픈북으로 보는 것과 비슷하다 |
| 환각 | AI가 사실이 아닌 내용을 그럴듯하게 지어내는 것 |
| 파인튜닝 | AI를 추가로 공부시켜 지식을 머리에 넣는 방법 |
| 청크 | 검색하기 좋게 잘라 둔 코드 조각. 여기서는 함수·클래스 하나 |
| 임베딩 | 글이나 코드의 "뜻"을 숫자 목록으로 바꾼 것. 뜻이 비슷하면 숫자도 가깝다 |
| 벡터 검색 / 벡터 저장소 | 임베딩 숫자가 가까운 것을 찾는 검색 / 그 숫자를 모아 둔 곳 |
| BM25 (키워드 검색) | 질문에 들어간 단어·이름이 그대로 나오는 곳을 찾는 검색 |
| RRF | 두 검색 결과를 점수 대신 순위만 보고 합치는 방법 |
| 호출 그래프 | 함수끼리 누가 누구를 부르는지 그린 연결 지도 |
| 파일:줄 근거 | "이 설명은 어느 파일 몇째 줄에 있다"는 출처 표시 |
| 인용 검사 | 붙인 근거 줄이 실제 코드에 있는지 기계가 확인하는 것 |
| 기권 | 근거를 못 찾으면 추측하지 않고 "확인 필요"라고 답하는 것 |
| 평가셋 | 정답이 정해진 시험 문제 모음. 같은 문제로 고치기 전후 점수를 비교한다 |
| SWE-QA | 코드 저장소에 대한 질문을 모은 공개 평가셋 (질문 720개) |
| 재현율 | 찾아야 할 것 중 실제로 찾아낸 비율 |
| Streamlit | 파이썬만으로 간단한 웹 화면을 만드는 도구 |
