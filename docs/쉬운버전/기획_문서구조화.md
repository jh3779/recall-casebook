# 온보딩 문서 구조화 에이전트 — 쉬운 버전

> 자세한 근거와 수치 출처는 원본 [`../기획_문서구조화.md`](../기획_문서구조화.md)에 있다. 원본은 검토용 초안(2026-10-01)이고, 이 문서도 그 초안을 쉽게 풀어 쓴 것이다.

## 한눈에 보기

- **무엇을**: 여기저기 흩어진 회사 온보딩(신입 적응) 문서를 모아, 신입이 읽기 좋은 가이드 한 장으로 정리하는 AI 도구를 만든다.
- **누구를 위해**: 신입을 받는 팀 리드·사수(1차 대상 후보, 아직 확정 아님)와, 그 가이드를 읽는 신입·부서 이동자를 위해서다.
- **왜**: 같은 정보가 문서마다 다르게 적혀 있고 빠진 곳도 있어서, 신입은 무엇이 맞는지 모르고 사수는 같은 설명을 반복한다.
- **다른 후보와의 관계**: 이 문서는 `기획_온보딩.md`(B안)를 "사람이 읽기 좋은 구조화"로 좁혀 자세히 만든 파생안(B')이다. B안의 분석 결과를 다시 쓰고, B안 문서는 고치지 않았다. 이 주제로 갈지는 아직 정하지 않았다.

## 어떻게 동작하나

이 도구가 하는 "구조화"는 다섯 가지 동작뿐이다. 비유하면, 흩어진 메모를 주제별 서랍에 넣고, 겹치는 건 합치고, 서로 다른 건 나란히 붙여 두고, 빈 서랍엔 "누가 채워 주세요" 쪽지를 붙이는 일이다.

1. **모으기** — 흩어진 문서에서 같은 주제의 내용을 칸(주제)별로 모은다.
2. **층 나누기** — "회사 전체 공통" 내용과 "팀별" 내용을 두 층으로 나눈다.
3. **중복 합치기** — 같은 말을 하는 문장들은 대표 문장 하나로 합치고, 출처는 모두 남긴다.
4. **충돌 표시** — 값이 서로 다른 문장들은 무엇이 맞는지 **고르지 않고** 나란히 보여 준다(충돌 카드).
5. **빈칸 표시** — 내용이 없는 칸은 비워 두고, 담당자에게 물어볼 질문을 만든다.
6. **가이드 만들기** — 신입의 시간 순서(입사 전 → 첫날 → 첫 주 → 첫 달)로 칸을 배치한다. 모든 문장에 원문 출처를 단다.
7. **사람이 승인** — 담당자가 칸별로 확인·수정하고, 충돌과 빈칸 질문에 답한다.

이 도구는 사실을 고치거나 새로 쓰지 않는다. 원본 문서도 덮어쓰지 않는다.

## 1. 무엇이 문제인가

- 예시 데이터는 GitLab이라는 회사의 공개 핸드북(마크다운 문서 4,612개, 약 612만 단어)이다. 문서를 아주 잘 쓰는 회사인데도 온보딩 정보가 흩어져 있다.
- "onboarding"으로 찾으면 129건 중 61건(47%, 절반 가까이)이 입사와 상관없는 내용이다(고객 온보딩 등).
- 엔지니어링 팀 17개 중 9개는 팀 온보딩 페이지가 "이슈 템플릿을 열어라" 한 줄뿐이다.
- 같은 사실이 페이지마다 다르다. 예: 온보딩 이슈를 만드는 시점이 "4일 전" / "4 영업일 전" / "4~10 영업일 전"으로 세 가지다.
- 이 수치들은 다른 저장소의 분석 결과를 가져온 것이다. **이 저장소에는 다시 계산해 볼 스크립트가 없다.**

**문제 한 문장(초안)**: 신입을 받는 팀 리드가, 흩어지고 서로 다른 말을 하는 문서 때문에 정리된 가이드를 만들 수단이 없어, 같은 설명을 반복하고 문서끼리의 모순은 신입이 먼저 발견한다.

- 지금 현장에서 이 문제를 어떻게 때우고 있는지는 **아직 조사하지 않았다**(가설만 있다).
- **사용자 검증이 없다.** 실제 팀 리드·사수 인터뷰를 아직 하지 않았다. 10/8 전까지 1–2명에게 확인할 계획이다.

## 2. 비슷한 것은 이미 있나

- 공식 페이지를 열어 확인했지만, **제품을 직접 써 보지는 않았다.** 일부 기능은 광고 문구에만 근거한다.
- 다섯 동작 각각은 이미 따로 하는 도구가 있다. 중복은 Guru·Slite, 빈칸은 Document360·Tettra·Slite, 충돌 표시는 Alhena가 한다.
- 하지만 목차를 기준으로 문서를 다시 짜면서 충돌·빈칸·문장별 출처를 **한 번에** 내는 도구는 찾지 못했다. "없다"가 아니라 "못 찾았다"이다.
- 빈칸을 찾는 시점이 다르다. 기존 도구는 누가 물었는데 답을 못 했을 때 안다(사후). 이 안은 묻기 **전에** 목차와 비교해서 찾는다(사전).
- 위키백과 연구(CLAIRE)에서는 AI가 모순을 표시만 하고 사람이 판단하게 했더니, 같은 시간에 모순을 64.7% 더 찾았다. 이것이 "AI는 판정하지 않고 확인만 요청한다"는 설계의 근거다.
- 가장 비슷할 수 있는 것은 Slite의 Agent 기능이다. 무료 체험이 되면 10/6–7에 직접 비교할 계획이다.

## 3. 왜 이 기술이 필요한가

이 안이 쓰는 핵심 기술은 **RAG**(검색 증강 생성 — AI가 답하기 전에 관련 자료를 먼저 찾아 보고, 그 자료 안에서만 쓰게 하는 방식)다. 시험 볼 때 교과서를 펴 놓고 해당 쪽을 찾아 답을 쓰는 것과 비슷하다.

- **전체를 다 볼 수 없어서**: 핸드북 전체(약 612만 단어)는 **LLM**(대규모 언어 모델 — ChatGPT 같은 글 쓰는 AI)에 한 번에 넣을 수 없다. 그래서 칸마다 관련 문단만 찾아온다.
- **온보딩 문서 밖에도 정보가 있어서**: 온보딩 문서 68건만 보면, 다른 문서(예: PM 직무 문서)에 있는 온보딩 사실을 놓친다.
- **출처를 남기려고**: AI가 그냥 정리하면 그럴듯하게 지어낼 수 있다. 찾아온 문단 안에서만 쓰게 하고, 문장마다 출처를 단다. 출처가 없는 문장은 버린다.

솔직하게 남겨 둔 약점:
- B안의 약점은 "68건이면 AI에 다 들어가니 검색이 필요 없다"였다. 이 안은 "68건 **밖**에서 온보딩 사실이 얼마나 나오나"를 실험(v2)으로 직접 잰다. 거의 안 나오면 RAG를 쓰는 이유가 약해지고, 그 결과도 그대로 적는다.
- 충돌 찾기는 AI 판단이라 틀릴 수 있다. 그래서 판정이 아니라 "확인 요청"으로만 낸다.
- 출처를 검사해도 요약하면서 뜻이 바뀌는 경우는 남는다. 사람이 표본을 보고 비율을 잰다.

## 4. 무엇으로 만드나

**아직 아무것도 설치하지 않았다.** 아래는 모두 후보이고, 10/6–7 시제품(프로토타입)을 만들며 정한다.

- 데이터: GitLab 핸드북 스냅샷(특정 시점에 복사해 둔 것). 사용 허락(라이선스)은 아직 확인해야 한다.
- 문서 자르기: 마크다운 소제목 단위로 자른다. 그래야 출처(파일과 줄 번호)를 정확히 남길 수 있다.
- 검색: 뜻으로 찾기 + 단어로 찾기를 섞는다. "권한 요청" 같은 정확한 용어도 잡기 위해서다.
- 벡터 저장소: 로컬(Chroma 등) 또는 PostgreSQL + pgvector 중 하나. 시제품에서 정한다.
- AI 모델: OpenAI API. 어떤 모델을 쓸지는 아직 정하지 않았다.
- 화면: Streamlit(파이썬으로 간단한 웹 화면을 빨리 만드는 도구)

## 5. 전체 구조

0. **목차 정하기(사람)** — B안에서 만든 11칸을 일반 용어로 바꾸고, 2층·시간순으로 배치한다.
1. **색인** — 핸드북 전체를 소제목 단위로 나누고 위치(파일·줄)를 저장한다.
2. **칸 배정(AI)** — 온보딩 문서 68건의 각 부분을 칸에 넣는다. 확신이 낮으면 "미배정"으로 남긴다.
3. **추가 검색** — 칸마다 핸드북 전체에서 관련 문단을 더 찾는다.
4. **사실 추출(AI)** — 문단에서 "누가/무엇을/언제/조건" 단위의 사실 카드를 뽑는다. 원문에 없는 사실은 버린다.
5. **묶기·충돌** — 같은 주제 사실끼리 묶는다. 값이 같으면 합치고, 다르면 충돌 카드를 만든다. 애매하면 충돌 카드로 보낸다(놓치는 것보다 묻는 게 낫다).
6. **빈칸** — 사실이 하나도 없는 칸에 담당자 질문을 단다.
7. **가이드 작성(AI)** — 사실 카드만 써서 칸별로 요약하고 문장마다 출처를 단다.
8. **출처 검사(기계)** — 출처가 실제 원문에 있는지 확인한다. 없으면 한 번 다시 쓰고, 그래도 안 되면 그 문장을 지운다.
9. **승인(사람)** — 담당자가 확인하고 답한다.

꼭 지킬 약속:
- 근거 없는 문장은 쓰지 않는다.
- 충돌한 값 중 맞는 것을 고르지 않는다. 충돌 카드에는 "정답" 칸 자체를 만들지 않는다.
- GitLab에서는 구조(칸 목록)만 빌리고, 사실(금액·도구 이름·일정)은 다른 회사 가이드에 넣지 않는다.
- 가이드 문장 → 사실 카드 → 원문 줄로 거슬러 올라갈 수 있게 한다.
- 평가 정답은 사람이 표시한다. AI가 만든 정답으로 채점하지 않는다.

## 6. 지금까지 한 것과 앞으로 할 것

**지금까지 한 것** (B안 작업을 이어받음):
- "onboarding" 검색 129건(47%는 무관)을 하나씩 열어 분류해, 입사·팀 온보딩 문서 68건(11개 부서)을 골랐다.
- 빈칸 찾기 시범: Basecamp 문서 1건에서 11칸 중 8칸이 맞았다. 단, 정답을 AI가 시범으로 표시한 것이라 **공식 평가셋(채점용 정답 모음)이 아니다.**

**앞으로 할 것** — "읽기 좋다"는 정답이 없어서 네 층으로 나눠 잰다.
- A. 가이드 문장이 원문에 실제로 있는 말인가 (문장 30개를 사람이 확인)
- B. 원문의 중요한 사실이 빠지지 않았나 (팀원이 표시한 사실 30개와 비교)
- C. 칸 배정·충돌·빈칸이 맞나 (팀원이 만든 정답표와 비교. 충돌은 지금 1건만 찾았고, 목표는 10건 이상이다)
- D. 신입이 실제로 더 빨리·정확히 찾나 (교육 동기 6–10명이 원본과 가이드로 각각 문제를 풀어 본다. 인원이 적어 "경향"만 보고, 원자료를 그대로 공개한다. 참가자 모집이 안 되면 D층은 다음 단계로 미룬다)

버전별 계획(모두 **가설**이고 아직 측정 전이다):
- v0: 단어 규칙으로 칸 배정 → 기준선
- v1: AI가 뜻으로 칸 배정
- v2: 핸드북 전체 검색 추가 → **핵심 실험**. "왜 RAG인가"를 이 숫자가 답한다.
- v3: 충돌 찾기 추가
- v4: 출처 검사 추가
- 최종: 가이드 vs 원본으로 신입 과업 시험

비용: 유료 API를 쓴다. 금액은 모델이 정해지면 계산하고, 실행 전에 팀에 확인받는다. 전체를 돌리기 전에 68건만 먼저 돌려 본다.

## 7. 어려웠던 점

- **검색 결과가 섞였다** — "onboarding"으로 찾으면 고객 온보딩 등이 섞였다. 129건을 직접 열어 분류해 68건을 골랐다. 단어가 안 들어간 문서는 못 잡았고, v2 전체 검색이 메울 예정이다.
- **팀 문서에 계정·권한 내용이 거의 없었다(10~19%)** — 알고 보니 팀 문서는 이 내용을 회사 공통 문서에 맡기고 있었다. 그래서 목차를 2층으로 나누기로 했다.
- **다른 회사는 같은 칸을 다른 말로 불렀다** — 단어 규칙이 놓쳤다. 칸 이름을 일반 용어로 바꿨고, AI 배정이 나아지는지는 v1에서 잰다.
- **"공개"라던 자료가 실제로는 비공개였다** — 직접 접근해 확인했고, 그 체크리스트 본문은 범위에서 뺐다.
- (예상) 표현만 다른 같은 규칙을 충돌로 잘못 잡을 수 있다 → 판정 대신 "확인 요청"으로 낸다.
- (예상) 시험 참가자가 적어 결론이 흔들릴 수 있다 → 문항별 원자료를 공개한다.

꿰는 한 문장(초안): 검색 결과도, 문서의 자기소개도 그대로 믿지 않고 — 직접 열어 보고, 숫자로 확인하고, 다른 회사 문서로 시험한다.

## 하지 않기로 한 것

- 충돌한 값 중 무엇이 맞는지 고르지 않는다(의도적). 나란히 보여 주고 담당자에게 묻는다.
- 원본 문서를 고치거나 자동으로 게시하지 않는다(의도적). 원본의 주인은 각 팀이다.
- GitLab의 **내용**을 다른 회사로 옮기지 않는다(의도적). "장비 지원금 1,500달러" 같은 사실은 다른 회사에선 틀린 답이다.
- 빈칸에 대한 질문만 만든다. 답을 받아 채우는 것은 사람이 한다.
- 온보딩 외의 사내 문서 전체는 이번 범위 밖이다.
- AI(RAG)가 읽기 좋은 형태로 내보내는 것도 이번 범위 밖이다. 확장할 수 있다고만 말한다.
- 핸드북 밖 자료(비공개 템플릿, Google Docs, 슬라이드)는 접근할 수 없어 못 한다. "원문 접근 불가"로 따로 표시한다.
- 옛 규칙이 남아 생긴 충돌도 충돌로 잡힌다. 원인(갱신 누락인지)은 구분하지 않는다.

## 아직 정해지지 않은 것

- 이 주제를 채택할지 (A 규제 RAG / B 온보딩 문서 / B' 이 안 / C 코드 온보딩)
- B안과의 관계: B안을 대체할지, B안에 합칠지, 별도 후보로 둘지
- 1차 대상: 팀 리드·사수 / 인사 담당자 / 신입 본인
- 1차 대상 인터뷰 1–2명 (아직 안 함)
- 참조 목차(11칸, 2층, 시간순) 확정
- GitLab 핸드북 라이선스 (데이터 사용·발표 인용 범위)
- 과업 시험 참가자(교육 동기 6–10명) 모집·동의
- 임베딩·LLM·벡터 저장소 선택과 예상 비용
- Slite Agent 직접 비교
- 현재 현장에서 문제를 어떻게 때우는지 조사
- 파트 분담(4개 파트 제안)은 확정이 아니다.
- 발표용 수치(68건 밖에서 더 찾은 사실 수, 과업 시험 결과)는 실험 후에 채운다. 임팩트 계산에 필요한 세 값(신입의 시간 단축, 연간 신입 수, 사수의 설명 시간 단축)도 아직 없다.

## 용어 풀이

| 용어 | 쉬운 뜻 |
|---|---|
| 온보딩 | 새로 들어온 사람이 회사·팀에 적응하도록 돕는 과정 |
| 구조화 | 흩어진 내용을 정해진 칸과 순서에 맞춰 정리하는 것 (이 문서에선 다섯 동작) |
| 칸(슬롯) | 가이드의 주제 칸. 예: "입사 전 준비" |
| 참조 목차 | 무엇이 빠졌는지 판단하는 기준이 되는 칸 목록 |
| 충돌 카드 | 같은 주제인데 값이 다른 문장들을 나란히 모아 둔 카드. 정답은 고르지 않는다 |
| 사실 카드 | 원문에서 뽑은 사실 하나와 그 출처를 함께 적은 기록 |
| LLM | 대규모 언어 모델. ChatGPT처럼 글을 읽고 쓰는 AI |
| RAG | AI가 답하기 전에 관련 자료를 찾아 보고, 그 안에서만 쓰게 하는 방식 |
| 청크(청킹) | 긴 문서를 검색하기 좋게 작은 조각으로 자른 것 (이 안은 소제목 단위) |
| 임베딩 | 글의 뜻을 숫자 목록으로 바꾼 것. 뜻이 비슷한 글을 찾을 때 쓴다 |
| 벡터 저장소 | 임베딩을 저장해 두고 비슷한 것을 빨리 찾는 창고 |
| 평가셋(정답표) | 결과를 채점하려고 사람이 미리 만들어 둔 정답 모음 |
| 재현율 / 정밀도 | 찾아야 할 것 중 몇 개를 찾았나 / 찾은 것 중 몇 개가 맞았나 |
| 과업 시험 | 사람에게 실제 문제를 풀게 하고 정답률·시간을 재는 시험 |
| 스냅샷 | 특정 시점에 복사해 둔 자료. 나중에 같은 자료로 다시 확인할 수 있다 |
