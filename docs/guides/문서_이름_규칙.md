# 문서 이름 규칙

> `docs/`에 문서를 만들거나 이름을 바꿀 때 따르는 규칙이다. 폴더 구조의 이유는 DEC-083, 문서 목록은 [`../README.md`](../README.md)다. 브랜치·커밋·PR 이름은 [`CONTRIBUTING.md`](../../CONTRIBUTING.md)가 정한다(여기서 다루지 않는다).
> 이 규칙은 2026-10-21 시점의 이름을 정리해 만들었다. 기존 문서 중 규칙과 다른 것은 5절에 이유와 함께 적었다.

## 1. 어느 폴더에 두나

위에서부터 먼저 맞는 것을 고른다.

| 질문 | 폴더 |
|---|---|
| 끝난 작업이거나 이전 주제의 기록인가? | `archive/` — 현행 판단의 근거로 쓰지 않는다 |
| 화면 규칙(토큰·컴포넌트·문구)인가? | `design-system/` |
| 표시자(사람)에게 나눠 주는 작업 안내서인가? | `labeling/` |
| 숫자 근거가 있는 실험·검증·관찰 기록인가? (평가가 아닌 관찰이면 문서 첫 줄에 "평가 아님"을 적는다) | `experiments/` |
| "어떻게 하는가"(설치·환경·명령·병합·배포)인가? | `guides/` |
| 프로젝트 진행·역할·시나리오 같은 기록인가? | `project/` |
| "무엇을, 왜 만드는가"(제품 요구·기획·계획·데이터 구조)인가? | `product/` |

- 폴더는 `docs/` 바로 아래 한 단계만 쓴다. 하위 폴더는 `design-system/`처럼 문서 묶음이 이미 있을 때만 둔다.
- 폴더 이름은 **영문 소문자**(하이픈 허용)다. 새 폴더는 `docs/README.md`의 "폴더 구조" 표에 한 줄을 더하고 DEC에 이유를 남긴다.
- 그림은 `images/`에 둔다.

## 2. 파일 이름 형식

```text
<접두어>_<주제>.md          예) 실험_P5_희소부품층화.md, 계획_케이스북.md
<주제>.md                   예) 시작하기.md, 개발환경.md
<영문 약어>.md              예) PRD.md, ERD.md, MERGE_PROTOCOL.md
```

1. **확장자는 `.md`(소문자)** 만 쓴다. 문서 안에 넣을 파일은 `images/`나 해당 폴더의 전용 위치에 둔다.
2. **단어는 밑줄(`_`)로 잇는다.** 공백·하이픈·괄호·점·쉼표·따옴표·이모지는 쓰지 않는다. 한 단어 안은 붙여 쓴다(`개발환경`, `환경셋팅`).
3. **한글 이름을 기본**으로 한다. 영문은 고유명사·표준 약어일 때만 쓴다 — `PRD`·`ERD`·`WBS`처럼 **대문자 약어**, `Vercel`·`LLM`처럼 **고유명사는 원래 표기**, `git`·`uv`처럼 도구 이름은 **소문자 그대로**. 영문 약어 문서(`PRD.md`, `MERGE_PROTOCOL.md`)는 대문자와 밑줄(`UPPER_SNAKE`)로 쓴다.
4. **길이는 한글 15자 안팎**으로 한다. 길어지면 주제를 줄이고 설명은 문서 첫 줄에 쓴다.
5. **날짜·판본·상태를 이름에 넣지 않는다.** `_2026-10-21`, `_v2`, `_초안`, `_최종`, `_수정본`, `_복사본` 금지 — 날짜는 문서 머리말에, 판본·상태는 git 이력과 PR에 둔다. (작업 중인 글은 브랜치에서 쓰고, 저장소 밖 초안 파일 이름은 이 규칙 밖이다.)
6. **사람 이름·팀 이름·내부 별명을 넣지 않는다.** 예외는 팀이 정한 파트 이름(`D파트_…`)뿐이다.
7. 폴더마다 안내가 필요하면 `README.md`(영문 대문자)를 둔다. 폴더 안 문서 목록은 `docs/README.md`가 갖고 있으므로 일반 폴더에는 따로 두지 않는다.

## 3. 접두어

접두어는 문서의 **성격**을 보여 주고, 같은 접두어끼리 목록에서 모인다. 새 성격이 필요하면 이 표에 한 줄을 더하고 쓴다.

| 접두어 | 성격 | 폴더 | 예 |
|---|---|---|---|
| `기획_` | 현행 기획서(주제 전환 때만 새로 쓴다) | `product/` | `기획_결함선례.md` |
| `계획_` | 구현·시험 계획서(하기 전에 쓴다) | `product/` | `계획_케이스북.md`, `계획_P3_리랭커시험.md` |
| `실험_` | 실험·검증 보고서(한 뒤에 쓴다) | `experiments/` | `실험_P5_희소부품층화.md` |
| `프런트_` | 화면 구현 검증·모델 표면 기록 | `experiments/` | `프런트_구현_검증.md` |
| `D파트_` | D 파트 표시자용 안내(파트 이름) | `labeling/` | `D파트_표시_안내.md` |
| (없음) | 한 주제를 설명하는 안내·가이드 | `guides/` 등 | `시작하기.md`, `배포_Vercel.md` |
| `WBS_` 등 영문 약어 | 업계 표준 약어로 부르는 문서 | `project/` | `WBS_역할분배_시간예산.md` |

- **`실험_` 번호**: 번호가 있는 실험은 `실험_P<번호>_<주제>.md`로 쓴다. 이 `P` 번호는 **실험 보고서끼리** 겹치지 않게 쓰고 보고서·DEC에서 부르는 이름과 같아야 한다. 새 실험은 이미 쓴 번호 다음(P6, …)을 잇는다. `.agent/PROJECT_CONTEXT.md`의 프로젝트 단계 P0~P4와는 **별개의 번호**다(실험 P4 = 임베딩 비교, 단계 P4 = 발표 준비) — 다만 기존 `실험_P2`·`계획_P2_API서버`·`계획_P3`은 단계 번호를 따라 지은 이름이라 예외로 둔다. 같은 실험의 보완(예: P4b)은 새 파일이 아니라 같은 문서의 절로 쓴다. 번호 없는 보조 실험은 `실험_<주제>.md`다.
- **`계획_`과 `실험_`은 역할이 다르다.** 계획서가 하기 전의 범위·사전 고정 규칙을, 실험 보고서가 결과를 담는다. 별도 계획서는 선택이지만 **"사전 고정"은 실행 전에 남긴 기록(커밋·이슈·PR 코멘트 중 하나)이 있을 때만** 쓸 수 있다 — 입력·지표·구간·판단 기준을 그 기록에 적고 보고서가 링크한다. 결과와 같은 커밋에 처음 쓴 규칙은 "사전 고정"이라 부르지 않는다(AGENTS.md 5-1·5-3). 이 조건을 증명할 기록이 없는 과거 실험(P5)은 일반 예외가 아니라 "사전 고정 여부를 독립 검증할 수 없는 실험"으로만 표시하고, **다음 실험부터 계획·사전 고정 기록을 먼저 커밋한다.** 짝이 있으면 서로 링크한다.
- **`기획_`은 하나만 현행이다.** 이전 기획서는 `archive/`로 옮긴다(이름은 그대로 두고 `archive/README.md` 표에 옛 경로를 적는다).

## 4. 문서 안의 이름과 링크

1. **첫 줄 제목(`# …`)은 파일 이름의 뜻과 같게** 쓴다. 밑줄은 공백으로, 접두어는 `실험 P5 — …`처럼 읽히게 풀 수 있다.
2. **링크는 상대 경로**로 쓴다(`../experiments/실험_P5_희소부품층화.md`). 절대 경로와 GitHub 주소(`blob/main/...`)는 쓰지 않는다 — 깨진 마크다운 링크는 `pr_checks`의 md-links가 잡는다. **백틱으로 적은 경로(`docs/…`)와 와일드카드 경로는 잡지 못하므로** 이름을 바꿀 때 `git grep`으로 옛 경로를 찾는다.
3. 코드 주석이나 규칙 문서가 문서를 가리킬 때는 **저장소 루트 기준 경로**(`docs/experiments/실험_P5_희소부품층화.md`)로 쓴다.
4. 새 문서는 **같은 PR에서 `docs/README.md`의 해당 폴더 표에 한 줄**을 더한다(내용 한 줄 요약 + 근거가 된 DEC 번호).

## 5. 규칙과 다른 기존 이름 (이유)

| 파일 | 규칙과 다른 점 | 이유 |
|---|---|---|
| `guides/git_명령어.md` | 소문자 영문 접두 | 도구 이름(`git`)은 소문자 그대로 쓴다(2절 3항) |
| `guides/MERGE_PROTOCOL.md` | 한글이 아닌 `UPPER_SNAKE` | 규칙 문서·스킬·CI 주석이 이 이름으로 부른다(2절 3항, 영문 약어형 문서) |
| `labeling/D파트_표시_안내_원인미확인.md` | 접두어 뒤 세부가 길다 | 같은 `D파트_표시_안내` 묶음의 변형이라 이름을 맞췄다 |
| `product/데이터_중복_처리_패턴.md` | 접두어 없음 | 계획·실험이 아닌 개념 설명(DEC-034) |
| `archive/기획v1.md` 등 | 판본(`v1`)이 이름에 있다 | 보관 문서는 옛 이름을 유지한다(`git log --follow`로 이력이 이어짐) |
| `archive/쉬운버전/` | 한글 폴더 이름 | 보관 폴더라 옛 이름을 유지한다 |
| `design-system/` 안 | 영문 소문자 하이픈 | 디자인 시스템은 코드·토큰 이름과 맞추기 위해 영문 `kebab-case`를 쓴다(`open-questions.md`, `tokens/colors.md`) |

이 표의 파일은 **이름을 바꿀 때 한꺼번에**(아래 6절) 고친다. 규칙을 어기는 새 이름을 이 표에 더하지 않는다.

## 6. 이름을 바꾸거나 문서를 옮길 때

1. `git mv`로 옮긴다(이력이 이어진다). 파일을 지우고 새로 만들지 않는다.
2. 문서 사이의 상대 링크와 코드·규칙 문서의 `docs/…` 경로(와일드카드 `docs/계획_*` 같은 것 포함)를 함께 고친다 — 한 번에 많이 옮길 때는 DEC-083처럼 일회용 변환 스크립트와 깨진 링크 전수 검사를 쓰고(스크립트는 저장소에 남기지 않았다), 끝에 `git grep`으로 옛 경로 잔존을 확인한다.
3. **결정·세션 기록(`.agent/DECISIONS.md`, `SESSION_LOG.md`)의 옛 경로는 고치지 않는다**(깨진 상대 링크만 새 경로로 고친다 — DEC-083 ③). 대신 `docs/README.md`의 "옛 경로 → 새 경로" 표에 한 줄을 더한다.
4. 이슈·PR 코멘트·외부 문서에 적힌 옛 경로는 바꿀 수 없으므로, 이름 변경 PR 본문에 옛 → 새 경로를 적는다.
5. 되돌리기 어려운 이름 규칙(접두어 추가·폴더 추가)은 `.agent/DECISIONS.md`에 DEC로 남긴다.

## 7. 체크리스트 (새 문서를 만들 때)

- [ ] 1절 순서로 폴더를 골랐다
- [ ] `<접두어>_<주제>.md` 또는 `<주제>.md`이고 밑줄·한글·대문자 약어만 쓴다(날짜·판본·상태 없음)
- [ ] 접두어가 3절 표에 있다(없으면 표에 한 줄 추가)
- [ ] 첫 줄 제목이 파일 이름의 뜻과 같다
- [ ] 상대 링크가 깨지지 않는다(`scripts/ci/pr_checks.py`의 md-links)
- [ ] `docs/README.md`에 한 줄을 더했다
