## 1. 한 줄과 배경

한국 부품사에서 북미 수출 차종을 맡은 품질·제품안전 엔지니어가 원인 모를 결함 신고를 받았을 때, 미국 정부(NHTSA) 공개 리콜·결함 조사에서 **같은 부품의 다른 회사 선례와 그 원인 서술을 원문 그대로** 찾아 주는 RAG 서비스다(DEC-030).

- **왜 급한가**: 미국 규정(49 CFR 573.6)은 안전 결함으로 판단되면 5영업일 안에 보고하라고 한다. 판단 시점은 "알았어야 했던 때"로 따져질 수 있고(기획서 1절), 엔지니어는 이 안에 **같은 부품의 과거 결함과 그 원인**이라는 근거를 모아야 한다.
- **지금의 한계**: 키워드 검색(NHTSA 사이트)은 표현이 다른 같은 결함을 놓치고, 원인은 리콜 요약이 아니라 Part 573 원본 보고서에 흩어져 있어 사람이 하나씩 열어야 한다(기획서 3절).
- **왜 다른 회사 데이터인가**: 같은 부품 분류에서 자기 회사 선례는 중앙값 1건, 다른 회사는 104건이고 자기 회사 선례가 0건인 질문이 약 40%다(기획서 2절, 749쌍 기준). 그래서 **검색은 전체 공개 리콜, 고객사(현대·기아) 선례는 화면에서 먼저** 보여 준다.

### 비목표 (하지 않는다 ❌)

- **판정**: "리콜해야 한다", "원인은 이것이다"를 말하지 않는다. 응답 스키마에 판정 필드가 없다(AGENTS.md 2-1).
- **한국어·현장 말투 질문**: 북미 담당 엔지니어는 NHTSA·고객사 문서를 영어로 다룬다는 가정이다(DEC-030, 3판).
- **회사 내부 데이터**(보증·사내 이력): 비공개라 범위 밖이다. 사내 이력 검색은 SAS 같은 기존 도구의 영역이다.
- **2014-08-20 이전 리콜의 원인 추출**: 원본이 정형 양식 이전의 자유 형식 서신이고 스캔본이 섞여 있어 OCR이 필요할 수 있다. 지어내지 않고 573 원문 수집 범위 밖이라 `no_573_report`로 표시하며, 원인 칸이 있는지 없는지는 판단하지 않는다(`cause_no_field`는 보고서를 읽고 칸이 없음을 확인한 경우로 구분).
- **공개 서비스 경로의 LLM 사용**: 원인 문장은 LLM 없이 원문을 그대로 붙인다(DEC-039 ③). LLM은 연구 시험과 8D 초안 보조 시험 구현(기본 꺼짐)에만 쓴다.
- **부품 분류 카드를 순위에 더하는 부스트**: 749문항 시험에서 기준 폭(0.03)에 못 미쳐 기각했다(DEC-045). 부품 분류로 거르기·하위 분류는 이 실험으로 판단하지 않았다.

## 3. 사용자와 시나리오

**사용자**: 한국 자동차 부품사에서 북미 수출 차종(현대·기아·제네시스 등 납품)을 맡은 품질·제품안전 엔지니어. 영어 문서를 읽을 수 있다.

**핵심 시나리오**

1. 미국 법인에서 "조향 보조가 갑자기 사라진다"는 신고 6건이 온다. 무엇이 고장 났는지는 알지만 **왜**인지는 모른다.
2. 영어로 결함 한 줄을 넣는다(예: `loss of power steering assist electric motor driven steering`).
3. 고객사(현대·기아) 선례가 먼저, 다른 회사 선례가 이어서 나온다. 카드를 열면 제조사가 573 보고서 원인 칸에 쓴 문장이 **원문 그대로**, 말한 주체·리콜 번호·출처와 함께 보인다. 확인 항목(같은 부품 · 생산 기간 · 고장 양상 · 시정 · 공급사 · 원인을 말한 주체)이 원문으로 붙는다.
4. 엔지니어가 우리 건과 같은지 **직접 판단**하고 리콜 범위·보고 판단의 근거로 쓴다. 도구는 판단하지 않는다.
5. (🟡 파이프라인 5단계) 쓸 선례를 담아 8D 작성 화면으로 넘어가, 자기 8D 파일의 문제 기술·원인 칸 끝에 원문을 참고로 덧붙인다.

## 5. 평가와 성공 지표

원칙: **같은 평가셋의 before/after 숫자로만 결정**하고, 차이가 0.03보다 작으면 같다고 본다(AGENTS.md 5절). 평가 정답은 정부 기록이며 AI로 지어내지 않는다.

| 지표 | 기준 | 현재 | 상태 |
|---|---|---|---|
| 대리 평가 Hit@10 (749문항: 조사 요약 첫 문장 → 그 조사에서 나온 리콜) | BM25 0.510 | BM25 + 뜻 검색 RRF **0.542**(회사 이름 뺀 질문 0.531) | ✅ 잠정(⚠ 재현 전 수치 포함) |
| 시점 평가 (질문 기준일 이전 리콜만 색인, 사람이 정답 표시) | 정답 있는 문항 ≥ 34개일 때만 성능 주장. 대리 평가와 **합치지 않고** 따로 보고 | 표시 마감 10/16, 채점·보고 10/17 | 🟡 결과 대기 — 34개 미만이면 발표에서 "미측정" |
| 원인 품질 (573 원인 칸 30건, 사람이 표시) | 원인을 말하는 글의 비율 | 표시 완료, 채점 전 | 🟡 |
| 원문 일치 | 원인 문장의 글자 대조 | 통과한 것만 표시(구조로 보장) | ✅ |
| 실무자 확인 | 실제 엔지니어 1명 이상 | 범위에서 제외(DEC-055) | ⬜ 다음 단계 |

주의: 대리 평가는 "결함 설명 → 해당 리콜을 잇는가"를 재는 것이고, 정답 리콜의 99.6%가 조사 시작 뒤에 접수돼 "과거 선례를 찾는가"는 재지 못한다(기획서 6절). 749문항은 방법끼리 비교하는 용도이고 정확도의 절대 수치로 주장하지 않는다.

## 6. 파이프라인 5단계 — 근거를 서류로: 8D 작성 보조 (🟡 시험 구현 — main 병합, 공개 서버에는 꺼짐)

**집중 범위(DEC-067, 2026-10-16)**: 8D 작성 보조는 당분간 **D4(원인)에 집중**한다. 케이스북 화면에서 선례를 체크하면 원인 원문이 근거로 쌓이고, D4 작성 구역(DEC-069 구현에서는 화면 아래 전체 폭)에 ① 선례 근거(읽기 전용, 말한 주체·출처 포함) ② **선례별 메모**(엔지니어 개인 메모, 브라우저 안에만) ③ 확인 질문(도구가 만든 고정 문장) ④ 엔지니어 작성 칸(유출 원인·근본 원인·검증 방법 — 서비스는 채우지 않는다) ⑤ 출력(`.docx` D4 칸에는 엔지니어 글, 8D 표 뒤 부록에는 타사 원문)이 놓인다. 출처는 **선례를 안내하는 화면에는 항상** 보이고, 엔지니어가 쓰는 D4 칸의 글에는 강제하지 않는다. 부록의 타사 원문에는 DEC-064 ③의 머리줄·꼬리줄(출처 파일·sha256 포함)이 그대로 붙는다(AGENTS.md 2-2·2-4). 필드별 출처(원인·생산 기간·공급사=573 판본, 결함·결과·시정=`FLAT_RCL`)는 DEC-067 결정 ⑧. 선례 체크·상세·선례별 메모·원인 묶기는 **구현**(PR-B, DEC-068), D4 작성 칸·확인 질문·`.docx` 출력도 **구현**(PR-C, DEC-069 — 부록은 기본 꺼짐, 검증 방법은 입력만)이다. LLM은 묶기와 확인 질문 번호 고르기까지만 하고(기본 확인 질문은 코드 규칙이 고정 문장에서 붙이고, 추가 질문은 LLM이 고정 풀에서 번호만 고른다 — DEC-071) 자사 원인 후보는 제안하지 않는다. D2·D3·D5·D7은 지금 있는 것만 두고 확장하지 않는다. 아래 내용 중 8D 전 단계를 다루는 줄(#139 계획·#140 대시보드)은 이 집중 범위 밖이다(처리는 HANDOFF Next Action 7의 사용자 결정).

**위치**: 이 서비스의 RAG 파이프라인은 **① 준비(색인) → ② 찾기 → ③ 원인 원문 붙이기 → ④ 검사·표시 → ⑤ 8D 작성 보조**다. ①~④는 공개 운영 중이고 LLM이 없다. ⑤는 같은 근거를 사용자의 8D 서류로 옮기는 단계이며 시험 구현이다(PR #141, DEC-064·065 — `main`에 병합됨).

**AI를 쓰는 범위**: ⑤에서도 AI는 정해진 일만 한다. LLM이 쓴 문장은 원문 글자 대조 밖에 있어 판정 금지·원문 보존 원칙(AGENTS.md 2-1·2-2)을 구조로 지킬 수 없다 — 원인 추출 30건 시험에서도 LLM이 글자를 바꾸고 실행마다 결과가 달랐다([`실험_P2_검색방식비교.md`](실험_P2_검색방식비교.md) 5절). 그래서 검색 화면에는 LLM 문장을 넣지 않고(DEC-039 ③), ⑤에서는 아래로 제한한다.

- **AI가 하는 일** ① 담은 선례의 원문을 비슷한 것끼리 묶는다(묶음 제목은 서버 내부용이라 화면·서류에 내지 않는다) ② 인용은 LLM 문자열이 아니라 서버가 출처 원문에서 잘라 낸 글자만 싣는다(출처 전체 원문, 원문에 없으면 버린다) ③ 자사의 원인·조치는 쓰지 않는다 ④ 확인 질문 문장은 LLM이 쓰지 않는다 — 기본 문장은 코드 규칙이 붙이고, 추가 질문은 LLM이 고정 풀(10개)에서 **번호만** 고른다(사용자 결정 2026-10-17, DEC-071; 풀 밖 번호는 버림).
- 이 단계는 결함 선례 찾기를 버리는 주제 전환이 아니라 **활용 범위 확장**이기도 하다(PR #139의 `docs/계획_8D작성보조에이전트.md`, DEC-063 — 아직 병합 전).
- **과장하지 않는다**: 시험 구현이고 공개 서버에는 없다. 묶음 품질은 정확도를 재지 않았다(사람이 읽는 몫). 실제 고객사 양식은 확인하지 못했다. "5단계를 끝냈다"가 아니라 "이 범위로 구현했고 평가는 남았다"이다.

**알려진 긴장**: ① 원인 원문이 D4 칸에 들어가면 타사 원인이 이 건의 근본 원인과 섞여 읽힐 수 있다 — DEC-064 ④는 D4를 부록으로만 분리했으나 DEC-076(2026-10-18, 사용자 결정)이 D4 본문에도 넣게 바꿨다. 섞여 읽히지 않도록 본문에서는 엔지니어 글 뒤에 "타사 공개 원문과 도구 안내문이며 자사 사실이 아닙니다" 제목과 각 인용의 머리줄·출처 줄을 항상 붙이고 기본은 꺼짐이다. 선례 내용은 D4에만 넣고 나머지 단계는 채우지 않는다. ② 평문으로 들어간 인용은 사용자가 고칠 수 있어 "한 글자도 바꾸지 않음"은 서비스가 보여 주는 단계까지만 보장한다. ③ 본문 삽입과 .docx 지원을 서비스 기본으로 삼을지는 합의 전이다(DEC-064 ⑥).
