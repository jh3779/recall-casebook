# 온보딩 체크리스트 RAG — 프로젝트 전체 기획 뼈대

> 프로젝트 **전체**의 뼈대다. 파트(도메인)별 기획은 이 뼈대 아래에 따로 둔다.
> 2026-10-02 회의 결론: **각 파트가 자기 도메인의 최소 DB + RAG PoC를 만들고, 그 결과를 보고 전체 방향을 확립한다.**
> 그래서 이 문서는 **확정된 것만 채우고**, 나머지는 "미정"으로 남긴다. 전체 큰 틀은 PoC 뒤 논의해서 쓴다.
>
> 틀은 [`기획.md`](기획.md)의 7단계 순서를 따른다 (순서 자체가 발표 목차다).
> 근거 없이 채운 칸은 발표장에서 바로 질문이 들어온다 — 모르면 "아직 없음"이라고 적는다.

## 2. 유사 서비스 조사 · 차별점

> 추측하지 말고 실제로 찾는다. 못 찾았으면 "못 찾았다"고 쓴다 — "경쟁자 없음"과 다르다.

| 이미 흔한 것 | 예시 (출처) |
|---|---|
| 출처를 붙인 사내 문서 Q&A | [Glean](https://www.glean.com/solutions/people), [Moveworks](https://www.moveworks.com/us/en/solutions/employee-onboarding) |
| 문서 최신성 관리(검증 주기) | [Guru Verification](https://www.getguru.com/features/verification), [Glean Verification](https://docs.glean.com/user-guide/knowledge/verification/how-verification-works) |
| 문서 간 충돌·중복 탐지 | [Guru](https://www.getguru.com/solutions/agentic-knowledge-base), [Leena AI](https://leena.ai/knowledge-management) |
| 버전·시점을 다루는 RAG 연구 | [VersionRAG](https://arxiv.org/abs/2510.08109), [HoH](https://arxiv.org/abs/2503.04800) |
| 엔터프라이즈 RAG 평가셋 | [EnterpriseRAG-Bench](https://arxiv.org/abs/2605.05253) — 합성 데이터 |

| 찾지 못한 것 | 근거 |
|---|---|
| 답변에 **문서 변경 이력(git)** 을 근거로 붙이는 온보딩 RAG | 위 상용 서비스는 충돌·최신성은 다루지만 변경 이력은 쓰지 않았다. 오래된 문서가 답을 뒤집는 문제는 [Stale-Document Poisoning](https://arxiv.org/abs/2609.31342)에 보고됨 |

- 특수성(차별점) 확정: ⬜ 미정 — 위는 후보 조사 결과일 뿐이다.

## 5. 아키텍처 · 워크플로우 설계

### 큰 그림 (목표 형태, 미확정)

```text
[질문 (영어)]
     │
     ▼
(나중) 라우팅 ── 어느 도메인이 답할지 고른다          ⬜
     │
     ▼
도메인별 RAG  ── 인사 / 엔지니어링 / 전사 / 영업·지원  (각 파트 PoC)
     │            공용 문서를 어디서 처리할지          ⬜
     ▼
[체크리스트 출력] item · reason · source · domain
```

### PoC 공통 기준 — 네 파트가 지킬 최소 단위

파트마다 RAG 구조는 자유롭게 고르되, **나중에 합칠 수 있도록** 아래만 맞춘다. (🟡 제안 — 팀 합의 필요)

| 항목 | 최소 기준 |
|---|---|
| 코퍼스 | 자기 도메인 핸드북 폴더의 영어 원문. 문서마다 **경로 + 스냅샷 커밋 SHA**를 기록한다 (추적성) |
| 최소 DB | 공용 참조 테이블 스키마 하나: `doc_id, domain, source_path, commit_sha, heading_path, chunk_text, embedding`. 컬럼만 합의하고 구현은 파트별로 한다 |
| RAG 구조 기록 | 청킹 · 임베딩 · 검색 · 리랭크 선택과 **"왜 이 도메인에 최적인가"** 를 4절 표 형식으로 남긴다 |
| 출력 | 체크리스트 공통 필드 `item, reason, source(path#heading), domain`. 항목 내용은 도메인마다 다르다 |
| 평가 | 영어 질문 + **사람이 표시한** 정답 문서·섹션 (AI로 지어내지 않는다, [AGENTS.md](../AGENTS.md) 5-2). 지표 **Recall@k, Hit@k** (k = 1, 3, 5, 10). 차이가 0.03 미만이면 같다고 본다 (AGENTS.md 5-3) |
| 산출물 | 파트 PoC = 이슈 1개 · PR 1개, 기준선 수치 1개 |

### 합칠 때 논의할 질문 (답은 모두 ⬜)

1. 벡터 DB를 도메인별로 나누나, 하나에 `domain` 컬럼으로 두나?
2. 공용 문서는 어디에 두나? (공용 문서도 결국 어느 도메인에 속하지 않나?)
3. 여러 도메인에 걸친 질문은 어느 도메인이 답하나? (라우팅)
4. 계층(회사 단계 / 부서 단계)을 언제 나누나? 나누는 방식에 따라 연산량이 달라진다.
5. 규칙을 통일할 것인가, 도메인별로 최적화할 것인가? 그 근거는 무엇인가?
