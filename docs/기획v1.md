# 온보딩 체크리스트 RAG — 기획 v1

## 1. 문제 정의

### 문제 배경

GitLab의 신규 입사자, 부서 이동자가 같이 새로운 업무 배정을 받았을때에 업무를 익힐 수 있도록 온보딩 하는 RAG 서비스이다.

실제 GitLab 회사의 사내 문서를 활용하였다.
이 사내 문서는 MD형태로 버전별로 분기가 관리되면서 업로드 되는 특징이 있다

### 문제 정의

> ⚠️ 아래 8개 중 5번만 핸드북 원문 근거가 있다. 나머지 7개는 **가설**이다 — 실제 신규 입사자·부서 이동자 사례(인터뷰, 사내 FAQ, 온보딩 관련 이슈 등)로 검증하기 전까지는 평가셋의 정답 근거로 쓰지 않는다 (AGENTS.md 5절 "평가셋을 AI로 지어내지 않는다"와 직결).

신규 입사자

1. (가설) 뭘 먼저 봐야 할지 모른다 — 전사 공통 자료와 부서 자료가 섞여 있고, 우선순위 안내가 없다.
2. (가설) 내 직무에 맞는 체크리스트인지 확신이 없다 — 핸드북이 직무별로 명확히 분리돼 있지 않아 읽어야 할 범위를 스스로 판단해야 한다.
3. (가설) 용어·약어·조직 구조가 생소하다 — 사내 맥락을 전제한 문서라 신규 입사자 기준으로 풀어 쓰여 있지 않다.
4. (가설) 문서가 최신인지 믿을 수가 없다 — 핸드북이 자주 갱신되는데 버전·시점 정보가 본문에 안 드러난다.

부서 이동자

5. **(근거 있음)** 뭘 "다시" 해야 하는지 구분이 안 된다 — 전사 온보딩은 이미 끝났는데, 새 자료가 처음부터 다시인지 직무 전환분만인지 불명확하다. (근거: `people-group/promotions-transfers.md:701` — 직무 전환 시 새 직무 온보딩 완료 요구)
6. (가설) 이전 부서 지식과 새 부서 지식이 어떻게 겹치는지 모른다 — 부서 간 공통·차이 항목이 문서상 매핑돼 있지 않다.
7. (가설) "이미 아는 척" 할 위험과 "모르는 척" 비효율 사이에서 헤맨다 — 체크리스트가 숙련도 구분 없이 동일하게 제공된다.

공통

8. (가설) 왜 이 항목이 필요한지(근거) 설명이 없다 — 체크리스트성 자료가 "할 일"만 나열하고, 사유·출처 연결이 약하다.


## 2. RAG가 필수적인 이유

9. 핸드북이 수시로 갱신된다 — 문서가 바뀔 때마다 그 내용이 지연 없이 답변에 반영되어야 한다. RAG는 검색 대상 문서만 갈아끼우면 바로 반영된다.
10. 답마다 근거(출처)를 보여줘야 한다 — 체크리스트 항목이 왜 필요한지 문서 경로·섹션까지 추적할 수 있어야 한다(고통 포인트 8번과 직결). RAG는 검색된 chunk를 그대로 인용할 수 있어 추적 가능성이 확보된다.
11. 환각(지어내기) 억제 — RAG는 검색으로 넘어온 문서 범위 안에서만 답하도록 강제할 수 있어, 모르는 걸 그럴듯하게 지어낼 위험을 줄인다.
12. 데이터 규모와 비용 — 실측 기준 34개 핵심 부서·4,612개 md 정도 분량이라 학습 기반 접근에 쓸 데이터 자체가 부족하다. RAG는 임베딩 재계산 정도로 대응할 수 있다.
13. 질문마다 다른 조합이 필요하다 — 신규 입사자/부서 이동자, 직무·부서에 따라 꺼내야 할 문서 조합이 달라진다(고통 포인트 1·2·5·6번). RAG는 질문마다 다른 문서 집합을 검색해 대응할 수 있다.
14. 버전·출처 추적 — 문서 경로 + 커밋 SHA까지 남기려는 설계(최소 DB 기준)는 검색 결과에 메타데이터를 붙이는 RAG 구조에서만 자연스럽게 된다.

### PoC 공통 기준 — 세 도메인이 지킬 최소 단위

> 도메인마다 RAG 구조는 자유롭게 고르되, **나중에 합칠 수 있도록** 아래만 맞춘다.

| 항목 | 최소 기준 |
|---|---|
| 코퍼스 | 아래 "34개 부서 ↔ 도메인 매핑" 표에서 **자기 도메인에 배정된 폴더들**(`docs/handbook/content/handbook/<부서>/`)의 영어 원문. 한 도메인이 여러 폴더를 맡을 수 있다 — 문서마다 경로를 기록한다(커밋 SHA는 스냅샷 `0ab0299` 고정). 공용 폴더(6개)는 세 도메인이 각자 색인해도 되지만, 합칠 때 아래 "최소 DB"의 중복 제거 키로 하나만 남긴다. 색인 제외 폴더(11개)는 코퍼스에 넣지 않는다 |
| 최소 DB | 공용 참조 테이블은 **원문 청크만** 담는다: `doc_id, domains, source_path, commit_sha, heading_path, chunk_text, chunk_hash`. **임베딩은 공용 테이블에 넣지 않는다** — 도메인마다 임베딩 모델을 자유롭게 고르므로(4절), 각 도메인이 자기 임베딩을 `(chunk_key, embedding_model, embedding)` 형태로 따로 보관한다(`chunk_key` = 아래 중복 제거 키). 컬럼만 합의하고 구현은 도메인별로 한다. **`domains`는 배열**이고, `chunk_hash`는 "공백 정리"(5절 ⑥에서 정의: 연속 공백·탭·줄바꿈을 한 칸으로, 앞뒤 공백 제거)를 적용한 `chunk_text`의 해시다. **중복 제거 키는 `(source_path, commit_sha, heading_path, chunk_hash)`** — 합칠 때 이 넷이 모두 같은 원문 청크만 하나로 합치고 `domains`는 합집합으로 보존한다(한 도메인 값만 남기면 다른 도메인 검색에서 그 청크가 빠진다). 중복 제거는 원문 청크에만 적용하므로 도메인별 임베딩은 합쳐도 사라지지 않는다. **검색은 `domains`에 선택된 도메인이 포함되는지로 거르고, 그 도메인의 임베딩 모델로 비교한다.** 한 제목 아래를 여러 청크로 나눈 경우 `chunk_hash`가 달라 모두 남는다 (DEC-013·DEC-014·DEC-015) |
| RAG 구조 기록 | 청킹 · 임베딩 · 검색 · 리랭크 선택과 **"왜 이 도메인에 최적인가"**를 4절 표에 남긴다 |
| 출력 | **사용자에게 보이는** 항목 필드는 `item, reason, criteria, check_method, source(path#heading), evidence_quote, domains`이다 (5절 ⑥). 자료형: `item`·`reason` 문자열(필수), `source` 문자열 `"path#heading"`(필수), `evidence_quote` 문자열(필수), `criteria`·`check_method` 문자열 또는 `null`, `domains` 문자열 배열(근거 청크의 `domains` 합집합). **`null`을 허용하는 필드는 `criteria`와 `check_method`뿐**이고, `source`·`evidence_quote`가 없거나 검증에 실패하면 그 필드를 비우는 게 아니라 **항목 전체를 제거**한다(5절 ⑦). **응답 전체는 `{commit_sha, items: [...]}`** 이다 — `commit_sha`는 응답 최상위의 문자열 하나이고(스냅샷이 `0ab0299` 하나로 고정돼 있어 항목별 버전은 두지 않는다), `items`의 원소가 위 필드를 갖는다. `source`·`domains`는 모델이 쓰지 않고 검증이 끝난 `chunk_key`의 메타데이터로 코드가 채운다(5절 ⑦). **근거가 없는 필드는 저장 값을 항상 `null`로 두고, "확인 필요"는 화면에서만 표시한다**(도메인마다 `""`·`"확인 필요"`로 달리 구현하지 않게). `criteria`는 "무엇이 이 항목을 갈라 주는 기준인가"를 원문 근거로 적는 필드이고, 해당 여부를 가리는 판정 필드가 아니다 (AGENTS.md 2절). 항목 내용은 도메인마다 다르다 |
| 문서 유래 질문 출처 | **(문서 유래 세트에만 적용)** **핸드북 문서에 이미 질문 형태로 쓰인 것(FAQ)**에서 그대로 뽑는다. 체크리스트 항목·onboarding101류 runbook 문장은 질문으로 옮기면 정답 문서와 단어가 겹쳐 점수가 부풀려지므로 **질문 출처로 쓰지 않고 정답 문서 후보로만** 쓴다 (DEC-012). 합성 질문과 실제 질문의 출처 규칙은 아래 "평가 질문 유형" 행을 따르며, 어느 세트에서도 팀원이 임의로 지어 쓴 질문은 넣지 않는다 (AGENTS.md 5절). 1절의 고통 포인트 중 (가설) 표시된 항목은 이 방식으로 검증되기 전까지 평가셋 근거로 쓰지 않는다 |
| 평가 질문 유형 | 평가표에 **"질문 유형: 문서 유래 / 합성 / 실제"** 열, `domains` 열, **`user_type`(신규 / 이동) 열**, **`scenario_type`(주요 업무 상황) 열**을 둔다. ① **문서 유래**(위 출처 규칙) = 검색이 동작하는지 확인하는 점수 세트. 질문 문장이 검색 대상 문서에 그대로 있어 단어가 같은 문서를 찾는 방식만으로도 높게 나오므로 **이 점수만으로 모델·파라미터의 승자를 정하지 않는다** (DEC-014). ② **합성**(DEC-021) = 웹 채팅(ChatGPT·Claude 등)에서 **역할을 부여해 생성한 질문**. "이번에 SA 팀으로 이동했는데 뭘 해야 해?"처럼 실제 서비스 입력에 가까운 질문을 확보하려는 세트이며 **모델·파라미터 최종 선택에도 쓴다. 단 조건**: (가) 질문을 만들 때 **역할 정의 문서만** 주고 정답 문서는 주지 않는다(정답 문장을 옮겨 쓰는 것 방지). 역할 정의 문서는 핸드북의 부서·직무 설명(후보: `job-description-library`, 각 부서 `_index.md`)에서 고르고 어느 문서인지 기록한다. (나) 도메인당 최소 34개이고 그중 **`user_type`별로 각각 최소 12개**(신규·이동 모두)를 채우고, 각 도메인의 **주요 업무 상황(`scenario_type`)을 도메인 담당자가 PoC 착수 전에 정해**(예: 권한·계정 신청, 교육·학습, 업무 절차, 도구·시스템, 소통·보고 — 예시일 뿐 도메인별로 정한다; 잠정 기준: 도메인당 3개 이상) **상황별로 각각 최소 5개**를 채운다. 생성 모델별 질문 수는 `user_type`·`scenario_type` 안에서 균형을 맞춘다. 같은 뜻의 질문은 하나만 남기고, 정답 문서가 없거나 여러 해석이 가능한 질문은 제외하며, 제외 사유를 평가표에 기록한다. 점수는 `user_type`별로도 따로 보고한다. (다) 생성에 쓴 모델·프롬프트 전문·생성일·근거 역할 문서를 평가표에 기록한다. (라) 사람이 정답 문서·섹션만 표시한다(`labeler_id`). (마) **최종 선택에 쓰는 질문은 생성 모델을 둘 이상(예: ChatGPT와 Claude) 써서 같은 수로 만들고, 생성 모델별 점수를 따로 보고한다.** 평가 후보가 생성 모델과 같은 계열이면 그 후보에 유리하게 나오지 않았는지 모델별 점수 차이로 확인한다. ③ **실제**(DEC-013·DEC-016) = 실제 사람이 한 질문(인터뷰·온보딩 문의·지원 요청). 수집되면 추가로 비교하고 합성 점수와 합치지 않는다. **원문은 저장소 밖(접근 제한 위치)에만 보관**하고, 저장소에는 질문자를 알아볼 수 있는 부분(이름·팀명·직책·날짜·프로젝트명 등 간접 식별 정보 포함)을 `[부서]`·`[직책]`으로 바꾼 질문만 넣는다(커밋한 정보는 지워도 git 이력에 남는다). 함께 기록하는 것은 출처 유형·수집 날짜(월 단위)·사람과 무관한 임의의 질문 기록 ID `source_id`뿐이고, 커밋 전에 팀원 한 명이 비식별 여부를 검토한다. 실제 질문에도 같은 최소 기준(도메인당 34개, `user_type`별 12개, `scenario_type`별 5개)을 적용한다. **이 기준을 못 채운 실제 질문 세트는 단독으로 최종 선택에 쓰지 않고, 기준을 채운 합성 세트와 함께 비교하는 용도로만 쓰며,** 못 채운 도메인은 문항별 결과만 보고한다. **세 세트 점수는 합산하지 않고 따로 보고한다.** 팀원이 임의로 지어 쓴 질문은 넣지 않는다 (AGENTS.md 5절) |
| 평가 | 위 방식으로 뽑은 영어 질문 + **사람이 표시한** 정답 문서·섹션. 평가표는 **질문 출처와 정답 위치를 서로 다른 필드로** 기록한다. 공통: `question`, `question_type`, `domains`, `user_type`, `scenario_type`. 문서 유래: `question_source_path#heading`(질문이 들어 있던 FAQ 위치). 합성: `generator_model`, `prompt`, `generated_at`, `role_source_path`(질문을 만들 때 준 역할 정의 문서). 실제: `source_id`, 출처 유형, 수집 월. **정답: `gold_source_path#heading`과 정답을 표시한 사람의 `labeler_id`**(질문 출처 필드와 합치지 않는다 — "질문을 만드는 데 본 문서"와 "정답 문서"를 구분하기 위해). **정답 표시 뒤 합성 질문의 `role_source_path`와 `gold_source_path`를 비교해 같은 문서(또는 같은 섹션)이면 최종 선택용 점수에서 빼고 별도 점수로 보고한다.** 이렇게 뺀 **뒤에 남은 질문을 기준으로** 도메인당 34개·`user_type`별 12개·`scenario_type`별 5개·생성 모델 간 같은 수를 다시 확인하고, 부족하면 후보 모델을 평가하기 전에 같은 생성 절차로 질문을 보충해 정답 표시와 제외 검사를 다시 한다(32개로 줄면 한 문항이 약 0.031이라 "0.03 미만이면 같다"는 기준이 깨진다). (역할 설명 문서 자체가 정답이 되면 단어가 같은 문서를 찾는 모델에 유리해진다). `labeler_id`는 사람과 직접 연결되지 않는 임의의 ID이고, 실명과의 대응표가 필요하면 질문 원문과 마찬가지로 저장소 밖(접근 제한 위치)에만 보관한다. 정답 표시는 팀원이 하되, AI 세션(웹 채팅·에이전트 등)에서 질문을 만들거나 추출하거나 다듬은 경우(합성 질문 생성, FAQ 추출·정리, 실제 질문 비식별 처리 등) 그 세션에서 이어서 정답을 **표시하거나 검증하지 않는다** — 같은 세션에서 이어 하게 되면 작업을 멈추고 다른 세션에서 하도록 요청한다. 사람이 직접 수집·정리해 AI 세션을 거치지 않은 질문은 해당 없음(DEC-024). 지표 Recall@k·Hit@k(k=1,3,5,10). 차이 0.03 미만이면 같다고 본다. **최종 모델·파라미터 선택은 조건을 지킨 합성 질문 세트 또는 실제 질문 세트의 before/after로 한다** — 문서 유래(FAQ) 점수만으로는 정하지 않는다 (DEC-014·DEC-021) |
| 평가 질문 최소 개수 | 문서 유래·합성·실제 각 세트는 **도메인당 최소 34개**. 한 문항 차이가 0.03보다 작아야 "0.03 미만이면 같다"는 기준이 의미가 있는데, 30개면 한 문항 ≈ 0.033이라 질문 하나 차이도 "다르다"가 된다(34개면 ≈ 0.029). FAQ만으로 34개를 못 채우는 도메인은 **못 채웠다는 사실과 실제 개수를 기록**하고, 0.03 비교 대신 **문항별 성공/실패 목록**으로 보고한다 |
| 산출물 | 도메인 PoC = 이슈 1개 · PR 1개 · 기준선 수치 1개 + **그 도메인 작업 기록 문서**(AGENTS.md 8절 — 코드만으로 끝나지 않는다) |

## 5. 아키텍처 · 워크플로우 설계

> **초안 (팀 확인 필요).** 질문이 들어오면 먼저 어느 도메인 질문인지 분류하고, 그 도메인에 맞는 RAG 모델(4절에서 도메인별로 고른 검색·임베딩 구성)로 보낸다. 도메인 PoC(10/6~7) 결과로 세부를 바꾼다.

```text
[① 질문 입력]  질문 시작 전에 선택: 사용자 유형(신규 입사자 / 부서 이동자) + 새 부서(도메인) → 그다음 업무 상황 서술
      ↓
[② 질문 분류]  선택한 도메인이 맞는지 확인하고 필요하면 1개 추가 (인사 / 엔지니어링 / 영업·지원) — 규칙 + LLM
      ↓            └ 도메인은 최대 2개까지 허용, 판별 불가면 선택한 도메인만 쓰고 "확인 필요" 표시. 공용 폴더는 항상 포함
[③ 모델 분류]  분류된 도메인의 RAG 모델 선택 (4절의 도메인별 구성)
      ↓
[④ 검색]       `domains`에 그 도메인이 포함된 청크(3절 매핑표 범위) top-k   ← 도메인별
      ↓
[⑤ 근거 범위 고정]  검색이 넘긴 청크의 source_path#heading_path 목록 = 인용 허용 범위
      ↓
[⑥ 체크리스트 생성]  고정 스키마 {item, reason, criteria, check_method, source, evidence_quote, domains}로만 출력 (+ 내부 검증용 chunk_key)   ← 공통
      ↓
[⑦ 인용 검증]  source가 ⑤ 범위 밖이거나 evidence_quote가 그 청크에 실제로 없으면 제거 / 근거 없으면 "확인 필요"   ← 공통
      ↓
[⑧ 답변]       검증된 항목(criteria·check_method·evidence_quote 포함) + 데이터 버전(commit_sha)
```

### 단계별 정의

| 단계 | 입력 → 출력 | 공통 / 도메인별 | 비고 |
|---|---|---|---|
| ① 질문 입력 | `{user_type, domain, question}` | 공통 | **`user_type`(신규/이동)과 `domain`(새 부서)은 질문 시작 전에 사용자가 고른다**(DEC-022). 이름·사번 같은 개인 식별 정보는 받지 않고 저장하지 않는다 |
| ② 질문 분류 | `question` + 선택한 `domain` → `domains[]`(최대 2) + 신뢰도 | 공통 | **규칙 + LLM 혼합**(잠정): 규칙(폴더·부서 이름 사전)으로 먼저 보정하고, 규칙으로 정해지지 않을 때 LLM이 판단한다. 규칙의 세부와 LLM 사용 시점은 PoC에서 정한다 |
| ③ 모델 분류 | `domains[]` → 도메인별 RAG 구성 선택 | 공통(라우터) | 구성 자체는 4절에서 도메인별로 고른다 |
| ④ 검색 | `question` → 청크 top-k (3절 공용 스키마 행) | **도메인별** | 청킹·임베딩·BM25·리랭크 자유 |
| ⑤ 근거 범위 고정 | 청크 → 허용 인용 목록 | 공통 | 이후 단계는 이 목록 밖을 인용할 수 없다 |
| ⑥ 체크리스트 생성 | 청크 + `question` → 항목 목록. 사용자 출력 필드는 `item, reason, criteria, check_method, source, evidence_quote, domains`, 내부 검증용으로 `chunk_key`만 따로 가진다 | 공통 스키마, 프롬프트는 도메인별 | 판정류 필드를 두지 않는다. **`criteria`·`check_method`는 `evidence_quote`에서 그대로 발췌하고 인용문 밖의 조건·기한을 쓰지 않는다.** 원문에 없으면 `null`(화면에서 "확인 필요"). **"공백 정리" = 연속된 공백·탭·줄바꿈을 한 칸으로 합치고 앞뒤 공백을 제거하는 것**이며, 3절 `chunk_hash`와 이 절의 비교·중복 제거가 모두 이 한 가지 정의를 쓴다(Markdown 줄바꿈 때문에 `Request access\nthrough the portal`과 `Request access through the portal`이 달라지지 않게). 생성하기 **전에** 여러 도메인 검색기의 결과를 `chunk_key`로 먼저 합치고(`domains`는 합집합) 합친 청크를 한 번만 생성에 넘긴다. 그래도 항목이 겹치면 중복 제거 키는 **`(chunk_key, evidence_quote, 정리한 item)`** 이다(`item`은 "공백 정리"만 적용한 문자열이고 **구두점·대소문자는 바꾸지 않는다**. 그래서 `A/B 계정 신청`과 `AB 계정 신청`은 서로 다른 항목으로 남는다). 같은 인용문에서 서로 다른 `item`이 나오면(예: "VPN 신청"과 "MFA 등록") 둘 다 남긴다. 키가 같은데 `criteria`·`check_method`가 다르면 `null`이 아닌 쪽을 남기고, 둘 다 값이 있고 다르면 두 항목 모두 남긴다 |
| ⑦ 인용 검증 | 항목 목록 + 허용 목록 → 검증된 항목 | 공통 | 코드로 검사 (프롬프트에 맡기지 않는다). 먼저 `chunk_key`가 ⑤ 허용 목록에 있는지 확인하고, **`source`·`domains`는 모델 출력이 아니라 그 `chunk_key`의 메타데이터에서 코드가 채운다**(모델이 다른 청크의 경로를 `source`로 쓰는 일을 막는다). 모델이 값을 함께 내놓는 구현이라면 메타데이터와 정확히 같은지 비교해 다르면 항목을 제거한다. 그다음 `evidence_quote`가 해당 청크 안에 실제로 있는지 확인한다. **보장하는 것은 "인용문이 실제 원문에 있다"까지**이고, 생성된 설명이 인용문과 의미가 같은지(원문에 없는 기한·조건을 덧붙이지 않았는지)는 이 검사로 보장하지 못한다. 구현할 때 빈·지나치게 짧은 인용을 거부하고, 인용에 없는 조건을 덧붙인 항목을 실패시키는 테스트를 추가하며, 최종 답변에 인용문을 함께 보여 사람이 의미 일치를 확인하게 한다. `criteria`·`check_method`는 **값과 `evidence_quote` 양쪽에 같은 "공백 정리"를 적용한 뒤 값이 인용문의 부분 문자열인지** 코드로 확인하고, 아니면 그 필드를 `null`로 비운다(비교에만 쓰고 사용자에게 보이는 인용문·값은 원문 그대로 둔다). 발췌를 엉뚱한 항목에 붙인 경우처럼 의미가 맞는지는 이 검사로 보장하지 못하므로 사람이 인용문을 보고 확인한다 |
| ⑧ 답변 | 검증된 항목 → 최종 출력 (인용문 `evidence_quote`를 함께 보여 사람이 의미 일치를 확인하게 한다) | 공통 | `commit_sha`·`source_path`까지 되짚을 수 있게 유지 |

### 서비스 원칙을 어느 단계가 강제하는가 (AGENTS.md 2절)

| 원칙 | 강제하는 단계 | 방식 |
|---|---|---|
| 15. 판정하지 않는다 | ⑥ | 출력 스키마에 판정류 필드를 두지 않는다 (스키마가 곧 규칙) |
| 16. 근거 없는 말은 하지 않는다 | ⑤⑦ | 인용 허용 범위를 검색 결과로 고정하고, 범위 밖·근거 없는 항목은 제거한다 |
| (경로·제목 추측 금지) | ⑦ | `source`가 허용 목록과 정확히 일치하지 않거나 `evidence_quote`가 그 청크에 없으면 "확인 필요" |
| 17. 추적 가능해야 한다 | ④⑧ | 공용 스키마의 `source_path`·`heading_path`·`commit_sha`를 답변까지 전달한다 |

### 결정된 것 (2026-10-04, DEC-020·DEC-022)

- 도메인은 3개이고 "전사 공통"은 도메인에서 제외, 공용 폴더 6개·색인 제외 폴더 11개(3절).
- 사용자는 질문 전에 **신규/이동 유형과 새 부서(도메인)** 를 고른다. 개인 식별 정보는 받지 않는다.
- 도메인은 질문당 **최대 2개**까지 허용하고, 질문 분류는 **규칙 + LLM 혼합**(잠정)이다.

### 미결 (팀 확인)

- ② 분류의 규칙 사전(어떤 이름·키워드를 규칙으로 쓸지)과 LLM을 부르는 조건, 정확도를 어떤 평가셋으로 잴지 (분류 평가셋도 AGENTS.md 5절 규칙을 따라야 한다).
- `user_type`이 ④ 검색과 ⑥ 생성을 어떻게 바꾸는지. 1절에서 근거가 확인된 것은 부서 이동자(5번: 새 직무 온보딩 완료 요구)뿐이므로, 이동자에게 "이미 끝냈을 전사 온보딩" 항목을 제외하거나 표시하는 방식을 가설로 두고 PoC에서 확인한다.
- 이동자에게 이전 부서를 묻지 않기로 했으므로(DEC-022) 1절의 고통 포인트 6번(이전·새 부서 지식의 겹침)은 이번 범위에서 다루지 않는다.
- 팀원 4명 vs 도메인 3개의 담당 배치(담당자 확정 때 같이 정한다). 공용 폴더 6개를 누가 색인할지도 같이 정한다.
