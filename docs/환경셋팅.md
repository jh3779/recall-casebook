# 환경셋팅 안내 — 결함 선례 작업 환경

결함 선례 찾기 도우미(DEC-030) 작업을 시작하는 팀원이 **도구 설치 → 저장소 받기 → 데이터 만들기 → 기준 점수 확인**까지 따라 하는 순서다.
공통 도구(uv·lefthook·gh)의 자세한 설명은 [`시작하기.md`](시작하기.md) 2~3절, git 명령은 [`git_명령어.md`](git_명령어.md)에 있다.

| 단계 | 할 일 | 끝났는지 확인 |
|---|---|---|
| 1 | 도구 설치 (컴퓨터당 1회) | `uv --version` · `lefthook version` · `pdftotext -v` |
| 2 | 저장소 받기 (저장소당 1회) | `uv run pytest`가 모두 passed |
| 3 | 데이터 받기·만들기 | `data/processed/defect/`에 `recalls.jsonl`·`eval.jsonl`·`build.json` |
| 4 | 기준 점수 확인 | Hit@10 0.510 (원본 사본이 있을 때) |

---

## 1. 도구 설치 (컴퓨터당 1회)

| 도구 | 왜 필요한가 |
|---|---|
| **uv** | Python 3.12 설치·가상환경·패키지 관리. `pip`·`venv` 대신 쓴다 (AGENTS.md 4절) |
| **lefthook** | 커밋·push 직전에 규칙 위반을 내 컴퓨터에서 먼저 잡는다 |
| **gh** (GitHub CLI) | PR 만들기·검사 결과 보기. 선택이지만 권장 |
| **poppler** (`pdftotext`) | 리콜 원본 보고서(Part 573) PDF를 글자로 바꾼다. `rclrpt` 스크립트에만 필요 |

**macOS**

```bash
brew install uv lefthook gh poppler
```

**Windows** — Git for Windows(Git Bash 포함)를 먼저 설치한 뒤, 설치 명령은 [`시작하기.md`](시작하기.md) 2절을 따른다. poppler는 scoop으로 설치한다(`scoop install poppler`). 이후 작업은 Git Bash에서 한다.

**확인**

```bash
uv --version       # 0.12.5 이상 (낮으면: brew로 설치했으면 brew upgrade uv, 아니면 uv self update)
lefthook version
git --version      # git switch를 쓰려면 2.23 이상
pdftotext -v       # 기준 판독은 26.08.0 — 다른 버전이면 573 판독 결과가 조금 달라질 수 있다
```

> Python은 따로 설치하지 않는다. uv가 `.python-version`(3.12)을 보고 받는다.

## 2. 저장소 받기 (저장소당 1회)

```bash
git clone https://github.com/jh3779/LG_CNS_RAG_main.git
cd LG_CNS_RAG_main

uv sync                # .venv 생성 + uv.lock 그대로 설치
lefthook install       # git 훅 설치 — 빼먹으면 검사 없이 커밋·push된다
cp .env.example .env   # API 키는 .env에만 적는다 (커밋 금지, 지금 단계에서는 키가 없어도 된다)
```

**확인** — 셋 다 이렇게 나오면 된다.

```bash
uv run pytest          # 모두 passed (2026-10-07 기준 102개)
uv run ruff check .    # All checks passed!
lefthook validate      # All good
```

## 3. 데이터 받기·만들기

원본(NHTSA 공개 파일, 573 PDF)과 결과물은 **커밋하지 않는다** — `data/raw/`, `data/processed/`는 `.gitignore`에 들어 있다. 스크립트로 받아 만든다. 자세한 설명은 [`scripts/defect_precedent/README.md`](../scripts/defect_precedent/README.md).

> 2026-10-06 원본 사본을 넘겨받았다면 ①(`fetch`)을 하지 말고 4절 A의 순서를 따른다.

```bash
uv run python -m scripts.defect_precedent.nhtsa fetch          # ① NHTSA 원본 zip 받기 (약 27MB) + manifest.json
uv run python -m scripts.defect_precedent.nhtsa build          # ② 리콜 카드·시험지 만들기 (약 2초)
uv run python -m scripts.defect_precedent.bm25_baseline        # ③ 기준 점수 Hit@1·3·5·10 (약 1분)
uv run python -m scripts.defect_precedent.rclrpt sample 300    # ④ 573 보고서 무작위 표본 판독 (pdftotext 필요, PDF 약 580개·약 118MB를 받음, 시간은 네트워크에 따라 다름)
```

만들어지는 것:

```text
data/
├── raw/
│   ├── nhtsa/            ① 원본 zip·명세·manifest.json (다시 받으면 옛 것은 nhtsa.<받은 시각>으로 보관)
│   └── rclrpt/           ④ 573 PDF
└── processed/defect/
    ├── recalls.jsonl     ② 리콜 카드 30,350장 (2026-10-06 원본 기준)
    ├── eval.jsonl        ② 시험 질문 749개
    ├── build.json        ② 어떤 원본에서 나왔는지 (sha256)
    └── causes_sample.jsonl  ④ 573 원인·공급사 판독 결과
```

- `rclrpt all`(약 1.2만 건, 수 시간)은 **팀 확인 뒤에만** 돌린다.
- 유료 API(LLM·임베딩)를 많이 부르는 작업은 예상 호출 수·비용을 먼저 공유하고 확인을 받는다 (AGENTS.md 7절).

## 4. 기준 점수 확인

NHTSA는 같은 주소에 매일 새 파일을 덮어쓴다. 그래서 **오늘 받은 원본으로는 2026-10-06 기준값이 그대로 나오지 않을 수 있다.** 경우가 둘이다.

**A. 2026-10-06 원본 사본을 넘겨받은 경우** — 3절 ①(`fetch`)은 **하지 않는다.** `fetch`는 이미 있는 `data/raw/nhtsa/`를 `data/raw/nhtsa.<받은 시각>`으로 옮기고 오늘 원본을 받아, 기준값이 재현되지 않는다. 순서는 이렇다.

1. 사본을 `data/raw/nhtsa/`에 둔다 (이미 `fetch`를 했다면 그 폴더를 다른 이름으로 옮기고 사본을 이 이름으로 둔다).
2. `uv run python -m scripts.defect_precedent.nhtsa build`
3. 아래 명령

```bash
uv run python -m scripts.defect_precedent.bm25_baseline --baseline scripts/defect_precedent/baseline_2026-10-06_maker-aliases.json
```

```text
리콜 30,350건 색인, 질문 749개 (대리 평가 · baseline_2026-10-06_maker-aliases.json 재현 (원본·카드·시험지 sha256 일치))
  연결 리콜 중 하나라도 (주 지표): Hit@1 0.307 · Hit@3 0.393 · Hit@5 0.455 · Hit@10 0.510
  첫 번째 연결 리콜만 (참고): Hit@1 0.296 · Hit@3 0.374 · Hit@5 0.438 · Hit@10 0.503
  2026-10-06 기준값: Hit@10 0.510 (주) / 0.503 (참고)
```

> 위 2번의 `build`는 사람이 확인한 회사명 대응표(`maker_aliases.csv`)를 읽어 카드의 `maker`·`maker_group`을 채운다(DEC-036). 그래서 카드를 이 코드로 만들었다면 기준 파일은 `baseline_2026-10-06_maker-aliases.json`이다. 회사명을 반영하기 전에 만든 카드(`recalls.jsonl`)로 재현하려면 옛 기준 `baseline_2026-10-06.json`을 쓴다(같은 원본·시험지·573 표본이고 카드만 다르며, BM25 점수는 같다). 드라이브의 `data.zip`은 회사명 반영 전 카드라서 옛 기준으로 재현되고, 새 카드는 드라이브 `defect_data_2026-10-08_maker-group`에 있다. `build`는 `data/processed/defect/`를 통째로 바꾸니 옛 카드가 필요하면 먼저 보관한다.

**B. 사본이 없는 경우** — 오늘 받은 원본으로 같은 질문 번호만 다시 잰다. 출력에 "재평가 (재현 아님)"이 붙고 값이 기준과 조금 다를 수 있다.

```bash
uv run python -m scripts.defect_precedent.bm25_baseline --baseline scripts/defect_precedent/baseline_2026-10-06_maker-aliases.json --allow-drift
```

> **사본 받기**: 2026-10-06 원본 사본은 팀 구글 드라이브에 `data.zip`으로 보관돼 있다(링크는 우지훈에게 받는다). 받은 파일은 저장소 **밖**에 두고, 저장소 루트에서 아래처럼 푼다. 압축 안의 `__MACOSX/` 폴더는 맥 메타데이터라 풀지 않는다(풀면 추적되지 않은 폴더가 생겨 실수로 커밋될 수 있다).
>
> ```bash
> # 기존 data/가 있으면 저장소 밖으로 옮긴 뒤 푼다 — 옮기기가 실패하면 unzip을 하지 않는다
> { [ ! -d data ] || mv data ~/data-backup-$(date +%Y%m%d-%H%M%S); } && unzip ~/Downloads/data.zip -x '__MACOSX/*'
> # 저장소 루트에서 실행 — data/raw/nhtsa·data/raw/rclrpt·data/processed/defect가 생긴다
> ```
>
> **반드시 빈 상태에서 푼다.** 이미 `data/`가 있으면 그 위에 풀지 말고 먼저 **저장소 밖으로** 옮긴다(위 첫 줄) — 덮어쓰기만으로는 압축에 없는 옛 파일(다른 날 받은 573 PDF·결과물)이 남아 기준 사본과 섞이고, 저장소 안(`data.old/` 등)에 두면 `.gitignore`에 걸리지 않아 원본이 실수로 커밋될 수 있다. `data/raw/`·`data/processed/`는 `.gitignore`에 있어 커밋되지 않는다(그 밖의 `data/` 하위 폴더는 커밋될 수 있으니 만들지 않는다). 받은 NHTSA 원본·카드·시험지가 기준과 같은지는 위 `bm25_baseline --baseline`이 sha256으로 확인하고("재현"이 나오면 같다), 573 PDF 사본은 `rclrpt sample --baseline`이 PDF sha256으로 따로 확인한다.
>
> **확인 기록(2026-10-08)**: 드라이브의 `data.zip`을 빈 폴더에 위 명령으로 풀어 `bm25_baseline --baseline` → "재현 (원본·카드·시험지 sha256 일치)", Hit@10 0.510 / 0.503, `rclrpt sample --baseline`(poppler pdftotext 26.08) → 채워짐 205 · 비어 있음 95 · 미확정 0 · 실패 0을 확인했다. 즉 **기준 점수와 573 표본 재현에는 `data.zip` 하나면 된다.** (2026-10-12 갱신: 판독 규칙이 바뀌어(DEC-047, PR #82) 지금 `rclrpt sample --baseline` 기대값은 채워짐 205 · 미보고·조사 중 서술 83 · 비어 있음 12다. 드라이브의 `data.zip`은 573 **전체 수집 전에** 만든 압축본이라 표본 PDF(약 580개)만 들어 있고, 그 안의 원인 파일도 `text_basis` 기록이 없어 서버가 시작을 거부한다. 서버용 원인 파일을 만들려면 `rclrpt all --expect-campaigns 11737`로 PDF 약 2.4만 개(약 5GB)를 받아야 하고 **3.5~4시간** 걸린다. 끝나면 실패 목록(18건 예상)을 확인한 뒤 같은 명령에 `--accept-failures <토큰들>`(첫 실행 출력에 나온다)을 붙여 다시 실행해 완성본을 만든다 — 두 번째 실행은 받은 PDF를 건너뛰어 판독만 약 4분이다. 자세한 절차는 `scripts/defect_precedent/README.md` 34~40행.) 박예원 님 드라이브 폴더 `defect_data_2026-10-06`은 `why_stats` 재현 입력(573 PDF 없음), `defect_data_2026-10-08`은 573 전체 원인 파일이다(`scripts/defect_precedent/README.md` "재현 범위").

이 점수는 **대리 평가**다 — "결함 설명과 그 리콜을 잇는 능력"을 재고, "과거 선례를 찾는 능력"은 재지 못한다 ([`기획_결함선례.md`](기획_결함선례.md) 6절).

## 5. 자주 막히는 것

| 증상 | 원인 | 해결 |
|---|---|---|
| `pdftotext`를 찾을 수 없다 | poppler 미설치 | 1절대로 poppler 설치 후 `pdftotext -v` 확인 |
| `build`가 줄 번호를 보여 주고 중단 | 원본 줄의 칸 수가 명세와 다름 (값이 옆 칸으로 밀렸을 수 있음) | 추측해 고치지 말고 그 줄 번호와 함께 팀에 공유 |
| `--baseline`이 "원본·카드·시험지가 기준 파일과 다르다"로 중단 | 오늘 받은 원본이라 sha256이 다름 | 사본을 넘겨받거나 `--allow-drift`로 재평가 (4절 B) |
| `recalls.jsonl·eval.jsonl이 없다` | `build`를 안 돌림 | 3절 ②부터 |
| 커밋이 "Conventional Commits 형식이 아닙니다"로 막힘 | 커밋 메시지 형식 | [`git_명령어.md`](git_명령어.md) 5절 |
| 훅이 하나도 안 돈다 | `lefthook install`을 안 함 | 2절 다시 |
| `uv sync`가 버전 오류 | uv가 오래됨 | brew로 설치했으면 `brew upgrade uv`, 아니면 `uv self update` |

## 6. 하지 않는 것

- `pip install`, `python -m venv`, `requirements.txt` 만들기 — uv만 쓴다.
- `.env` 내용을 커밋·공유하기, API 키를 코드·로그·PR에 넣기.
- `data/raw/`·`data/processed/`의 원본·결과물을 커밋하기 — 다시 만드는 스크립트만 커밋한다.
- 2026-10-06 원본 사본(`data/raw/nhtsa`, `data/raw/nhtsa.<받은 시각>`) 지우기 — 지우면 기준값을 같은 값으로 재현할 수 없다.
