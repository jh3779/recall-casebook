# 실험: 8D 초안(D2·D4) 묶음 표본 관찰 (2026-10-16)

> 목적: 담은 선례의 원문을 LLM이 **묶고 제목만 붙이게** 했을 때 쓸 만한지, 그리고 서버의 원문 대조(`server/rag/draft.py`)가 글자를 바꾼 인용을 막는지 본다(DEC-065). **평가가 아니다** — 정답이 없고 "쓸 만한가"는 사람이 읽고 판단한다. 서비스 수치로 올리지 않는다.
> **상태: 실제 호출 성공(run2~4, 각 14회). 단 프롬프트를 run2 결과를 보고 고쳐서 run3·4를 돌렸으므로, run3·4는 같은 7개 질문 위의 "고친 뒤" 관찰이다 — 처음 보는 입력에서의 성능이 아니다.**

- **원문 대조는 이 표본에서 한 건도 걸리지 않았다**(`not_in_source` 0). 이것은 "LLM이 글자를 안 바꿨다"가 아니라 "바꿨다면 서버가 버렸을 텐데 버릴 것이 없었다"이다. 서버가 원문에서 인용을 직접 잘라 싣는 구조라 화면에 가는 글자는 어느 경우에도 원문이다(DEC-065).
- **제목 문제(run2에서 발견):** 한 묶음 제목이 "공급업체 공정 품질 편차로 인한 씰 누유"였는데 원문은 "possible quality control deviation"·"could"처럼 추측 표현이었다. 제목이 원문의 불확실성을 지우고 단정 문장이 됐다 — 서비스 원칙 1·3절에 걸린다. 그래서 제목을 "~적은/서술한/언급한 선례" 형식으로 강제하고(`TITLE_FORMAT_RE`), 프롬프트에 "원문과 같은 확실도, '~로 인한 ~' 금지"를 넣었다.
- **수정 뒤(run4):** LLM이 처음 붙인 제목 45개 중 44개가 규칙을 통과했고 1개(40자 초과)는 서버가 "묶음 N"으로 대체했다. "로 인한/때문" 단정 표지는 0건. 그 묶음은 "공급업체 제조 공정 편차로 피스톤 씰이 누유할 수 있다고 적은 선례"로 바뀌었다.
- **남은 문제:** 위 묶음 제목에 원문의 "possible quality control deviation" 중 *possible*은 여전히 없다. 형식 검사는 "~적은 선례"로 끝나는지만 보지, 원문의 한정어가 제목에 남았는지는 못 본다. 이 부분은 사람이 원문 인용과 나란히 읽고 판단한다(화면에는 제목을 보이지 않고 "묶음 N"과 인용 원문만 보인다 — 제목은 서버가 묶음을 정할 때만 쓴다).

## 4. 아직 모르는 것

- **화면–서버 실연동:** 초안 묶음 화면이 실제 서버 응답을 받아 그리는 것을 브라우저에서 확인하지 않았다. 서버(Python)와 화면(TS) 각각의 시험과, 서버 실호출은 따로 통과했다.
- **묶음 품질의 사람 판단:** 서로 다른 표현("PCB controller"·"Printed Circuit Board")이 같은 묶음으로 가는지, "N/A"·"NR" 같은 원인 미보고 서술이 따로 묶이는지는 사람이 읽고 정해야 한다. 이 문서는 그 판정을 하지 않았다.
- **정식 RAG(검색 결과를 LLM에게 주고 *생성*하게 하는 경로)의 환각률:** 이 기능은 "묶음·제목만"을 LLM이 맡고 인용은 서버가 원문에서 자르는 구조라, 환각 측정이 필요한 경로와 다르다. 후자는 이 문서에서 재지 않았다(그 경로의 100문항 시험은 열람 제한 문서라 main에 올리지 않고 별도로 보관한다 — DEC-065).

| 서버가 버린 번호 | 해당 없음 | 2(사유 구분 불가) | 1(상한 3개 초과 1, 풀 밖 0, 중복 0) |

  - **읽는 법**: 묶기가 일관되게 나빠졌다는 신호는 없다. 원문 대조에서 버려진 인용(`not_in_source`·`unknown_source`)은 세 열 모두 0이고 호출은 모두 성공했다. 나머지 지표는 같은 새 코드의 두 측정 사이(A↔B: 중복 인용 3↔1, 제목 규칙 위반 1↔4, 묶인 원문 89↔93, 묶음 50↔53)가 이전↔이후 사이만큼 벌어져서, **이 표본(7개 질문 × 3회)으로는 묶기 품질의 악화나 개선을 가르지 못한다.** 같은 원문 두 번 인용은 세 열 모두 `engine connecting rod bearing failure` 한 질문에서만 나왔다(이전 1/3회, A 3/3회, B 1/3회) — 이 질문의 입력 특성일 수 있고 프롬프트 때문인지는 모른다. 서버가 중복을 버려 화면에는 원문이 한 번만 나간다. 입력 토큰은 번호 선택 지시와 주제 목록만큼 늘었다(회차당 4,400→5,772, +31%). 처음 보는 입력에서의 성능이나 묶기 품질의 판정이 아니다.
  - **측정 B로 확인된 것**: 풀 밖 번호(`unknown_question`)는 21회에서 0건이었고, 버린 1개는 모델이 유효한 번호 4개를 돌려줘 상한(3)을 넘은 것이다(`rearview camera image does not display` run1: P2·P5·P7·P10 → P10 버림). 고른 번호는 `draft_sample.py`가 `raw_question_ids`로 기록한다.
  - 결과 파일(`*.jsonl`)과 보조 스크립트는 저장소에 올리지 않았다. 보조 스크립트(이전 코드 호출용, 키는 환경변수에서만 읽고 출력하지 않는다):

```python
import importlib.util, json, os, sys, time
from functools import partial
from server.rag import draft  # PYTHONPATH가 585b713 작업 폴더를 먼저 가리킨다

assert not hasattr(draft, "QUESTION_POOL"), "이전 코드가 아니다"
spec = importlib.util.spec_from_file_location("ds", sys.argv[2])
ds = importlib.util.module_from_spec(spec)
spec.loader.exec_module(ds)
llm = partial(
    draft.call_llm,
    api_key=os.environ["OPENAI_API_KEY"],
    model=draft.DEFAULT_MODEL,
    effort=draft.DEFAULT_EFFORT,
)
rows = []
for q in ds.QUESTIONS:
    resp = ds.search(q, ds.API)
    cards = ds.pick_cards(resp, draft.MAX_CARDS, "d4")
    d, used = draft.generate("d4", cards, llm)
    rows.append(
        {
            "question": q,
            "build_id": resp["build_id"],
            "n_sources": len(draft.build_sources("d4", cards)),
            "draft": d,
            "raw_titles": [g["title"] for g in json.loads(used.text)["groups"]] if used else [],
            "input_tokens": used.input_tokens if used else 0,
            "output_tokens": used.output_tokens if used else 0,
        }
    )
    time.sleep(0.5)
open(sys.argv[1], "w", encoding="utf-8").write(
    "\n".join(json.dumps(r, ensure_ascii=False) for r in rows)
)
```
