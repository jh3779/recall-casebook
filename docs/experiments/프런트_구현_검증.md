## 자동 검사

최종 명령과 결과는 아래와 같다. 프런트는 `.nvmrc`의 Node 24(v24.21.0)에서 실행했다. 로컬 기본 Node가 26이라 npm의 Node 24 실행 환경으로 명령을 감쌌다.

| 명령 | 결과 |
|---|---|
| `cd frontend && npm ci` | 성공, 취약점 0건 |
| `npm run lint` | 성공, 경고·오류 0건 |
| `npm run build` | TypeScript·Vite 성공 |
| `npm test` | 8개 파일, 74개 통과 |
| `uv run ruff check .` | 통과 |
| `uv run ruff format --check .` | 113개 파일 통과 |
| `uv run pytest` | 498개 통과, 16개 건너뜀, 기존 경고 1개 |
| `node frontend/scripts/check-demo-against-cards.mjs data/processed/defect/recalls.jsonl` | 최종 75/75건 원문 세 칸·회사명·리콜 번호 일치 |
| `git diff --check` | 통과 |

Python은 쓰기 가능한 임시 uv 캐시(`UV_CACHE_DIR=/private/tmp/lgcns-uv-cache`)를 사용했다. 건너뛴 16개는 `TEST_DATABASE_URL`이 없는 DB 통합 시험이다. 프런트 스크립트는 모두 있어 생략한 명령이 없다. 이는 병합용 엄격 local CI나 독립 코드 리뷰를 대신하지 않는다.

시험 근거는 `frontend/src/*test*`, `search/*test*`, `components/Loader.test.tsx`다. 실제 응답 픽스처는 목업의 JSON을 바이트 그대로 옮겼으며, 없는 원인 상태만 별도 합성 픽스처로 구분했다. 원문·출처 렌더링, 코드포인트/겹침/잘못된 꼬리표, API 오류·깨진 응답, 모르는 상태, 판정 패턴 0건을 검사한다. 장비 리콜 시험의 잘못된 차종 가정은 사용자 확인 후 두 차종 전체 기준으로 고쳤다(16E041000은 Ram).

빌드에서 three.js가 포함된 `ShowroomView`는 별도 동적 청크다. 약 653KB(압축 약 166KB)라 Vite의 500KB 경고가 남으며, 검색 진입 청크는 약 246KB(압축 약 78KB)다. 쇼룸을 열 때 해당 청크와 모델을 받는다.

## 브라우저 확인

Safari에서 `http://localhost:5173`을 열어 공개 API에 연결했다. 화면의 판본은 build `f1fe1843ed0f2c66`, 스냅샷 `2026-10-06`, 카드 30,350장, 묶음 `dd0efac013a4…`였다. 사용한 질문은 설계에 있는 공개 예시와 입력 검사용 문자열이다.

| 흐름 | 관찰 |
|---|---|
| 첫 화면 | 예시 4개·하는 일/하지 않는 일·판본·쇼룸 진입 표시 |
| `electric power steering assist loss` | 고객사 4건·다른 회사 10건, `24V412000` 원인 “Contaminated solder flux…”·HL Mando 근거 표시 |
| 한국어만 `조향 고장` | 전송 전 영어 입력 안내, 질문 유지 |
| 390px 모바일 | 목록과 상세가 한 단으로 표시되고 `← 목록` 복귀 동작 |
| 쇼룸·분류 선택 | 75건 데모 안내, Silverado 36건/Ram 39건, 접수일 범위, 같은 분류의 다른 차종 문구 |

모바일에서 전체 결과가 0건이어도 안내와 응답 출처가 숨지 않도록 빈 결과 레이아웃을 분리했다. 실제 API에서 전체 0건 응답은 만들지 않았으며 이 경우의 브라우저 조작 검증은 미실시다. 연결 오류·422·시간 초과·형식 오류는 fetch 대역 시험으로 확인했고 실제 지연/장애 서버로 브라우저를 시험하지 않았다. 실제 모델 파일 누락·WebGL 사용 불가 상황의 브라우저 재현도 미실시다(실패 처리와 검색 복귀 UI는 구현).
