# Decisions

## DEC-001: 다른 프로젝트와 동일한 GitHub Flow 협업 규칙 채택
- **Decision**: branch-strategy-kit 기반 단명 브랜치 전략(`main` 단일 영구 브랜치, `<type>/<name>` 8종 접두어, Conventional Commits PR 제목, squash merge)을 채택한다.
- **Reason**: file-converter·SACHO·project-human-p 등 기존 저장소와 규칙을 통일해 팀원·봇(리뷰봇·플랜봇)이 동일하게 동작하게 한다.
- **Alternatives**: Git Flow(develop 브랜치 유지) — 소규모 단기 프로젝트에 과함.
- **Status**: Accepted
- **Date**: 2026-10-01

## DEC-002: git 훅은 pre-commit 프레임워크 대신 lefthook
- **Decision**: 로컬 git 훅을 lefthook(`lefthook.yml` + `scripts/check-*.sh`)으로 관리한다. pre-commit: 비밀 파일·개인키·1MB 초과 차단 / commit-msg: Conventional Commits / pre-push: main 직접 push 차단 → 브랜치명 (piped).

- **Alternatives**: pre-commit 프레임워크 — 초기 셋팅에서 썼다가 교체.
- **Status**: Accepted
- **Date**: 2026-10-01

## DEC-004: Python 의존성·가상환경은 uv로 관리
- **Decision**: Python 3.12(`.python-version`) + uv(`pyproject.toml`·`uv.lock`, `required-version >=0.12.5`). `package = false`. 런타임 의존성은 스택 확정 전까지 비워 두고 dev 그룹에 pytest·ruff만 둔다. CI는 `uv sync --locked`.
- **Reason**: 사용자 지시(RAG 개발 환경). career-radar·file-converter와 같은 방식이고, lock 파일로 팀원 간 환경을 똑같이 맞출 수 있다.
- **Alternatives**: pip + requirements.txt (참고 레포 방식) — lock·Python 버전 관리가 약함. Poetry — 팀 내 사용 사례 없음.
- **Status**: Accepted
- **Date**: 2026-10-01

## DEC-006: main 룰셋 — PR·필수 체크 강제, 필수 승인 0명
- **Decision**: 룰셋 `main 보호`로 삭제·force push를 막고, PR(squash만)과 필수 상태 체크 3개(`lint-and-test`·`check-branch-name`·`validate-pr-title`)를 강제한다. 필수 승인 수는 0명, bypass 없음.
- **Reason**: 팀원이 아직 합류하지 않아 승인 1명 이상이면 본인 PR을 영구히 병합할 수 없다(작성자 승인은 세지 않음). lanecoach-ai DEC-006과 같은 판단. 규칙 위반·테스트 실패는 체크로 막는다.
- **Alternatives**: 승인 1명 + CODEOWNERS 리뷰 필수 — 팀원 초대·수락 후 재검토.
- **Status**: Accepted
- **Date**: 2026-10-01

## DEC-007: 필수 리뷰어 대신 병합 전 검증 프로토콜(문서 규칙)
- **Decision**: main 룰셋의 필수 승인은 0명으로 유지하고, 병합 전에 `docs/MERGE_PROTOCOL.md` 게이트 9개(CI, 자동 리뷰 존재·최신성, 지적 전부 처리, 스레드 해결, diff 정독, 서비스 원칙 스윕, RAG 근거, 의존성·인계)를 돌려 결과 표를 PR 코멘트로 남긴다. Claude Code는 `pre-merge-check` 스킬로 실행. `gh pr merge`는 deny → ask로 바꿔, 사용자가 명시적으로 지시하고 게이트가 ✅일 때만 에이전트가 병합할 수 있게 했다.
- **Reason**: 사용자 지시("리뷰어 필수는 없이, 대신 문서로 에이전트에게 병합 전 자동리뷰 내용 확인"). project-human-p의 MERGE_PROTOCOL + pre-merge-check 구조를 가져옴.
- **Alternatives**: 룰셋 `required_review_thread_resolution` 켜기 — 구조적으로 강제되지만 사용자가 문서 규칙을 지시해 이번엔 G-05 게이트로만 확인. 필수 승인 1명 — 사용자가 원하지 않음.
- **Status**: Accepted
- **Date**: 2026-10-01

## DEC-008: 병합 전 검증 중 기계 판정 가능한 게이트를 CI 필수 체크로
- **Decision**: `pr-verify`(scripts/ci/pr_checks.py — 판정 필드·비밀값·RAG 수치 근거·PR 본문·type 목록 6곳·문서 링크·AGENTS import)와 `merge-gate`(scripts/ci/merge_gate.py — 현재 head 기준 자동 리뷰·미해결 스레드 0·✅ 결과 코멘트 → 커밋 상태)를 추가하고 룰셋 필수 체크를 5개로 늘린다. 필수 승인은 계속 0명.
- **Reason**: 사용자 지시("CI에도 내부 상세 검증"). DEC-007의 문서 규칙만으로는 에이전트가 따를 때만 지켜지므로, 기계로 판정 가능한 부분은 병합 버튼에서 막는다.
- **Alternatives**: 룰셋 `required_review_thread_resolution` — merge-gate가 G-05를 함께 보므로 중복. 외부 비밀값 스캐너(gitleaks 등) — 지금 규모에는 정규식으로 충분, 필요 시 추가.
- **한계**: G-04·G-06 내용 판단은 기계로 못 함 (merge-gate는 결과 코멘트 존재까지만). issue_comment 트리거는 main의 워크플로를 쓰므로 이 PR 병합 전에는 push 이벤트로만 판정. 스레드 resolve는 이벤트가 없어 수동 재실행 필요.
- **Status**: Accepted
- **Date**: 2026-10-01

## DEC-009: merge-gate는 main 코드로만 실행, 2단계 도입
- **Decision**: `merge-gate` 트리거를 `pull_request_target`·`issue_comment`로 바꾸고 (처음엔 `workflow_dispatch`도 넣었으나 PR 브랜치로 수동 실행하면 PR이 고친 워크플로가 쓰기 권한으로 돌아 제거 — 리뷰봇 `88648fa` 리뷰) checkout을 main으로 고정한다(PR 코드 미실행, API로만 판정). 이 워크플로가 main에 없으면 PR에서 돌 수 없으므로 필수 체크에서 잠시 빼고(1단계) PR #1 병합 후 다음 PR에서 상태 게시를 확인해 다시 필수로 넣는다(2단계). 함께: Codex 리뷰 형식 인식, 결과 코멘트 뒤 새 리뷰면 pending, G-02(출처)는 수동 게이트로 명시, RAG 경로 설정을 `scripts/ci/pr_verify.toml`로 이동(G-09 충돌 해소), RAG 근거에 지표 이름 요구·skip은 검증 방법 섹션 안에서만.
- **Reason**: 리뷰봇(Codex) 리뷰(PR #1, head `9c78f5d`·`def6923`) — `statuses: write`로 PR이 고칠 수 있는 스크립트를 실행해 PR이 자기 게이트를 통과시킬 수 있었음(C2). 사용자 승인("보완 작업 진행").
- **Alternatives**: `pull_request`·`pull_request_review` 유지 + 스크립트 경로만 main에서 받기 — 워크플로 파일 자체가 PR 쪽이라 PR이 고칠 수 있어 기각.
- **남은 한계**: 같은 계정 자기 인증, 쓰기 권한자의 상태 위조 → 리뷰 전용 계정·GitHub App 필요(이슈 #4 → 분리하지 않기로 함, DEC-017).
- **Status**: Accepted
- **Date**: 2026-10-01

## DEC-011: PoC 평가 질문을 두 세트로 나누고, 최소 30문항·공용 테이블 중복 제거 키를 정한다
- **Decision**: `docs/기획v1.md` 3절 "PoC 공통 기준"에 다음을 넣는다. ① 평가표에 "질문 유형" 열 — **문서 유래**(핸드북에 이미 쓰인 체크리스트·FAQ·runbook에서 추출, 기준선 Recall@k용 본 세트)와 **상황 서술**(사람이 직접 쓰고 작성자·정답 표시자를 기록하는 소량 세트, 도메인당 5~10개). 두 점수는 합산하지 않고 따로 보고한다. ② 문서 유래 세트는 **도메인당 최소 30문항**, 못 채우면 그 사실과 개수를 기록하고 0.03 비교 대신 문항별 성공/실패 목록으로 보고한다. ③ 공용 참조 테이블의 **중복 제거 키는 `(source_path, commit_sha, heading_path)`**.
- **Reason**: grilling Q1·Q2·Q4, 사용자 인터뷰로 권장안 채택(2026-10-02). Q1: 문서 유래 질문은 정답 문장을 거의 그대로 옮겨 검색이 쉽게 맞아, 실제 입력("SA 팀으로 이동했는데 뭘 해야 해?")과의 간극을 따로 봐야 한다. Q2: 20문항이면 한 문항 = 0.05라 동등 판정 폭 0.03을 구분할 수 없다(30문항 ≈ 0.033). Q4: 공용 폴더를 여러 도메인이 각자 색인하면 합칠 때 같은 청크가 중복돼 검색 결과가 오염된다.
- **Alternatives**: Q1 문서 유래만 사용 — 간극을 기록만 하고 측정하지 않아 기각. Q2 50문항 — 문서 유래 규칙상 못 채우는 도메인이 늘어 기각. Q4 공용 폴더를 아예 두지 않음 — `upstream-studios`처럼 여러 도메인에 걸친 폴더가 실제로 있어 기각.
- **남은 확인**: 상황 서술 세트가 AGENTS.md 5절("평가셋을 지어내지 않는다")과 충돌하는지 팀 확인. `domain` 컬럼 배열화는 검토 중. 전사 공통 분할안·공용 폴더 목록은 아직 **제안**이라 이 결정에 넣지 않았다.
- **Status**: Superseded by DEC-030 (온보딩 평가·스키마 부분, 2026-10-06 주제 전환) — 이전: Accepted — ①의 "문서 유래" 출처는 DEC-012로, "상황 서술" 세트와 ③의 키는 DEC-013으로 바뀜
- **Date**: 2026-10-02

## DEC-014: 공용 테이블의 domain을 domains[]로 확정하고, FAQ 점수는 모델 선택의 단독 근거로 쓰지 않는다

## DEC-015: 공용 테이블에서 임베딩을 빼고, 도메인당 최소 평가 문항을 34개로 올리고, AGENTS.md 5절의 질문 출처를 두 세트로 정리한다
- **Decision**: ① 공용 참조 테이블은 원문 청크(`doc_id, domains, source_path, commit_sha, heading_path, chunk_text, chunk_hash`)만 담고, 임베딩은 도메인이 `(chunk_key, embedding_model, embedding)`으로 따로 보관한다. 중복 제거는 원문 청크에만 적용한다. ② 문서 유래 세트의 도메인당 최소 문항을 30개에서 **34개**로 올린다(DEC-011 ②의 숫자를 대체). ③ AGENTS.md 5절 2항을 "문서 유래(FAQ)"와 "실제 질문(수집, 출처 기록)" 두 세트로 정리한다.

## DEC-016: 실제 질문 출처는 비식별로 기록하고, 실제 질문 세트도 최소 34개로 한다
- **Decision**: ① 실제 질문(인터뷰·온보딩 문의·지원 요청)의 **원문은 저장소 밖(접근 제한 위치)에만 보관**하고, 저장소에는 간접 식별 정보(이름·팀명·직책·날짜·프로젝트명)를 `[부서]`·`[직책]`으로 바꾼 질문 + 출처 유형 + 수집 날짜(월 단위) + 사람과 무관한 임의의 질문 기록 ID `source_id`만 남긴다. 커밋 전 팀원 한 명이 비식별 여부를 검토한다. ② 실제 질문 세트는 **도메인당 최소 34개**이고(평가표에 `domains` 열), 못 채운 도메인은 문항별 결과만 보고하며 그 도메인의 모델·파라미터 최종 선택만 보류한다. (7차 리뷰 `29188df` 지적으로 "이름만 지우면 문장으로 식별 가능"·"전체 합계 34개" 허점을 보완) ③ 정답 표시자는 실명 대신 임의의 `labeler_id`로 기록하고 실명 대응표는 저장소 밖에 둔다. 질문을 준 사람은 자기 질문의 정답 표시자가 되지 않는다(8차 리뷰 `39e4822` — 비식별 질문 옆 실명이 질문자를 다시 드러냄). 이전에 정답 표시자 실명을 기록하기로 한 부분(DEC-011 이전 3절 "평가" 행)을 대체. AGENTS.md 5절 2항과 `docs/기획v1.md` 3절 "평가 질문 유형" 행에 반영.
- **Reason**: PR #7 여섯 번째 Codex 리뷰(커밋 `bffa01f`). DEC-015에서 내가 넣은 "누가·언제·어디서" 기록 규칙이 부서 이동·인사 관련 문의자의 신원을 git 이력에 남길 수 있다 — 평가 재현에는 신원이 필요 없다. 또 모델 최종 선택 근거가 되는 실제 질문 세트에 문항 수 기준이 없으면 5문항일 때 한 문항이 0.20을 움직여 우연히 한 문제 더 맞힌 모델이 뽑힌다.
- **Alternatives**: 신원을 접근 제한 저장소 파일에 암호화해 커밋 — 이력에 남는 위험을 줄이지 못해 기각. 실제 질문은 소수여도 선택 근거로 허용 — 우연 선택 위험으로 기각.
- **영향**: 실제 질문을 34개 모으기 어려우면 최종 모델 선택이 보류된다(DEC-014의 알려진 한계가 더 커짐). 팀이 수집 경로와 목표 수를 10/6 회의에서 정해야 한다. 익명 `source_id` 부여 규칙과 원본 보관 위치는 정하지 않았다.
- **Status**: Accepted (자동 리뷰 지적 반영, 사용자 병합 지시 전 최종 확인 필요) — 최종 선택 시점 관련 부분은 DEC-021로 완화, 비식별 기록 규칙은 그대로 유효 — ③의 "질문을 준 사람은 자기 질문의 정답 표시자가 되지 않는다"는 DEC-024로 대체(`labeler_id` 비식별 기록은 유효) — 2026-10-06 주제 전환(DEC-030)으로 온보딩 전용 부분은 대체, 실제 질문 비식별·`labeler_id` 기록 규칙은 AGENTS.md 5절로 계속 유효

## DEC-017: 리뷰 게시 계정을 분리하지 않고(B안 폐기), 자동 리뷰봇의 리뷰로만 내용을 확인한다
- **Decision**: 자동 리뷰는 지금처럼 서버의 디스코드 봇(Codex)이 하고 게시 계정도 `jh3779` 그대로 쓴다. 리뷰 전용 계정(`reviewering`)과 그 계정의 리뷰만 인정하는 `merge-gate` 허용 리뷰어 목록(이슈 #4 B안)은 **쓰지 않는다**. 같은 계정이 리뷰와 ✅ 결과 코멘트를 모두 올리는 자기 인증(C1)은 **알려진 한계**로 받아들이고, 병합하는 사람이 결과 코멘트의 리뷰 출처로 확인한다. 이 결정으로 `merge-gate` 필수 체크 승격(이슈 #5)의 선행 조건이었던 B안은 사라진다.

## DEC-019: 최종 출력 스키마를 {commit_sha, items} 구조로 정하고, source·domains는 코드가 채운다
- **Decision**: 서비스 응답 전체는 `{commit_sha, items: [...]}`이다(`commit_sha`는 최상위 문자열 하나, 스냅샷이 `0ab0299`로 고정돼 항목별 버전 없음). `items`의 사용자 출력 필드는 `item, reason, criteria, check_method, source, evidence_quote, domains`이고, 내부 검증용은 `chunk_key` 하나다. `source`(`"path#heading"`)와 `evidence_quote`는 필수 문자열이며 검증에 실패하면 항목 전체를 제거한다. `null`은 `criteria`·`check_method`에서만 허용하고, 근거가 없으면 저장 값은 `null`, 화면에는 "확인 필요"로 표시한다. `source`·`domains`는 모델이 쓰지 않고 검증된 `chunk_key`의 메타데이터로 코드가 채운다. `criteria`·`check_method`는 `evidence_quote`에서 그대로 발췌하며 값이 인용문의 부분 문자열인지 코드로 확인한다. "공백 정리"는 연속된 공백·탭·줄바꿈을 한 칸으로 합치고 앞뒤 공백을 제거하는 것으로 정의하며(구두점·대소문자는 보존), `chunk_hash`·인용 비교·항목 중복 제거가 모두 이 정의를 쓴다. 인용 비교는 값과 `evidence_quote` 양쪽에 같은 정리를 적용하되 사용자에게는 원문을 보인다. 항목 중복 제거 키는 `(chunk_key, evidence_quote, 공백 정리한 item)`이고, 생성 전에 검색 결과를 `chunk_key`로 먼저 합쳐 한 번만 생성한다.
- **Reason**: 이슈 #11, PR #13 자동 리뷰(커밋 `bec8dd4`~`0716a55`)의 필수 보완. 출력 스키마가 단계마다 다르면 4개 도메인이 따로 구현한 결과를 합칠 수 없고, 모델이 다른 청크의 경로를 `source`로 쓰는 것·인용문 밖의 조건을 지어내는 것을 막으려면 값의 출처를 코드가 정해야 한다. 키에 `item`을 넣은 이유: 한 문장에서 나온 서로 다른 두 항목이 같은 `(chunk_key, evidence_quote)`라 이전 키로는 하나가 사라진다.
- **Alternatives**: 항목별 `commit_sha` — 스냅샷이 하나로 고정돼 불필요해 기각(여러 버전을 쓰게 되면 재검토). `source`를 모델이 쓰고 사후 비교만 — 허용은 하되 기본은 코드가 채우는 방식. 빈 값을 `""`·`"확인 필요"` 문자열로 저장 — 도메인마다 구현이 갈려 기각.
- **영향**: 5절은 아직 초안이라 도메인 PoC(10/6~7) 결과로 바뀔 수 있다. 구현 때 필요한 테스트 사례: 빈·짧은 인용 거부, 인용에 없는 조건을 덧붙인 항목 실패, **줄바꿈·탭이 있는 인용문과 공백만 다른 값은 통과, 탭이 든 같은 청크는 도메인과 관계없이 같은 `chunk_hash`·`chunk_key`**, **`A/B 계정 신청`과 `AB 계정 신청`은 서로 다른 항목으로 보존**.
- **Status**: Superseded by DEC-030 (온보딩 평가·스키마 부분, 2026-10-06 주제 전환) — 이전: Accepted (PR #13 병합 시 확정)
- **Date**: 2026-10-03

## DEC-021: 합성 질문 세트를 정식으로 추가하고 모델·파라미터 최종 선택에 쓸 수 있게 한다

## DEC-022: 사용자는 질문 전에 유형과 새 부서를 고른다 — 도메인 최대 2개, 질문 분류는 규칙 + LLM(잠정)

- **Reason**: 2026-10-04 사용자 결정(인터뷰 Q3·R4와 B-5 논의). 유형과 부서를 입력으로 받으면 분류가 단순해지고 이동자에 맞춘 검색·생성을 할 수 있다. 개인 식별 정보 범위를 최소로 둔다.

## DEC-033: 회사명은 `maker`(정리한 이름)와 `maker_group`(같은 회사로 묶어 볼 단위) 두 칸으로 나눈다
- **Decision**: 리콜 카드의 회사명을 두 칸으로 다룬다. `maker` = 신고서 이름을 정리한 이름(표기 차이·법인 형태 차이 Corp ↔ LLC는 한 이름으로 통일, 지역이 다르면 따로). `maker_group` = 사용자가 "같은 회사의 선례"로 묶어 볼 단위(미국 법인 ↔ 본사, 이름이 바뀐 회사 Chrysler → DaimlerChrysler → FCA → Stellantis). `maker`는 표기·법인 형태를 통일한 이름이고, 신고 당시 원문은 `raw_maker`에 그대로 보존한다(화면에 신고 당시 이름이 필요하면 `raw_maker`를 쓴다). 이름이 바뀐 회사도 `maker`를 새 이름으로 덮어쓰지 않고 `maker_group`으로만 잇는다. 모든 줄에 `maker_group` 값을 넣고(묶을 곳이 없으면 `maker`와 같다) 근거를 `group_basis`(없음·자동·초안)로 남긴다.
- **Reason**: 2026-10-07 사용자 결정. 사용자(한국 부품사 엔지니어)는 "그 회사의 선례"를 한데 보고 싶지만, 서류에 쓰는 정보라 신고 당시 이름을 잃으면 추적할 수 없다(AGENTS.md 2절 4항). 후신 관계를 `maker`에 덮어쓰면 판단이 틀렸을 때 되돌리기 어렵다.
- **Alternatives**: `maker`를 최신 이름으로 덮어쓰기 — 화면은 단순하지만 신고 당시 이름이 사라지고 후신 판단이 `maker`에 박혀 기각. 후신 관계 미반영 — Chrysler 계열 카드 약 1,500건이 이름 5개로 갈린 채 남아 기각. 미국 법인과 본사를 한 `maker`로 합치기 — 사용자 결정으로 따로 두고 `maker_group`으로만 잇기로 함.
- **정정 (2026-10-08, 이슈 #35, 우지훈 결정 2026-10-07)**: 위 Decision의 "`maker`는 신고 당시 이름을 지우지 않고"는 법인 형태 통일(예: `GENERAL MOTORS CORP.` → `General Motors LLC`, 287줄은 사람 확인 대상으로 돌리지 않음)과 어긋나는 표현이어서 "표기·법인 형태는 통일하고 원문은 `raw_maker`에 보존한다"로 고쳤다. 동작은 바뀌지 않았다. `maker_group`의 뜻은 PR #39 결정 기록 2에 따라 "같은 그룹이면서 같은 브랜드를 쓰는 회사들"이고, 그룹 소속·개명은 공개 문서로 확인한 것만 묶는다(확인본 반영 완료, DEC-036).
- **Status**: Accepted — 확인본(PR #39)과 카드 반영(PR #42)은 2026-10-08에 끝났다. 처음에는 `maker_group`의 `초안` 값을 확인 전으로 보고 카드 적용을 확인과 새 기준 freeze 뒤로 미뤘었다(과거 조건)

## DEC-034: 데이터는 Supabase(Postgres)에 build 단위로 올린다 — 날짜는 date 타입, 리콜 번호 앞 6자리는 생성 칸으로 잇는다
- **Decision**: 정리된 데이터(`recalls`·`eval_questions`·`causes`, 이어서 `maker_aliases`)와 어느 원본에서 만들었는지(`data_builds`)를 Supabase의 Postgres에 올린다. ① **build 단위로 보관한다** — `build_id`는 입력 파일 4개(원본 명세·카드·시험지·원인 파일)의 sha256으로 정해지는 불변 식별자이고, 줄마다 `build_id`·`snapshot_date`·`row_sha256`을 두며 `(build_id, 번호)`를 기본키로 쓴다. **내용이 하나라도 다르면 다른 build라서 같은 날짜라도 덮어쓰지 않고 둘 다 보관한다**(예: 같은 날짜의 표본 build와 전체 build) — 같은 `snapshot_date`가 다른 내용을 가리키게 되지 않는다. 같은 build를 다시 올리면 저장된 행 해시·원인 명세가 새 계산과 모두 같을 때만 아무것도 바꾸지 않고 끝나고, 하나라도 다르면 덮어쓰지 않고 중단한다. 평소 조회는 `*_latest` 뷰로 하며 `latest_build`가 build 하나를 고른다(전체본이 있으면 가장 최근 전체본, 없을 때만 가장 최근 표본, 같은 종류 안에서는 나중에 올린 것 — 나중 날짜의 표본이 이전 전체본을 가리지 않게 날짜보다 종류가 먼저다. 표본만 보는 `*_latest_sample` 뷰는 따로 둔다). 표본 기준 파일은 저장소의 `baseline_2026-10-06.json`만 쓰고 `--baseline` 옵션은 두지 않는다(임의 기준 파일로 불완전한 표본이 통과하는 것을 막는다). 적재할 때 직전 날짜의 build와 비교한 새로 생김·바뀜(칸별)·사라짐·그대로 건수를 `data_builds.change_summary`에 남긴다(원인 `causes`는 표본과 전체본의 크기가 달라 **같은 종류의 직전 build**와만 비교하고, 같은 종류가 없으면 비교하지 않았다고 적는다). build를 지우는 명령은 두지 않는다 — 지운 데이터를 되살릴 보관소(아카이브)가 없으면 NHTSA가 옛 파일을 다시 주지 않아 근거를 잃기 때문이다. ② 날짜는 `date` 타입이고, 칸마다 정해진 형식(`YYYYMMDD`, `snapshot_date`는 `YYYY-MM-DD`)만 받아 틀리면 추측하지 않고 중단한다. ③ `recalls`에 `campaign6`(= `left(campno, 6)`) **생성 칸**을 두어 `causes.campaign`(6자리)과 잇는다 — 한 캠페인이 `recalls` 여러 건(`campno`)에 붙을 수 있어 조인은 일대다다(282개 캠페인). ④ 모든 테이블은 RLS를 켜고 정책을 두지 않으며, `*_latest`·`latest_build` 뷰는 `security_invoker = true`로 만들어 API 키로는 읽히지 않게 한다(이 옵션이 없으면 뷰가 RLS를 우회한다 — 로컬에서 30,350줄이 그대로 보이는 것을 확인했다). ⑤ **원인 파일의 완전성은 사람이 입력한 숫자가 아니라 독립된 명세와 대조한다.** `--causes sample|full`로 **명시**하고(자동으로 고르지 않음), 표본은 커밋된 기준 파일(`baseline_2026-10-06.json`)의 `rclrpt_sample` 300개 캠페인과 정확히 같아야 하며, 전체는 `rclrpt all`이 완성본과 함께 만드는 `causes.manifest.json`(줄 수·파일 sha256·캠페인 목록 sha256·기대 캠페인 수)과 같아야 한다 — 명세가 없으면 올리지 않는다. 어느 원인 파일(종류·이름·sha256·건수)과 어느 명세로 올렸는지 `data_builds`에 남긴다. ⑥ 적재는 `scripts/defect_precedent/load_db.py`로 하고 오류가 나면 트랜잭션 전체가 되돌아간다.
- **Reason**: 2026-10-07 사용자 결정(Supabase 사용, 조인 칸 추가, 날짜 `date`, 스냅샷별 보관 A안). 서비스 원칙 "답변 → 근거 → 데이터 버전 추적"(AGENTS.md 2절 4항)을 DB에서도 지키려면 과거 답변이 쓴 데이터를 되살릴 수 있어야 한다. ## DEC-035: force push는 설정으로 막고, 이미 push한 커밋은 고치지 않고 새 커밋을 쌓는다
- **Decision**: ① `.claude/settings.json`에서 일반 force push(`--force`, `-f`, `+브랜치`)는 **Claude Code가 보통 쓰는 형태**를 앞 옵션 위치와 관계없이 **deny**하고(모든 형태를 막지는 못함 — 아래 "한계", 완전한 방어는 pre-push 훅 후속), `--force-with-lease`는 **ask**(매번 사용자 확인)로 둔다. 패턴: deny `Bash(git push* --force)`·`Bash(git push* --force *)`·`Bash(git push* -f*)`·`Bash(git push* +*)`·`Bash(git push* --mirror*)`·자주 쓰는 묶음 `-uf`·`-qf`·`-vf`·`-nf`, ask `Bash(git push*--force-with-lease*)`. deny 패턴은 옵션 앞에 공백을 요구해 `-f`로 끝나는 브랜치 이름(`docs/raw-f`)을 잘못 막지 않고, `-f*`로 `-fu` 같은 묶음 옵션도 막는다(PR #37 리뷰). ② AGENTS.md 6절: 이미 push한 커밋은 amend·rebase로 고치지 않고 새 커밋을 쌓는다.
- **Reason**: 2026-10-07 PR #33에서 에이전트가 이미 push한 커밋(`3a0a890`)을 amend하고 사용자 요청 없이 `git push -q --force-with-lease`로 덮어썼다(→ `bae75cc`, 사용자 사후 승인). AGENTS.md 6절에 규칙이 있었고 설정에도 `Bash(git push --force:*)` deny가 있었지만, `:*`는 명령 앞부분 일치라 `-q`가 앞에 끼면 걸리지 않았다(Claude Code 문서 code.claude.com/docs/en/permissions: "The `:*` form is only recognized at the end of a pattern", 규칙 평가 순서 deny → ask → allow, `&&` 등으로 이은 복합 명령은 하위 명령마다 검사). 같은 원인의 실수는 다시 생길 수 있어 문서가 아니라 구조로 막는다(AGENTS.md 2절 취지). 사용자 결정(2026-10-07, "기록해줘").
- **Alternatives**: ① 모든 `git push`를 ask — 일상 push마다 확인이 떠 작업이 느려져 제외. ② 기존 접두사 규칙 유지 — 이번 구멍이 그대로라 제외. ③ `--force-with-lease`도 deny — 규칙상 사용자가 요청하면 허용되는 명령이라 ask로 둠. 옛 접두사 규칙 `git push --force:*`가 `git push --force-with-lease …`(앞에 다른 옵션 없음)도 막고 있었다면 이번 변경은 그 경우를 deny에서 ask로 완화한 것이고, 이는 의도된 것이다. ask가 실제로 효과를 내는 경로는 사용자가 로컬 설정에 `git push` allow를 저장한 경우다 — 평가 순서 deny → ask → allow라 ask가 그 allow를 이긴다.
- **한계**: 문서상 `*`는 공백을 포함한 임의 텍스트와 일치하고 패턴 어디에나 둘 수 있다("A `*` in a Bash rule matches any text, including spaces"). 다만 설정은 Claude Code가 보통 쓰는 형태만 막는다 — `git -C <폴더> push --force`·`git -c … push`처럼 형태가 다른 호출, 위 네 가지 외의 묶음(예: `-uqf`), refspec 안의 `+`(예: `git push origin HEAD:+x` — `feat/a+b` 같은 브랜치 이름을 잘못 막지 않으려고 `+` 앞에 공백을 요구한 결과)는 걸리지 않는다. 글자 패턴으로는 모든 형태를 막을 수 없으므로, **후속으로 실제로 원격 커밋을 잃게 하는 push(빨리 감기가 아닌 갱신)를 거부하는 pre-push 훅**을 검토한다(사용자 결정 2026-10-07, Codex `31e6d003` 지적) — 훅은 사람·모든 에이전트에 적용된다. 사람의 git(터미널)·다른 에이전트는 이 설정의 영향을 받지 않으므로 AGENTS.md 규칙도 함께 둔다.
- **Status**: Accepted (사용자 결정 2026-10-07)
- **Date**: 2026-10-07

## DEC-036: 회사명 대응표의 확인본을 `nhtsa build`가 카드에 반영한다 — `maker` 의미 변경과 `maker_group` 칸 추가
- **Decision**: ① `nhtsa build`가 사람이 확인한 `maker_aliases.csv`(확인본, DEC-033)를 읽어 카드의 `maker`(정리한 이름)와 `maker_group`(같은 회사로 묶어 볼 단위)을 채운다. 신고서 원문은 `raw_maker`에 그대로 보존한다. 확인이 끝나지 않았거나(`unreviewed` 검사: 줄 삭제·추가, 고정 칸 변조, 이유 없는 수정, 같은 `maker`가 여러 `maker_group`, 확인 필요·보류가 남은 줄) 대응표에 없는 이름이 있으면 짐작하지 않고 중단한다. ② 카드 칸은 `maker_group`을 `maker` 바로 뒤에 **추가**하고 다른 칸은 지우거나 바꾸지 않는다. DB `recalls`에도 `maker_group`을 더하되 NULL을 허용한다 — 옛 build는 NULL이고 새 build부터 적재 코드가 값을 요구한다(없으면 `nhtsa build` 안내와 함께 중단). 이미 만들어진 테이블에는 `alter table … add column if not exists`로 칸이 더해진다. ③ `build.json`에 대응표 파일의 sha256(`maker_aliases_sha256`)을 남기고 `verify_build`가 대조한다(이 칸이 없는 옛 `build.json`은 건너뜀). ④ 옛 기준(`baseline_2026-10-06.json`)은 카드 해시가 달라져 "재현"이 불가능해진다. `--without-aliases` 옵션은 두지 않는다 — 옛 값이 필요하면 회사명 반영 전 커밋(`9e8381f`)을 체크아웃해서 재현한다. 새 기준은 `baseline_2026-10-06_maker-aliases.json`이고, BM25가 회사 이름을 색인하지 않아(`defect`+`consequence`+`remedy`만) 점수는 같을 것으로 예상하며 실제로 재서 기록한다.
- **Reason**: 사용자는 "그 회사의 선례"를 한데 보고 싶지만 서류에 쓰는 정보라 신고 당시 이름을 잃으면 추적할 수 없다(DEC-033). 반영을 `build` 안에 두면 같은 원본·같은 확인본에서 같은 카드가 다시 만들어지고(재현), 확인본의 해시가 `build.json`에 남아 "어느 표로 만든 카드인지" 되짚을 수 있다(AGENTS.md 2절 4항). 미확인 초안이 서비스 데이터에 섞이면 같은 회사의 선례가 갈라지거나 다른 회사가 묶일 수 있어, 확인 검사를 통과한 표만 쓴다.
- **Alternatives**: 후처리 스크립트로 카드를 고치기 — 카드가 `build`와 따로 만들어져 재현이 깨질 수 있어 기각. `maker_aliases` 테이블을 DB에 따로 올리기 — 대응표는 저장소에 있고 해시를 `build.json`에 남기므로 칸만 추가하고, 필요해지면 나중에 더한다. `--without-aliases` 옵션으로 옛 카드도 만들기 — 옛 기준을 계속 쓸 일이 거의 없어 옵션·분기·테스트 비용이 더 크다고 보고 기각(사용자 결정 2026-10-07). `maker_group`을 NOT NULL로 — 이미 적재된 build가 있는 DB에 칸을 더할 수 없어 기각.
- **운영 메모 (2026-10-08, PR #42 리뷰 반영)**: ① 같은 스냅샷 날짜의 옛 build(`3c15c6bcf7dc7c3a`, `maker`가 원문과 같음, `maker_group` 전부 NULL)와 새 build(`f5cb2f944f36125d`, 정리한 이름)는 `data_builds.change_summary`가 날짜 비교라 "첫 build"로 남는다 — 두 build 사이에 `maker`가 바뀐 카드는 `campno`로 직접 조인해 센 10,038건이다. build 사이에 `maker`를 직접 비교하지 않는다. 추적은 build_id → `build.json`의 `recalls_sha256` → 기준 파일 `baseline_2026-10-06_maker-aliases.json`의 `maker_aliases_sha256`(확인본 해시)로 한다. ② 대응표 해시는 파일 전체(줄바꿈만 LF로 맞춤) 기준이라 **확인본을 한 글자라도 고치면**(메모 보강 포함) `verify_build`가 멈춘다 — `nhtsa build`를 다시 하고 새 기준을 freeze해야 한다. 엄격한 쪽이 안전해서 의도한 동작이다. ③ 적재 코드는 새 카드 여부를 첫 줄에 `maker_group` 키가 있는지로만 본다(값 검사는 하지 않음). ④ 한계(후속): `unreviewed`가 대조하는 초안(`maker_aliases_draft.csv`)의 해시는 기록하지 않는다 — 확인본과 초안의 `review_required`를 함께 지우면 검사를 통과할 수 있다. 초안 해시 기록은 `build.json`에 칸을 더하는 일이라 새 기준 재고정이 필요해 별도 이슈(#45)로 둔다.
- **Status**: Accepted (사용자 결정 2026-10-07). 구현·실제 카드 반영은 PR #42(2026-10-08)에서 끝났고 새 build `f5cb2f944f36125d`가 Supabase에 적재됐다 (#31)
- **Date**: 2026-10-07

## DEC-037: 시점 평가는 범위를 줄여 진행한다 — 예비 5문항, 개시 문서 질문만, 573 원인 문장 제외, 후보 묶음 정답 표시
- **Decision**: 기획 6절 "시점 평가"를 다음 범위로 진행한다. ① **질문**: 조사 개시 문서(ODI Resume, `static.nhtsa.gov/odi/inv/<연도>/INOA-<조사번호>-<숫자>.pdf`)의 요약을 원문 그대로 옮기고 PDF 원문과 글자 단위로 대조한다. 후보는 개시 문서가 확인되는 2007년 이후 개시 333문항. 현재판 요약 + 공개일(②)과 신고 문서(③)는 쓰지 않는다. ② **문항 수**: 예비 시험을 30문항에서 **5문항**으로 줄인다(절차 확인용, 성능·방식 선택 근거 아님). 본 평가는 시드를 고정해 약 45문항을 무작위로 뽑고(예비와 겹치지 않게, 시드·목록은 정답 표시 전 커밋) 정답 있는 문항 34개 이상으로 잰다. ③ **색인**: 기준일(`open_date`) 이전에 접수된 리콜 카드만(`received_date < open_date`) 색인하고 **573 원인 문장은 뺀다**. ④ **정답 표시**: 문항마다 BM25 상위 20 + B 방식 상위 20을 합친 후보를 출처·순위를 숨기고 섞어 보여 주고, A(박예원)·C(박성호)가 나눠 표시한다. 5문항은 둘 다 표시해 일치를 본다. B(우지훈)는 후보에 자기 검색 결과가 들어가므로 정답을 표시하지 않는다. ⑤ **중단 기준**: 10/16까지 정답 있는 문항이 34개 미만이면 발표에서 "미측정"으로 표시한다.
- **Reason**: 749문항 대리 평가는 정답 리콜의 99.6%가 조사 시작 뒤 접수돼 "과거 선례 찾기"를 재지 못하고, 시점 평가 없이는 발표에서 그 주장을 할 수 없다(기획 6절). A의 확인(2026-10-08, #38): 현재판 요약의 공개일은 `FLAT_INV`·공개 API 어디에도 없어 불가, 개시 문서는 2007년 이후 확인 — 34문항을 채우기에 충분하다. 예비 30 + 본 평가 34 = 64문항은 10/20 발표까지 정답 표시 시간이 모자란다. `causes.jsonl`은 최신 판본의 원인 문장만 담아 기준일 당시 판본을 쓸 수 없고, 최신본을 쓰면 나중에 추가된 원인이 새어 들어간다. 573 자료는 2014-08-20 이후 리콜에만 있어 기준일 이전 선례에서 빠지는 양도 적다. 3만 건을 사람이 다 볼 수 없어 두 검색의 상위 후보만 판단한다(TREC식 후보 묶음). 2026-10-08 우지훈 제안, 박예원 동의(#38 댓글).
- **Alternatives**: 시점 평가를 "미측정"으로 두기 — 서비스의 핵심 주장을 근거 없이 두게 돼 기각(단, ⑤ 중단 기준으로 남김). 예비 30문항 유지 — 일정상 본 평가를 못 채워 기각. 신고 문서를 질문으로 — 질문 모집단이 749개 조사와 달라지고 개시 문서로 충분해 기각(HANDOFF 할 일 24). 573 옛 판본 원인 문장을 다시 뽑아 포함 — PDF 재처리가 필요해 일정상 보류. 후보 없이 전체 색인을 사람이 훑기 — 작업량이 커서 기각.
- **영향 / 알려진 한계**: 시점 평가 점수는 "573 없이 리콜 카드만 잰" 범위로 보고한다. 두 검색이 모두 놓친 선례는 정답에서 빠진다(후보 묶음 편향). 후보에 B 방식이 들어가므로 정답을 본 뒤 검색을 고치지 않는다(AGENTS.md 5절). 질문을 AI 세션에서 옮기면 그 세션에서 정답을 표시하지 않는다(DEC-024 — 박예원은 시트로 따로 표시). C 박성호 참여는 아직 본인 확인 전.
- **Status**: Proposed (우지훈 제안·박예원 동의 2026-10-08, C 박성호 확인 전)
- **Date**: 2026-10-08
