# Decisions

## DEC-001: 다른 프로젝트와 동일한 GitHub Flow 협업 규칙 채택
- **Decision**: branch-strategy-kit 기반 단명 브랜치 전략(`main` 단일 영구 브랜치, `<type>/<name>` 8종 접두어, Conventional Commits PR 제목, squash merge)을 채택한다.
- **Reason**: file-converter·SACHO·project-human-p 등 기존 저장소와 규칙을 통일해 팀원·봇(리뷰봇·플랜봇)이 동일하게 동작하게 한다.
- **Alternatives**: Git Flow(develop 브랜치 유지) — 소규모 단기 프로젝트에 과함.
- **Status**: Accepted
- **Date**: 2026-10-01

## DEC-002: git 훅은 pre-commit 프레임워크 대신 lefthook
- **Decision**: 로컬 git 훅을 lefthook(`lefthook.yml` + `scripts/check-*.sh`)으로 관리한다. pre-commit: 비밀 파일·개인키·1MB 초과 차단 / commit-msg: Conventional Commits / pre-push: main 직접 push 차단 → 브랜치명 (piped).

- **Alternatives**: pre-commit 프레임워크 — 초기 셋팅에서 썼다가 교체.
- **Status**: Accepted
- **Date**: 2026-10-01

## DEC-004: Python 의존성·가상환경은 uv로 관리
- **Decision**: Python 3.12(`.python-version`) + uv(`pyproject.toml`·`uv.lock`, `required-version >=0.12.5`). `package = false`. 런타임 의존성은 스택 확정 전까지 비워 두고 dev 그룹에 pytest·ruff만 둔다. CI는 `uv sync --locked`.
- **Reason**: 사용자 지시(RAG 개발 환경). career-radar·file-converter와 같은 방식이고, lock 파일로 팀원 간 환경을 똑같이 맞출 수 있다.
- **Alternatives**: pip + requirements.txt (참고 레포 방식) — lock·Python 버전 관리가 약함. Poetry — 팀 내 사용 사례 없음.
- **Status**: Accepted
- **Date**: 2026-10-01

## DEC-006: main 룰셋 — PR·필수 체크 강제, 필수 승인 0명
- **Decision**: 룰셋 `main 보호`로 삭제·force push를 막고, PR(squash만)과 필수 상태 체크 3개(`lint-and-test`·`check-branch-name`·`validate-pr-title`)를 강제한다. 필수 승인 수는 0명, bypass 없음.
- **Reason**: 팀원이 아직 합류하지 않아 승인 1명 이상이면 본인 PR을 영구히 병합할 수 없다(작성자 승인은 세지 않음). lanecoach-ai DEC-006과 같은 판단. 규칙 위반·테스트 실패는 체크로 막는다.
- **Alternatives**: 승인 1명 + CODEOWNERS 리뷰 필수 — 팀원 초대·수락 후 재검토.
- **Status**: Accepted
- **Date**: 2026-10-01

## DEC-007: 필수 리뷰어 대신 병합 전 검증 프로토콜(문서 규칙)
- **Decision**: main 룰셋의 필수 승인은 0명으로 유지하고, 병합 전에 `docs/MERGE_PROTOCOL.md` 게이트 9개(CI, 자동 리뷰 존재·최신성, 지적 전부 처리, 스레드 해결, diff 정독, 서비스 원칙 스윕, RAG 근거, 의존성·인계)를 돌려 결과 표를 PR 코멘트로 남긴다. Claude Code는 `pre-merge-check` 스킬로 실행. `gh pr merge`는 deny → ask로 바꿔, 사용자가 명시적으로 지시하고 게이트가 ✅일 때만 에이전트가 병합할 수 있게 했다.
- **Reason**: 사용자 지시("리뷰어 필수는 없이, 대신 문서로 에이전트에게 병합 전 자동리뷰 내용 확인"). project-human-p의 MERGE_PROTOCOL + pre-merge-check 구조를 가져옴.
- **Alternatives**: 룰셋 `required_review_thread_resolution` 켜기 — 구조적으로 강제되지만 사용자가 문서 규칙을 지시해 이번엔 G-05 게이트로만 확인. 필수 승인 1명 — 사용자가 원하지 않음.
- **Status**: Accepted
- **Date**: 2026-10-01

## DEC-008: 병합 전 검증 중 기계 판정 가능한 게이트를 CI 필수 체크로
- **Decision**: `pr-verify`(scripts/ci/pr_checks.py — 판정 필드·비밀값·RAG 수치 근거·PR 본문·type 목록 6곳·문서 링크·AGENTS import)와 `merge-gate`(scripts/ci/merge_gate.py — 현재 head 기준 자동 리뷰·미해결 스레드 0·✅ 결과 코멘트 → 커밋 상태)를 추가하고 룰셋 필수 체크를 5개로 늘린다. 필수 승인은 계속 0명.
- **Reason**: 사용자 지시("CI에도 내부 상세 검증"). DEC-007의 문서 규칙만으로는 에이전트가 따를 때만 지켜지므로, 기계로 판정 가능한 부분은 병합 버튼에서 막는다.
- **Alternatives**: 룰셋 `required_review_thread_resolution` — merge-gate가 G-05를 함께 보므로 중복. 외부 비밀값 스캐너(gitleaks 등) — 지금 규모에는 정규식으로 충분, 필요 시 추가.
- **한계**: G-04·G-06 내용 판단은 기계로 못 함 (merge-gate는 결과 코멘트 존재까지만). issue_comment 트리거는 main의 워크플로를 쓰므로 이 PR 병합 전에는 push 이벤트로만 판정. 스레드 resolve는 이벤트가 없어 수동 재실행 필요.
- **Status**: Accepted
- **Date**: 2026-10-01

## DEC-009: merge-gate는 main 코드로만 실행, 2단계 도입
- **Decision**: `merge-gate` 트리거를 `pull_request_target`·`issue_comment`로 바꾸고 (처음엔 `workflow_dispatch`도 넣었으나 PR 브랜치로 수동 실행하면 PR이 고친 워크플로가 쓰기 권한으로 돌아 제거 — 리뷰봇 `88648fa` 리뷰) checkout을 main으로 고정한다(PR 코드 미실행, API로만 판정). 이 워크플로가 main에 없으면 PR에서 돌 수 없으므로 필수 체크에서 잠시 빼고(1단계) PR #1 병합 후 다음 PR에서 상태 게시를 확인해 다시 필수로 넣는다(2단계). 함께: Codex 리뷰 형식 인식, 결과 코멘트 뒤 새 리뷰면 pending, G-02(출처)는 수동 게이트로 명시, RAG 경로 설정을 `scripts/ci/pr_verify.toml`로 이동(G-09 충돌 해소), RAG 근거에 지표 이름 요구·skip은 검증 방법 섹션 안에서만.
- **Reason**: 리뷰봇(Codex) 리뷰(PR #1, head `9c78f5d`·`def6923`) — `statuses: write`로 PR이 고칠 수 있는 스크립트를 실행해 PR이 자기 게이트를 통과시킬 수 있었음(C2). 사용자 승인("보완 작업 진행").
- **Alternatives**: `pull_request`·`pull_request_review` 유지 + 스크립트 경로만 main에서 받기 — 워크플로 파일 자체가 PR 쪽이라 PR이 고칠 수 있어 기각.
- **남은 한계**: 같은 계정 자기 인증, 쓰기 권한자의 상태 위조 → 리뷰 전용 계정·GitHub App 필요(이슈 #4 → 분리하지 않기로 함, DEC-017).
- **Status**: Accepted
- **Date**: 2026-10-01

## DEC-011: PoC 평가 질문을 두 세트로 나누고, 최소 30문항·공용 테이블 중복 제거 키를 정한다
- **Decision**: `docs/기획v1.md` 3절 "PoC 공통 기준"에 다음을 넣는다. ① 평가표에 "질문 유형" 열 — **문서 유래**(핸드북에 이미 쓰인 체크리스트·FAQ·runbook에서 추출, 기준선 Recall@k용 본 세트)와 **상황 서술**(사람이 직접 쓰고 작성자·정답 표시자를 기록하는 소량 세트, 도메인당 5~10개). 두 점수는 합산하지 않고 따로 보고한다. ② 문서 유래 세트는 **도메인당 최소 30문항**, 못 채우면 그 사실과 개수를 기록하고 0.03 비교 대신 문항별 성공/실패 목록으로 보고한다. ③ 공용 참조 테이블의 **중복 제거 키는 `(source_path, commit_sha, heading_path)`**.
- **Reason**: grilling Q1·Q2·Q4, 사용자 인터뷰로 권장안 채택(2026-10-02). Q1: 문서 유래 질문은 정답 문장을 거의 그대로 옮겨 검색이 쉽게 맞아, 실제 입력("SA 팀으로 이동했는데 뭘 해야 해?")과의 간극을 따로 봐야 한다. Q2: 20문항이면 한 문항 = 0.05라 동등 판정 폭 0.03을 구분할 수 없다(30문항 ≈ 0.033). Q4: 공용 폴더를 여러 도메인이 각자 색인하면 합칠 때 같은 청크가 중복돼 검색 결과가 오염된다.
- **Alternatives**: Q1 문서 유래만 사용 — 간극을 기록만 하고 측정하지 않아 기각. Q2 50문항 — 문서 유래 규칙상 못 채우는 도메인이 늘어 기각. Q4 공용 폴더를 아예 두지 않음 — `upstream-studios`처럼 여러 도메인에 걸친 폴더가 실제로 있어 기각.
- **남은 확인**: 상황 서술 세트가 AGENTS.md 5절("평가셋을 지어내지 않는다")과 충돌하는지 팀 확인. `domain` 컬럼 배열화는 검토 중. 전사 공통 분할안·공용 폴더 목록은 아직 **제안**이라 이 결정에 넣지 않았다.
- **Status**: Accepted — ①의 "문서 유래" 출처는 DEC-012로, "상황 서술" 세트와 ③의 키는 DEC-013으로 바뀜
- **Date**: 2026-10-02

## DEC-012: 문서 유래 평가 질문은 FAQ 형태만 쓰고, 체크리스트·runbook 문장은 정답 문서 후보로만 쓴다
- **Decision**: DEC-011의 "문서 유래" 세트 출처를 **핸드북에 이미 질문 형태로 쓰인 FAQ**로 좁힌다. 체크리스트 항목·onboarding101류 runbook 문장은 질문 출처로 쓰지 않고 정답 문서 후보로만 쓴다. AGENTS.md 5절 2항과 `docs/기획v1.md` 3절 "평가 질문 출처"·"최소 개수" 행에 반영.
- **Reason**: PR #7 두 번째 Codex 리뷰(커밋 `813a772`). 체크리스트 문장을 그대로 질문으로 쓰면 질문과 정답 문서에 같은 단어가 반복돼 단어 검색만으로 맞는다 — 모델을 이 점수로 고르면 실제 질문에서 성능이 낮을 수 있다. DEC-011 Q1과 같은 문제의식이며 이를 출처 단계에서 막는다.

## DEC-019: 최종 출력 스키마를 {commit_sha, items} 구조로 정하고, source·domains는 코드가 채운다
- **Decision**: 서비스 응답 전체는 `{commit_sha, items: [...]}`이다(`commit_sha`는 최상위 문자열 하나, 스냅샷이 `0ab0299`로 고정돼 항목별 버전 없음). `items`의 사용자 출력 필드는 `item, reason, criteria, check_method, source, evidence_quote, domains`이고, 내부 검증용은 `chunk_key` 하나다. `source`(`"path#heading"`)와 `evidence_quote`는 필수 문자열이며 검증에 실패하면 항목 전체를 제거한다. `null`은 `criteria`·`check_method`에서만 허용하고, 근거가 없으면 저장 값은 `null`, 화면에는 "확인 필요"로 표시한다. `source`·`domains`는 모델이 쓰지 않고 검증된 `chunk_key`의 메타데이터로 코드가 채운다. `criteria`·`check_method`는 `evidence_quote`에서 그대로 발췌하며 값이 인용문의 부분 문자열인지 코드로 확인한다. "공백 정리"는 연속된 공백·탭·줄바꿈을 한 칸으로 합치고 앞뒤 공백을 제거하는 것으로 정의하며(구두점·대소문자는 보존), `chunk_hash`·인용 비교·항목 중복 제거가 모두 이 정의를 쓴다. 인용 비교는 값과 `evidence_quote` 양쪽에 같은 정리를 적용하되 사용자에게는 원문을 보인다. 항목 중복 제거 키는 `(chunk_key, evidence_quote, 공백 정리한 item)`이고, 생성 전에 검색 결과를 `chunk_key`로 먼저 합쳐 한 번만 생성한다.
- **Reason**: 이슈 #11, PR #13 자동 리뷰(커밋 `bec8dd4`~`0716a55`)의 필수 보완. 출력 스키마가 단계마다 다르면 4개 도메인이 따로 구현한 결과를 합칠 수 없고, 모델이 다른 청크의 경로를 `source`로 쓰는 것·인용문 밖의 조건을 지어내는 것을 막으려면 값의 출처를 코드가 정해야 한다. 키에 `item`을 넣은 이유: 한 문장에서 나온 서로 다른 두 항목이 같은 `(chunk_key, evidence_quote)`라 이전 키로는 하나가 사라진다.
- **Alternatives**: 항목별 `commit_sha` — 스냅샷이 하나로 고정돼 불필요해 기각(여러 버전을 쓰게 되면 재검토). `source`를 모델이 쓰고 사후 비교만 — 허용은 하되 기본은 코드가 채우는 방식. 빈 값을 `""`·`"확인 필요"` 문자열로 저장 — 도메인마다 구현이 갈려 기각.
- **영향**: 5절은 아직 초안이라 도메인 PoC(10/6~7) 결과로 바뀔 수 있다. 구현 때 필요한 테스트 사례: 빈·짧은 인용 거부, 인용에 없는 조건을 덧붙인 항목 실패, **줄바꿈·탭이 있는 인용문과 공백만 다른 값은 통과, 탭이 든 같은 청크는 도메인과 관계없이 같은 `chunk_hash`·`chunk_key`**, **`A/B 계정 신청`과 `AB 계정 신청`은 서로 다른 항목으로 보존**.
- **Status**: Accepted (PR #13 병합 시 확정)
- **Date**: 2026-10-03

## DEC-021: 합성 질문 세트를 정식으로 추가하고 모델·파라미터 최종 선택에 쓸 수 있게 한다
- **Decision**: 평가 질문 세트를 **문서 유래 / 합성 / 실제** 3개로 한다. **합성** = 웹 채팅(ChatGPT·Claude 등)에서 역할을 부여해 생성한 질문. 최종 선택에 쓸 수 있되 조건: ① 생성 때 **역할 정의 문서만** 주고 정답 문서는 주지 않는다(역할 정의 문서는 핸드북의 부서·직무 설명 — 후보 `job-description-library`, 각 부서 `_index.md` — 에서 고르고 기록) ② 도메인당 최소 34개이며 `user_type`(신규/이동)별로 각각 최소 12개, 같은 뜻의 질문은 하나만 남기고 정답이 없거나 해석이 여러 가지인 질문은 제외하며 제외 사유를 기록 ③ 생성 모델·프롬프트 전문·생성일·근거 역할 문서를 평가표에 기록 ④ 사람은 정답 문서·섹션만 표시(`labeler_id`) ⑤ **최종 선택에 쓰는 질문은 생성 모델을 둘 이상 써서 같은 수로 만들고 생성 모델별 점수를 따로 보고**(후보 모델과 생성 모델이 같은 계열일 때의 편향을 점수 차이로 확인) ⑥ 세 세트 점수는 합산하지 않고 따로 보고하며 `user_type`별 점수도 보고 ⑦ 도메인 담당자가 정한 주요 업무 상황(`scenario_type`, 잠정 도메인당 3개 이상)별로 각각 최소 5개이고 생성 모델별 수는 `user_type`·`scenario_type` 안에서 균형 ⑧ 같은 기준(34개·유형별 12개·상황별 5개)을 실제 질문에도 적용하고, 못 채운 실제 질문 세트는 단독 최종 선택에 쓰지 않고 기준을 채운 합성 세트와 함께 비교하는 용도로만 쓴다 ⑨ 평가표에서 질문 출처 필드(문서 유래 `question_source_path`, 합성 `generator_model`·`prompt`·`generated_at`·`role_source_path`, 실제 `source_id`·출처 유형·수집 월)와 정답 위치(`gold_source_path#heading`, `labeler_id`)를 서로 다른 필드로 둔다. (PR #16 자동 리뷰 `7eabe22`·`4e128dc` 지적 반영: 비슷한 질문 반복·생성 모델 편향·유형/상황 대표성·출처와 정답 구분. `scenario_type` 목록과 최소 개수 5·3은 담당자 확정 전 잠정) 팀원이 임의로 지어 쓴 질문은 어느 세트에도 넣지 않는다. DEC-013의 "상황 서술 세트는 실제 사례 확보 전까지 점수 제외"와 DEC-014·DEC-016의 "최종 선택은 실제 질문 뒤"를 이 결정으로 완화한다(실제 질문은 추가 비교용). ⑩ 정답 표시 뒤 `role_source_path`와 `gold_source_path`가 같은 문서·섹션인 합성 질문은 최종 선택용 점수에서 빼고 별도 점수로 보고하며, **② 34개·`user_type`별 12개·⑦ `scenario_type`별 5개·⑤ 생성 모델 균형은 이 제외 뒤에 남은 질문 기준**이다(부족하면 후보 모델 평가 전에 같은 생성 절차로 보충하고 정답 표시·제외 검사를 반복. 32개면 한 문항이 약 0.031이라 0.03 기준이 깨짐)
- **Reason**: 2026-10-04 사용자 결정(인터뷰 Q1·R1). 실제 질문을 모으기 어렵고 10/12~14 기준선 점수가 필요하다. 사람이 쓴 질문 대신 웹 채팅 역할극으로 서비스 입력에 가까운 질문을 대량 확보한다. 같은 문장이 정답 문서에 들어 있지 않으면 FAQ 점수 부풀림 문제가 줄어든다.
- **Alternatives**: 합성은 개발용으로만 쓰고 최종 선택은 실제 질문 뒤 — 일정 위험으로 기각(선택지로 제시했으나 사용자가 조건부 사용을 택함). 규칙 유지, 웹 채팅은 아이디어만 — 같은 이유로 기각.
- **영향**: 이전 "AI나 팀원이 질문을 지어내지 않는다" 규칙(AGENTS.md 5절 2항)을 고쳤다. 남는 위험: 생성 모델이 역할 문서의 문체를 따라 검색에 유리한 질문을 만들 수 있고, 같은 계열 모델이 질문 생성과 답변을 모두 하면 편향이 겹친다 — 다중 생성 모델 균형(조건 ⑤)과 실제 질문 추가 비교로 줄인다. 평가 후보 모델은 기술 스택이 정해져야 알 수 있어, 생성 모델 선택은 스택 인터뷰 뒤에 확정한다. 역할 정의 문서의 정확한 선정, 생성 프롬프트 초안, 언어(영어)는 아직 정하지 않았다.
- **Status**: Accepted (사용자 결정 2026-10-04)
- **Date**: 2026-10-04

## DEC-022: 사용자는 질문 전에 유형과 새 부서를 고른다 — 도메인 최대 2개, 질문 분류는 규칙 + LLM(잠정)
- **Decision**: 서비스는 질문을 받기 전에 **사용자 유형(신규 입사자 / 부서 이동자)** 과 **새 부서(도메인)** 를 선택하게 한다. 이름·사번 등 개인 식별 정보는 받지 않고 저장하지 않는다. 이동자의 이전 부서는 묻지 않는다. 질문당 도메인은 **최대 2개**까지 허용하고(선택한 도메인 + 필요 시 1개 추가), 공용 폴더는 항상 포함한다. 질문 분류는 **규칙 + LLM 혼합**(규칙으로 먼저 보정, 규칙으로 안 정해질 때 LLM)을 잠정안으로 하고 세부는 PoC에서 정한다.
- **Reason**: 2026-10-04 사용자 결정(인터뷰 Q3·R4와 B-5 논의). 유형과 부서를 입력으로 받으면 분류가 단순해지고 이동자에 맞춘 검색·생성을 할 수 있다. 개인 식별 정보 범위를 최소로 둔다.
- **Alternatives**: 질문에서 유형을 자동 추출 — 틀릴 수 있고 정확도를 따로 재야 해서 기각. 구분 없이 같은 흐름 — 이동자의 재온보딩 범위(고통 포인트 5번) 활용 불가로 기각. 이전 부서까지 입력 — 입력이 늘고 개인정보 범위가 커져 이번 범위에서 제외(고통 포인트 6번은 다루지 않음).
- **영향**: `docs/기획v1.md` 5절 ①②와 단계 표에 반영. `user_type`이 검색·생성을 어떻게 바꾸는지는 가설(이동자에게 전사 온보딩 항목 제외·표시)이고 PoC에서 확인한다. 규칙 사전·LLM 호출 조건·분류 정확도 평가셋은 미정이다.
- **Status**: Accepted (사용자 결정 2026-10-04, 분류 세부는 잠정)
- **Date**: 2026-10-04

## DEC-024: "질문자≠정답 표시자" 규칙을 없애고 "질문 생성 세션에서 이어 하지 않기"로 대체한다
- **Decision**: 평가 질문의 정답을 표시할 때 "질문을 준 사람은 자기 질문의 정답 표시자가 되지 않는다"(DEC-016 ③)는 규칙을 **없앤다.** 대신 **AI 세션(웹 채팅·에이전트 등)에서 질문을 만들거나 추출하거나 다듬은 경우(합성 질문 생성, FAQ 추출·정리, 실제 질문 비식별 처리 등), 그 세션에서 이어서 정답을 표시하거나 검증하지 않는다.** 같은 세션에서 이어 하게 되면 **작업을 멈추고 다른 세션에서 하도록 요청한다.** 사람이 직접 수집·정리해 AI 세션을 거치지 않은 질문에는 분리할 세션이 없어 해당 없음이다. `labeler_id`(실명 대신 임의 ID, 대응표는 저장소 밖)와 실제 질문의 비식별 기록·커밋 전 비식별 검토 1명(DEC-016 ①)은 그대로 유효하다. `AGENTS.md` 5절 2항과 `docs/기획v1.md` 3절 "평가" 행에 반영.
- **Reason**: 2026-10-06 사용자 결정(이유 설명은 받지 않음). 참고(작성자 추정, 사용자 확인 전): 자기가 작성한 코드를 같은 컨텍스트에서 리뷰하지 않는 규칙(`AGENTS.md` 6절)과 같은 원리, 즉 질문을 만든 맥락이 정답 표시로 이어지지 않게 하려는 것으로 보인다.
- **Alternatives**: 기존 규칙 유지, 두 규칙 모두 적용 — 사용자가 대체를 선택했다.
- **영향 / 알려진 위험**: DEC-016 ③이 이 규칙을 둔 이유는 "비식별 질문 옆 실명이 질문자를 다시 드러낸다"(8차 리뷰 `39e4822`)였다. 지금은 실명 대신 `labeler_id`를 쓰고 대응표를 저장소 밖에 두므로 위험이 줄었지만, **실제 질문의 질문자가 팀원이면서 자기 질문을 표시하면 `labeler_id`와 `source_id`로 질문자가 추정될 여지는 남는다.** 그래서 `labeler_id` 대응표와 `source_id` 원본은 저장소 밖에 두는 규칙을 반드시 지킨다.
- **후속(미결)**: 평가표에 세션 분리를 지켰는지 남기는 확인 항목(예: `session_separation_checked` 같은 비식별 값, 채팅 URL·계정 정보는 저장하지 않음)은 DB·평가표 필드를 정하는 10/6 회의 결과와 함께 정한다(PR #19 자동 리뷰 선택 개선).
- **Status**: Accepted (사용자 결정 2026-10-06)
- **Date**: 2026-10-06

## DEC-026: `chunk_key`는 네 값을 이은 단일 해시 키(A안)로 확정한다
- **Decision**: 청크와 임베딩·응답을 연결하는 공용 키 `chunk_key`는 **단일 키**다. `chunk_key = sha256(UTF-8(source_path ␟ commit_sha ␟ heading_path ␟ chunk_hash)).hexdigest()[:32]`(`␟`=U+001F, 소문자 hex). `commit_sha`는 데이터가 고정 스냅샷(`0ab0299…`)과 같으면 그 40자 SHA, 다르면 `dirty`. `heading_path`는 H2~H4 제목 원문을 `>`로 이은 값. `chunk_hash`는 "공백 정리"(DEC-019)한 `chunk_text`의 sha256 앞 16자. `doc_id = sha256(source_path ␟ commit_sha).hexdigest()[:16]`. 같은 키가 둘 이상 나오면 색인을 중단한다. 고정 검증값: `("sales/a.md", "0ab0299ce073b847558867ae5abbc42c570bc8d5", "A>B", "abc123")` → `5203c258dd38e5392a58755a62840ae0`.
- **Reason**: 2026-10-06 사용자 결정(A안으로 진행). 팀 의견: 박예원 A안, 박성호 A안, 우지훈 A안, 이승노 의견 대기. 실측(영업·지원 청크 15,661개): 네 값은 전부 구분되고 `chunk_hash`를 빼면 1,417행이 겹쳐 `chunk_hash`는 키에 꼭 필요하다. 응답의 `source`(`path#heading`)는 고유하지 않아 키를 대신할 수 없다.
- **Alternatives**: 네 컬럼 복합키(B안) — 임베딩 표마다 네 칸이 반복되고 문서 여러 곳을 고쳐야 해서 탈락. ERD에는 비교 배경으로만 남긴다.
- **영향**: `docs/ERD.md`·`docs/PRD.md`를 단일 키 하나로 확정(이 PR). PR #20 구현에서 "provisional" 표시를 제거하고 재색인한다. 모든 도메인이 같은 계산식을 쓴다. **계산식을 바꾸면 모든 도메인의 청크·임베딩을 다시 만들어야 한다**(색인 설명의 `chunk_key_recipe`가 달라지면 `eval`이 거부한다).
- **Status**: Accepted (사용자 결정 2026-10-06, 이승노 확인 대기 — 바뀔 수 있음)
- **Date**: 2026-10-06

## DEC-027: 공용 DB는 Supabase로 진행하고 담당 구조는 변경 가능성을 기록해 정한다
- **Decision**: 하나의 공용 DB는 **Supabase(PostgreSQL + pgvector)** 로 진행한다(박성호 제안). 담당 구조(**변경 가능**): 박성호 = Supabase 프로젝트·권한·지출 상한·접속 규칙, 우지훈 = 표 설계 SQL·적재 스크립트 초안, 이승노 = DB 설계 검토(본인 확인 대기). 박성호 답변: Pro 플랜, 전용 새 프로젝트 생성, 지출 상한 설정, 종료 후 포트폴리오로 안 쓰면 삭제, 권한 부여 가능 여부 확인 중. 미확인: 월 비용·팀원 추가 비용, 대체 관리자, 프로젝트 이름·리전. 진행 방식(전면 사용 vs 개발은 로컬·통합은 Supabase에 적재하는 단계적 방식)은 아직 정하지 않았다(권장: 단계적).
- **접속 규칙**: 접속 문자열·비밀번호·API 키(특히 서비스 롤 키)는 코드·로그·PR·이슈·디스코드 공개 채널에 올리지 않고 각자 `.env`의 `VECTOR_DB_URL`에만 보관한다. 팀원은 조직 멤버 초대를 우선하고, 문자열이 필요하면 권한이 제한된 별도 DB 역할의 것만 비공개로 전달한다. 접속은 IPv4가 되는 공유 풀러 주소를 우선 쓴다.
- **Reason**: 2026-10-06 사용자 결정("Supabase로 진행하자", 이유 설명은 받지 않음). 참고: 결제가 이미 되어 있고 4명이 같은 DB에 동시에 접근할 수 있다.
- **Alternatives**: SQLite 파일 하나(박예원 의견, 서버 불필요) — 로컬 개발과 대체안으로 유지한다. 박예원의 이의 여부 확인 중.
- **영향**: `docs/기획v1.md` 4절 영업·지원 DB 행, `docs/ERD.md` 저장 엔진 문구. 새 코드(스키마 SQL, 적재)는 접속 방식 확인 뒤 별도 코드 PR. 공식 문서로 확인한 한도: Free는 DB 500MB 초과 시 읽기 전용, Pro는 디스크 8GB 포함·자동 확장, 직접 접속은 IPv6(IPv4는 풀러 또는 유료 애드온).
- **Status**: Accepted (사용자 결정 2026-10-06, 박성호 확인 3개·박예원 이의·이승노 의견 대기 — 바뀔 수 있음)
- **Date**: 2026-10-06

## DEC-028: 인용 일치에 양 끝 경계 문자 정리를 허용하고 표시는 원문 구간으로 교체한다
- **Decision**: `evidence_quote`가 청크에 있는지 확인하는 일치 기준을 "공백 정리만"(DEC-019)에서 **"공백 정리 + 인용문 양 끝의 경계 문자 정리"**로 넓힌다. 경계 문자는 목록 기호(`- `·`* `·`1. `), 감싼 따옴표(`" ' “ ” ‘ ’`), 줄임표, 끝 구두점(`. , ; : ! ? — – -`)이다. **가운데의 글자·대소문자·구두점은 정확히 같아야** 하고, 정리 뒤 12자 미만이면 인정하지 않는다. 통과한 항목의 `evidence_quote`는 모델이 쓴 문자열이 아니라 **코드가 원문(모델에게 보낸 앞 2,000자 범위)에서 찾은 정확한 구간**으로 교체하고 모델 원문은 `model_quote`에 보관한다. `criteria`·`check_method`는 교체된 원문 구간을 기준으로 비교한다. 정리 없이 통과한 인용은 그대로, 정리로 통과한 건수는 `quote_boundary_adjusted`로 센다.
- **Reason**: 2026-10-06 사용자 결정(B안). 근거(프롬프트 v2, 같은 30개 3회): 제거된 인용문 55건 중 약 80~90%가 "내용은 같고 양 끝 문자만 다름"이었고(모델이 따옴표로 감싸거나 목록 기호·끝 마침표를 붙이거나 뗌), 이 규칙을 저장된 실행에 다시 적용하면 인용문 확인율이 **0.772 → 0.900**(v1 0.612 → 0.781)이 된다. 사용자에게 보이는 인용문은 항상 코드가 원문에서 잘라 온 구간이라 "인용이 원문에 있다"는 보장은 오히려 더 강해진다.
- **Alternatives**: ① 엄격 유지(공백 정리만) — 계약은 그대로지만 모델이 경계 문자를 계속 틀려 사용자에게 보이는 항목이 줄어듦. ② 대소문자·가운데 구두점까지 무시 — 숫자·부정어 차이를 가릴 수 있어 탈락.
- **영향**: `scripts/sales_support_llm.py`(PR #20), `docs/기획v1.md` 5절 ⑦. 한계: 이 검사가 보장하는 것은 여전히 "인용문이 원문에 있다"까지이고 항목·이유가 인용문의 뜻과 맞는지는 사람이 확인한다. 가운데가 다른 인용(약 24건/55건)은 계속 거부된다. 프롬프트 v2에서 `not_in_text`로 분류된 2건은 사람이 확인한다.
- **Status**: Accepted (사용자 결정 2026-10-06)

## DEC-029: 웹 화면은 React(`frontend/`), 서버는 FastAPI(`api/`)로 두고 같은 저장소에서 관리한다
- **Decision**: 웹 화면(F·E)은 **React**로 만들고(박예원 담당) 저장소 루트 **`frontend/`**에 둔다. 서버(API)는 **FastAPI**로 만들고(우지훈 담당) **`api/`**에 둔다. 서버는 질문 한 번에 `{commit_sha, items}` **전체를 JSON 한 번에** 돌려준다(스트리밍 없음). 프런트 패키지 관리는 **npm**이고 `package-lock.json`을 커밋하며, **Node 버전은 `frontend/.nvmrc`에 우지훈이 고정**한다. 프런트 CI는 기존 `lint-and-test`와 **별도 워크플로**(`frontend-ci.yml`)로 두고 **필수 체크로 올리지 않으며**, `frontend/package.json`이 있을 때만 검사한다. **발표 데모는 발표자 노트북에서 로컬 실행**(서버 + React 개발 서버)하고 10/19에 녹화본을 준비한다(진행계획 위험표 그대로). 일정은 **A안**: 10/10 전에 API 약속을 `docs/PRD.md` 6-1절에 확정하고, 프런트는 그 JSON 목업으로 먼저 개발해 10/14에 서버와 연결한다.
